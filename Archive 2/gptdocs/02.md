# `docs/01_STUDIO_IDENTITY.md`를 작성하라

현재 저장소는 여러 게임 프로젝트의 그래픽 아트 제작을 담당하는 독립적인 **Game Art Studio**다.

이번 작업에서는 다음 파일 하나만 작성한다.

`docs/01_STUDIO_IDENTITY.md`

이미 `CLAUDE.md`가 존재한다면 먼저 읽어서 최상위 원칙과 충돌하지 않도록 하라.

그러나 `CLAUDE.md`의 내용을 다시 요약해서 반복하는 문서를 만들지 마라.

이 문서의 목적은 단 하나다.

> **이 Art Studio가 무엇이며, 무엇을 위해 존재하고, 어디까지를 자신의 작업 영역으로 보는지를 정의한다.**

---

# 1. 이 문서의 역할

`01_STUDIO_IDENTITY.md`는 Art Studio의 **정체성 정의서**다.

Claude Code의 세부 행동 규칙을 적는 문서가 아니다.

특정 게임의 아트 디렉션 문서도 아니다.

이미지 생성 파이프라인 설명서도 아니다.

도구 사용 매뉴얼도 아니다.

에셋 규격 문서도 아니다.

이 문서를 읽은 사람이 다음 질문에 명확하게 답할 수 있어야 한다.

* 이 저장소는 왜 존재하는가?
* 무엇을 만드는 조직인가?
* 일반 게임 개발 프로젝트와 무엇이 다른가?
* 일반 이미지 생성 프로젝트와 무엇이 다른가?
* 특정 화풍 전문 스튜디오인가?
* 어떤 종류의 게임과 아트를 담당할 수 있는가?
* 게임 프로젝트와 어떤 관계를 가지는가?
* 이곳에서 축적해야 하는 핵심 역량은 무엇인가?

---

# 2. 기본 정체성

Art Studio를 다음과 같이 정의한다.

> 여러 게임 프로젝트의 시각적 방향을 실제 제작 가능한 그래픽 자산으로 구현하기 위해 존재하는 독립적인 게임 아트 제작 워크스페이스.

이 스튜디오는 하나의 게임을 위해 만들어진 프로젝트가 아니다.

여러 게임을 동시에 또는 순차적으로 담당할 수 있다.

게임마다 장르, 플랫폼, 카메라, 표현 방식, 그래픽 밀도와 화풍이 완전히 달라도 된다.

예를 들어 다음 프로젝트가 같은 Art Studio를 사용할 수 있다.

* 픽셀 아트 기반 2D 게임
* HD-2D 게임
* Roblox 캐주얼 게임
* 역사 시뮬레이션
* 탑뷰 전략 게임
* 보드게임
* 플랫포머
* 액션 게임
* 공포 게임
* 아이소메트릭 게임
* 일러스트 중심 게임
* 3D 게임
* 웹게임

이 목록을 지원 범위의 제한으로 정의하지는 않는다.

새로운 게임이나 새로운 표현 방식이 등장하면 그에 맞는 제작 방법을 선택할 수 있어야 한다.

# 3. 특정 화풍을 갖지 않는다

Art Studio 자체의 고정 화풍을 만들지 않는다.

다음 중 어느 것도 스튜디오 전체의 기본 스타일이 아니다.

* 픽셀 아트
* HD-2D
* 애니메이션풍
* 반실사
* 사실적 렌더링
* 로우폴리
* 수채화
* 레트로
* 현대적 모바일 게임풍
* 특정 시대의 게임 그래픽

스타일은 **스튜디오의 속성이 아니라 각 게임 프로젝트의 속성**이다.

따라서 한 게임에서 사용한 팔레트, 비율, 픽셀 밀도, 조명 방식, 캐릭터 형태 등을 다른 게임에 자동으로 적용하지 않는다.

Art Studio가 잘해야 하는 것은 하나의 화풍을 반복하는 것이 아니라:

> **주어진 아트 방향을 빠르게 이해하고, 그 방향에 맞는 제작 방법으로 전환하는 능력**

이다.

# 5. 단순 이미지 생성 프로젝트가 아니다

Art Studio를 “AI로 이미지를 만드는 프로젝트”로 정의하지 않는다.

이미지 생성은 여러 제작 방법 중 하나다.

실제 작업은 필요에 따라 다음을 포함할 수 있다.

* 직접 생성
* 이미지 편집
* 레퍼런스 기반 변형
* 여러 결과의 조합
* 색상 수정
* 크기 조정
* 도트화
* 팔레트 변환
* 타일 제작
* 스프라이트 시트 구성
* 애니메이션 프레임 제작
* 텍스처 제작
* 3D 렌더를 2D 에셋의 기반으로 활용
* 외부 에셋 수정
* 기존 에셋 재가공
* 사람이 제작한 원본의 기술적 처리
* 생성형 도구 없이 제작되는 작업

따라서 이 프로젝트의 핵심 역량을 특정 생성 모델의 프롬프트 작성 능력으로 축소하지 않는다.

---

# 6. 일반 게임 개발 프로젝트와도 다르다

Art Studio는 게임의 전체 구현을 담당하는 개발 저장소가 아니다.

기본적으로 다음은 Art Studio의 주된 책임이 아니다.

* 게임 규칙 구현
* 전투 시스템 개발
* 네트워크 시스템
* 데이터베이스
* 서버
* 저장 시스템
* 전체 UI 로직
* 게임 경제
* NPC AI
* 게임의 핵심 코드 아키텍처

다만 좋은 아트 결과를 만들기 위해 게임 엔진이나 게임 프로젝트를 활용하는 것은 가능하다.

예:

* 실제 카메라에서 캐릭터 크기를 확인한다.
* Unity에서 조명을 적용해 본다.
* Godot에서 타일의 반복감을 확인한다.
* Roblox Studio에서 실제 플레이 거리에서 가독성을 확인한다.
* 애니메이션이 엔진에서 자연스럽게 연결되는지 확인한다.

즉 게임 엔진은 경우에 따라 **Art Studio의 검증 환경 또는 제작 도구**가 될 수 있다.

게임 개발 전체를 Art Studio가 흡수하지는 않는다.

이 스튜디오의 산출물은 단순히 “이미지 파일”이 아니다.

작업에 따라 다음과 같은 결과물이 만들어질 수 있다.

* 컨셉 후보
* 스타일 탐색 결과
* 캐릭터 시안
* 환경 시안
* 승인된 원본 에셋
* 게임 엔진용 변환본
* 스프라이트 시트
* 타일셋
* 텍스처
* VFX 소스
* 에셋 규격 정보
* 제작에 사용된 설정
* 재생성에 필요한 프롬프트 또는 파라미터
* 비교용 리뷰 자료
* 게임 적용 후 스크린샷
* 제작 과정에서 축적된 기술적 노하우

모든 작업이 이 산출물을 전부 만들어야 하는 것은 아니다.

작업 목적에 필요한 것만 만든다.

# 8. 프로젝트와 스튜디오의 관계

각 게임은 자신의 정체성을 가진다.

Art Studio는 그 정체성을 소유하지 않는다.

게임 프로젝트에서는 필요에 따라 다음과 같은 정보가 Art Studio로 전달될 수 있다.

* 게임의 기본 설명
* 장르
* 플랫폼
* 카메라
* 현재 아트 방향
* 레퍼런스
* 스타일 규격
* 필요한 자산 목록
* 기존 에셋
* 디렉터의 피드백과 결정

Art Studio는 이 정보를 바탕으로 해당 게임에 맞는 제작 환경을 구성한다.

따라서 관계는 다음과 같이 이해한다.

```text
게임 프로젝트
    │
    │ 아트 요구사항 / 방향 / 레퍼런스
    ▼
ART STUDIO
    │
    │ 탐색 / 제작 / 가공 / 검증
    ▼
게임용 아트 자산
    │
    ▼
게임 프로젝트
```

이 과정은 일방향 납품만을 의미하지 않는다.

게임에 실제 적용한 결과를 다시 Art Studio에서 확인하고 수정하는 왕복 작업도 가능하다.

---

# 9. 제작 방식은 프로젝트에 종속된다

Art Studio 내부에 하나의 절대적인 제작 파이프라인을 두지 않는다.

어떤 게임에서는:

```text
레퍼런스
→ 이미지 생성
→ 수정
→ 승인
→ Unity 적용
```

이면 충분할 수 있다.

다른 게임에서는:

```text
컨셉
→ 3D 블록아웃
→ 렌더
→ 픽셀 변환
→ 손질
→ 스프라이트 시트
→ Godot 적용
```

일 수도 있다.

또 다른 게임에서는 사람이 만든 그림을 단순히 게임 규격으로 가공하는 것이 전부일 수도 있다.

따라서 Art Studio는 하나의 파이프라인을 모든 프로젝트에 강제하지 않는다.

대신 필요한 제작 능력을 모듈처럼 보유하고 조합한다.

---

# 10. 이 스튜디오가 축적해야 할 것

게임별 화풍은 서로 격리해야 하지만, 제작 경험까지 버려서는 안 된다.

Art Studio가 장기적으로 축적해야 하는 것은 **범용적인 제작 능력과 기술적 노하우**다.

예를 들어:

* 레퍼런스를 분석하는 방법
* 다양한 생성 도구의 특성과 한계
* 이미지 후처리 방법
* 픽셀 아트 검증 방법
* 타일 제작과 검사 방법
* 배경 제거 방법
* 스프라이트 시트 제작 방법
* 애니메이션 자산 가공 방법
* 텍스처 제작 방법
* 이미지 변환 방법
* 게임 엔진별 전달 경험
* 자동화 가능한 반복 작업
* 품질 비교 방법
* 파일 및 버전 관리 방법

이를 통해 새로운 게임이 들어왔을 때 처음부터 모든 제작 체계를 다시 만들지 않아도 되도록 한다.

다만 이전 게임의 스타일 자체를 새 게임의 기본값으로 복사해서는 안 된다.

# 11. Art Studio의 전문성

이 스튜디오가 지향하는 전문성은:

> 모든 화풍을 동일한 방식으로 만들 수 있다는 의미의 범용성이 아니다.

오히려:

> 서로 다른 화풍과 제작 조건을 구분하고, 각각에 맞는 도구와 방법을 선택할 수 있는 범용성이다.

예를 들어 픽셀 아트와 반실사 일러스트는 같은 규칙으로 제작하지 않는다.

2D 캐릭터와 아이소메트릭 타일도 같은 문제로 보지 않는다.

Roblox용 자산과 고밀도 PC 게임용 자산도 동일한 기술 규격을 사용하지 않는다.

전문성은 모든 것을 하나의 방식으로 통일하는 데 있지 않고, **문제의 종류를 구분하는 능력**에 있다.

---

# 12. 사람과 도구

Art Studio는 사람의 아트 디렉팅 능력을 대체하기 위해 존재하지 않는다.

게임 디렉터가 방향을 정하고 최종 결과를 판단한다.

이 스튜디오는 그 방향을 구현하기 위해 필요한 다양한 수단을 제공한다.

Claude Code, 이미지 생성 AI, 외부 API, MCP, Blender, Unity, Godot, Roblox Studio, 이미지 처리 프로그램 및 기타 도구는 모두 그 수단이 될 수 있다.

어떤 도구도 Art Studio 자체와 동일시하지 않는다.

예를 들어:

> Art Studio = Claude Code

가 아니다.

Claude Code는 Art Studio를 운영하고 여러 제작 수단을 연결하는 중요한 작업 환경 중 하나다.

마찬가지로:

> Art Studio = AI 이미지 생성

도 아니다.

생성형 AI 역시 제작 수단 중 하나다.

---

# 13. 지향하는 작업 경험

Art Studio는 디렉터가 기술적인 잡무 때문에 아트 판단의 흐름을 잃지 않도록 돕는 것을 지향한다.

좋은 작업 경험은 다음과 같다.

디렉터는:

* 방향을 설명한다.
* 레퍼런스를 제시한다.
* 후보를 비교한다.
* 선택한다.
* 수정 방향을 말한다.
* 실제 게임 화면을 보고 다시 판단한다.

Art Studio는:

* 필요한 자료를 정리한다.
* 적합한 제작 방법을 준비한다.
* 후보를 제작하거나 제작 도구를 연결한다.
* 반복적인 기술 작업을 처리한다.
* 결과를 비교 가능한 형태로 정리한다.
* 채택된 결과를 게임에서 사용할 수 있도록 준비한다.

이 관계를 지나치게 복잡한 승인 시스템이나 자동화 파이프라인으로 만들지 않는다.

# 14. 이 문서가 정의하지 않는 것

다음 내용은 이 문서에서 세부적으로 정의하지 않는다.

* 디렉터와 Claude 사이의 세부 권한 경계
* 저장소의 구체적인 폴더 구조

# 15. 문서의 마지막에 담아야 할 핵심

문서 마지막에는 이 Art Studio의 정체성을 짧고 명확하게 정리한다.

의미는 다음과 같아야 한다.

> Art Studio는 특정 화풍의 이미지 생성기가 아니다.
>
> 여러 게임의 서로 다른 아트 디렉션을 이해하고, 각각에 적합한 제작 수단을 선택하여 실제 게임용 그래픽 자산으로 구현하는 독립적인 제작 조직이다.
>
> 게임마다 스타일은 달라지지만, 제작 기술과 경험은 스튜디오에 축적된다.
>
> 도구와 자동화는 목적이 아니라 디렉터의 작업 능력을 확장하기 위한 수단이다.

문장을 그대로 복사할 필요는 없지만 의미는 유지한다.

# 작성 원칙

* 한국어로 작성한다.
* `CLAUDE.md`와 중복되는 행동 규칙을 불필요하게 반복하지 않는다.
* 정체성 정의에 집중한다.
* 구체적인 구현 세부사항을 미리 결정하지 않는다.
* 특정 게임을 중심 사례로 만들지 않는다.
* 특정 도구를 핵심 전제로 삼지 않는다.
* 현재 존재하지 않는 자동화나 기능이 이미 구현되어 있다고 쓰지 않는다.
* 지나치게 기업 조직도처럼 만들지 않는다.
* AI 시스템 설계 문서처럼 만들지 않는다.
* 게임 아트를 실제로 제작하는 작업실이라는 감각을 유지한다.
* 간결한 원칙과 필요한 설명을 균형 있게 구성한다.
* 이후 문서들이 각각 자신의 역할을 가질 수 있도록 경계를 지킨다.
