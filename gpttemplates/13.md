# `templates/PROJECT_BRIEF.md`를 작성하라

현재 저장소는 여러 게임 프로젝트의 그래픽 아트 제작을 담당하는 독립적인 **Game Art Studio**다.

이번 작업에서는 다음 파일 하나만 작성한다.

`templates/PROJECT_BRIEF.md`

먼저 아래 문서를 읽는다.

* `CLAUDE.md`
* `docs/01_STUDIO_IDENTITY.md`
* `docs/02_DIRECTOR_RELATIONSHIP.md`
* `docs/03_PROJECT_STRUCTURE.md`
* `docs/04_ART_DIRECTION_SYSTEM.md`
* `docs/05_TOOL_ROLES.md`

기존 문서의 철학과 역할 분리를 유지한다.

이번 문서는 Art Studio 자체의 운영 문서가 아니라, **새로운 게임 프로젝트를 Art Studio에 등록할 때 복제해서 사용하는 프로젝트별 템플릿**이다.

목적은 하나다.

> **Art Studio가 해당 게임이 무엇인지, 어떤 환경에서 플레이되는지, 어떤 종류의 아트가 왜 필요한지를 빠르게 이해할 수 있도록 최소한의 프로젝트 맥락을 제공한다.**

---

# 1. `PROJECT_BRIEF.md`의 역할

`PROJECT_BRIEF.md`는 게임의 전체 기획서를 대체하지 않는다.

또한 `ART_DIRECTION.md`를 대체하지 않는다.

이 문서는 Art Studio가 작업을 시작하기 위해 필요한 **게임 맥락의 요약본**이다.

이 문서를 읽으면 최소한 다음 질문에 답할 수 있어야 한다.

* 이 게임은 무엇인가?
* 플레이어는 무엇을 하는가?
* 어떤 장르인가?
* 어떤 플랫폼에서 실행되는가?
* 어떤 카메라와 화면 구성을 사용하는가?
* 어떤 플레이 상황에서 아트가 보이는가?
* 어떤 자산을 만들어야 하는가?
* 현재 개발 단계는 어디인가?
* 기존 아트가 존재하는가?
* Art Studio가 이번 프로젝트에서 맡아야 할 범위는 어디까지인가?

---

# 2. 가장 중요한 원칙

`PROJECT_BRIEF.md`는 **게임 설명 문서**다.

화풍 세부 규칙을 적는 문서가 아니다.

다음 내용은 기본적으로 `ART_DIRECTION.md` 또는 후속 `STYLE_SPEC.md`가 담당한다.

* 팔레트
* 아웃라인
* 캐릭터 비율의 세부 규칙
* 픽셀 밀도
* 명암 단계
* 조명 스타일
* 브러시 질감
* 세부 색상 규칙
* 스타일 레퍼런스 분석
* 금지하는 화풍

`PROJECT_BRIEF.md`에서는 이러한 내용이 필요하다면 짧게 연결만 하고, 상세하게 중복 작성하지 않는다.

---

# 3. 템플릿은 짧고 실제로 채우기 쉬워야 한다

이 문서는 새 게임을 시작할 때마다 사용한다.

따라서 거대한 설문지가 되어서는 안 된다.

모든 항목을 반드시 채워야 하는 양식으로 만들지 않는다.

아직 정해지지 않은 정보는 다음과 같이 표시할 수 있어야 한다.

```text id="ru3xej"
미정
없음
확인 필요
현재 탐색 중
```

빈칸을 채우기 위해 임의의 결정을 만들지 않는다.

---

# 4. 문서 상단 — 프로젝트 식별 정보

템플릿 상단에 간단한 프로젝트 식별 영역을 둔다.

포함할 수 있는 항목:

* 프로젝트 이름
* 프로젝트 ID
* 문서 상태
* 마지막 업데이트
* 게임 프로젝트 위치 또는 연결 정보
* 사용 엔진
* 목표 플랫폼

단, 아직 별도의 복잡한 metadata 형식이나 YAML frontmatter를 강제하지 않는다.

읽기 쉬운 Markdown 형식을 사용한다.

예시 구조의 의미:

```text id="avty66"
# PROJECT BRIEF

## 프로젝트 정보

- 프로젝트 이름:
- 프로젝트 ID:
- 개발 엔진:
- 목표 플랫폼:
- 현재 단계:
- 게임 저장소:
```

정확한 항목명과 구조는 문서 목적에 맞게 정리한다.

---

# 5. 한 문장 설명

가장 먼저 게임을 한 문장으로 설명할 수 있는 항목을 둔다.

예:

```text id="0yxuvp"
한국의 골목 놀이를 1인칭 팀 기반 추격전으로 재해석한 캐주얼 멀티플레이 게임.
```

또는:

```text id="7qb9hw"
주사위를 굴려 보드를 순환하면서 영지를 성장시키고 상대와 전투하는 판타지 전략 보드게임.
```

이 문장은 마케팅 카피가 아니다.

Art Studio가 게임의 종류를 즉시 이해하기 위한 설명이다.

---

# 6. 게임의 핵심 경험

게임 규칙 전체를 복사하지 않는다.

Art Studio가 시각적으로 이해해야 하는 핵심 경험만 설명한다.

예:

* 빠르게 추격하고 숨는다.
* 넓은 맵에서 상대의 위치를 추론한다.
* 작은 유닛 여러 개를 동시에 관리한다.
* 보드 위에서 캐릭터가 이동한다.
* 플레이어가 캐릭터를 가까이서 오래 본다.
* 많은 적이 화면에 동시에 등장한다.
* 플레이어가 환경을 탐색하며 단서를 찾는다.

이 정보는 아트 제작에 직접 영향을 준다.

예를 들어:

```text id="m6zynx"
전투 중 캐릭터가 매우 작게 보인다.
```

는 캐릭터 디테일과 실루엣 설계에 중요하다.

---

# 7. 장르

게임 장르를 간단히 기록한다.

예:

* action
* strategy
* RPG
* board game
* platformer
* fighting
* survival
* horror
* casual multiplayer
* simulation
* puzzle

필요하다면 복수 장르를 사용할 수 있다.

장르 이름만으로 아트 스타일을 추론하지 않는다.

---

# 8. 플레이 구조

Art Studio가 화면이 어떤 상황에서 반복적으로 보이는지 이해할 수 있도록 핵심 플레이 구조를 짧게 기록한다.

예:

```text id="145kac"
1 match = 약 5~8분

대기
→ 탐색
→ 추격
→ 교전
→ 결과
```

또는:

```text id="1brnoi"
월드맵
→ 도시 진입
→ 전투
→ 결과
→ 성장
```

이것은 상세 게임 디자인 문서가 아니다.

아트가 등장하는 주요 상황을 이해하기 위한 요약이다.

---

# 9. 플레이어가 가장 자주 보는 것

이 항목은 반드시 고려한다.

Art Studio에게 매우 중요한 정보다.

예:

* 플레이어 캐릭터의 등
* 보드 전체
* 1인칭 손과 아이템
* 캐릭터 초상화
* 전투 유닛
* 도시 건물
* 넓은 환경
* UI 아이콘
* 몬스터
* 카드

Art Studio의 제작 우선순위는 플레이어가 실제로 얼마나 자주 보는가와 관련될 수 있다.

---

# 10. 카메라

카메라는 아트 제작에 직접 영향을 준다.

가능한 정보를 기록한다.

예:

* first-person
* third-person
* side view
* top-down
* isometric
* fixed camera
* orthographic
* perspective

필요하다면 추가로:

* 일반적인 카메라 거리
* 캐릭터 화면 점유율
* 줌 가능 여부
* 플레이 중 시점 변화

등을 기록할 수 있다.

정확한 수치가 아직 없으면 억지로 정하지 않는다.

---

# 11. 플랫폼

목표 플랫폼을 기록한다.

예:

* PC
* Web
* Roblox
* Android
* iOS
* Console
* multi-platform

플랫폼은 다음과 같은 아트 결정에 영향을 줄 수 있다.

* 화면 크기
* 성능
* texture size
* 가독성
* 입력 방식
* UI 크기
* asset complexity

하지만 이 문서에서 플랫폼별 기술 규격까지 정의하지 않는다.

---

# 12. 화면 비율 및 해상도

이미 알려져 있다면 기록한다.

예:

```text id="ea68bq"
기본 화면 비율: 16:9
목표 기준 해상도: 1920×1080
모바일 대응: 필요
```

내부 렌더 해상도나 픽셀 아트 해상도처럼 화풍에 직접 관련된 값은 `STYLE_SPEC`에서 상세화할 수 있다.

---

# 13. 게임의 세계

Art Studio가 환경과 캐릭터의 맥락을 이해할 수 있을 정도로만 세계를 설명한다.

예:

* 현대 한국 골목
* 삼국시대 중국
* 가상의 산업 도시
* 동화풍 판타지 세계
* 폐쇄된 호텔
* 우주 식민지

긴 세계관 설정을 모두 복사하지 않는다.

아트 제작에 직접 필요한 내용에 집중한다.

---

# 14. 시대와 장소

특히 디자인에 영향을 준다면 별도로 기록한다.

예:

```text id="xtp8q4"
시대: 1990년대 후반
장소: 한국 지방 소도시
```

또는:

```text id="byplbx"
시대: 후한 말~삼국시대
지역: 중국
```

역사적 고증이나 문화적 맥락이 중요한 경우 이후 reference와 Art Direction에서 더 상세하게 다룰 수 있다.

---

# 15. 게임의 주요 대상

Art Studio가 우선 이해해야 하는 핵심 대상을 기록한다.

예:

* 플레이어 캐릭터
* 주요 NPC
* 적
* 보스
* 진영
* 핵심 건물
* 주요 아이템
* 차량
* 몬스터
* 맵의 랜드마크

모든 자산을 나열하는 manifest가 아니다.

게임의 시각적 중심이 무엇인지 알려주는 항목이다.

---

# 16. 자산 범위

현재 Art Studio에 요청되는 자산 종류를 기록할 수 있는 섹션을 둔다.

예:

```text id="jglrq5"
현재 예상 범위:

- 캐릭터
- 몬스터
- 환경
- 타일
- 소품
- UI 그래픽
- 아이콘
- 초상화
- VFX
- 텍스처
```

해당되지 않는 항목은 제거할 수 있다.

향후 정확한 목록은 `ASSET_MANIFEST.md`가 담당한다.

---

# 17. 현재 가장 중요한 자산

모든 자산을 동시에 만들지 않을 수 있으므로 현재 우선순위를 기록할 수 있게 한다.

예:

```text id="jrtqnm"
현재 우선순위:

1. 플레이어 캐릭터 기본 디자인
2. 일반 적 실루엣
3. 핵심 맵 환경
```

이것은 전체 asset manifest의 대체물이 아니다.

현재 제작 방향을 이해하기 위한 정보다.

---

# 18. 기존 아트 상태

새 프로젝트라고 해서 항상 아트가 없는 것은 아니다.

다음 중 어떤 상태인지 기록할 수 있어야 한다.

예:

```text id="y39dbn"
- 기존 아트 없음
- 컨셉아트만 존재
- placeholder 존재
- 이미 제작된 일부 에셋 존재
- 기존 게임 버전의 아트 존재
- 외부 구매 에셋 사용 중
```

기존 자료가 있다면 위치를 연결할 수 있도록 한다.

---

# 19. 레퍼런스 상태

레퍼런스가 어디에 있는지 기록한다.

예:

```text id="w9j4h7"
references/
```

또는 외부 문서나 실제 게임 프로젝트 위치를 연결할 수 있다.

이 문서에 레퍼런스 분석 내용을 길게 쓰지 않는다.

그 내용은 `ART_DIRECTION.md`에서 다룬다.

---

# 20. 개발 단계

게임의 개발 단계는 아트 제작 방식에 영향을 준다.

예:

* idea
* prototype
* vertical slice
* production
* polish
* live service

예를 들어 prototype 단계에서는 정밀한 최종 에셋보다 방향 탐색이 중요할 수 있다.

반대로 production 단계에서는 기존 스타일 일관성이 더 중요할 수 있다.

---

# 21. 현재 게임 구현 상태

필요하다면 아트 관점에서 현재 구현 수준을 기록한다.

예:

```text id="ea2mnb"
- greybox map 존재
- 플레이 가능한 prototype 존재
- 캐릭터는 capsule placeholder
- lighting 임시
- UI 미구현
```

이 정보가 있으면 Art Studio가 실제 게임 화면을 활용한 검증 가능성을 판단할 수 있다.

---

# 22. 게임 엔진과 Art Studio의 관계

프로젝트가 사용하는 엔진을 기록하되, Art Studio가 엔진 전체를 관리하는 것으로 해석하지 않는다.

예:

```text id="im7gvl"
Engine: Unity

Art Studio 활용:
- sprite import 확인
- lighting test
- 실제 표시 크기 screenshot 검증
```

아직 검증 방식이 결정되지 않았다면 비워둘 수 있다.

---

# 23. 플레이 환경

필요하다면 다음과 같은 정보를 적을 수 있다.

* 싱글플레이 / 멀티플레이
* 로컬 / 온라인
* 짧은 세션 / 장시간 플레이
* 모바일 세로 / 가로
* 스트리밍 시청 고려
* 여러 캐릭터 동시 등장
* 빠른 화면 움직임

이 정보는 아트 가독성에 영향을 줄 수 있다.

---

# 24. 대상 플레이어

게임의 주요 대상층이 디자인에 영향을 줄 정도라면 기록한다.

예:

* 어린 플레이어
* Roblox 일반 사용자
* 전략 게임 팬
* 역사 시뮬레이션 팬
* 캐주얼 모바일 사용자
* 성인 공포 게임 사용자

하지만 사용자를 고정관념으로 단순화하여 화풍을 자동으로 결정하지 않는다.

---

# 25. 시각적으로 중요한 게임플레이 정보

아트가 단순 장식이 아니라 게임 정보를 전달해야 하는 경우 기록한다.

예:

* 적과 아군을 즉시 구분해야 함
* 아이템 등급이 멀리서 보여야 함
* 적의 무기 종류를 실루엣으로 구분해야 함
* 안전 지역과 위험 지역이 색으로 구분되어야 함
* 상호작용 가능한 오브젝트가 배경에서 읽혀야 함

이 항목은 매우 중요할 수 있다.

아트 방향은 플레이 가독성과 연결되어야 한다.

---

# 26. 게임에서 피해야 할 기능적 문제

화풍이 아니라 **게임 화면에서 발생하면 안 되는 문제**를 기록할 수 있다.

예:

* 캐릭터가 배경과 섞이면 안 됨
* 작은 화면에서 아이템이 사라져 보이면 안 됨
* 적과 NPC가 혼동되면 안 됨
* 타일 반복이 지나치게 눈에 띄면 안 됨
* UI 그래픽이 플레이 영역보다 강하면 안 됨

미적인 금지사항은 `ART_DIRECTION.md`가 담당한다.

---

# 27. Art Studio의 현재 작업 범위

이번 프로젝트에서 Art Studio가 담당할 영역을 명확히 기록할 수 있어야 한다.

예:

```text id="0pvzjj"
Art Studio 담당:

- 캐릭터 컨셉
- sprite 제작
- 환경 타일
- UI icon
- Unity용 export

Art Studio 비담당:

- UI layout
- 게임 로직
- 애니메이션 코드
- 레벨 디자인
```

프로젝트마다 다를 수 있다.

---

# 28. 외부 제작자 또는 외부 자산

다른 제작자가 존재한다면 필요한 수준에서 기록할 수 있다.

예:

* 3D 캐릭터는 외주 제작
* UI는 별도 디자이너 담당
* 배경은 Asset Store 기반
* 초상화만 Art Studio 담당

Art Studio가 모든 시각 자산을 직접 만든다고 가정하지 않는다.

---

# 29. 기술적 제약

게임 아트 제작에 직접 영향을 주는 기술 제약이 이미 존재한다면 기록할 수 있다.

예:

* 모바일 성능 제한
* texture memory 제한
* Roblox upload 제한
* sprite atlas 사용
* WebGL 대응
* 특정 shader 사용 불가

구체적인 asset validation 규칙은 후속 문서에서 다룬다.

여기서는 이미 알고 있는 중요한 제약을 전달하는 정도로 한다.

---

# 30. 일정과 마일스톤

Art Studio의 제작 우선순위에 실제 영향을 준다면 간단히 기록할 수 있다.

예:

```text id="yd44p0"
Vertical Slice 목표:
2026-09

현재 필요한 것:
주인공 + 일반 적 + 첫 맵
```

복잡한 프로젝트 관리 문서로 만들지 않는다.

---

# 31. 아직 결정되지 않은 것

별도의 섹션으로 두는 것이 좋다.

예:

```text id="4g4oz1"
## 아직 결정되지 않은 것

- 최종 캐릭터 표현 방식
- 카메라 거리
- UI 스타일
- 엔진 조명 사용 범위
```

미정 상태를 명시적으로 유지하면 Claude가 임의로 빈칸을 채우는 것을 방지할 수 있다.

---

# 32. 관련 문서

프로젝트의 다른 핵심 문서로 연결할 수 있는 섹션을 둔다.

예:

```text id="4c8rv2"
## 관련 문서

- `ART_DIRECTION.md`
- `STYLE_SPEC.md`
- `ASSET_MANIFEST.md`
```

존재하지 않는 문서를 이미 작성된 것처럼 표현하지 않는다.

---

# 33. 변경 시점

`PROJECT_BRIEF.md`는 매 작업마다 수정하는 일지 문서가 아니다.

다음과 같은 상황에서 갱신할 수 있다.

* 플랫폼 변경
* 엔진 변경
* 게임 장르 또는 핵심 플레이 구조 변경
* 카메라 변경
* Art Studio 담당 범위 변경
* 주요 개발 단계 변경

작은 아트 피드백은 이 문서에 누적하지 않는다.

---

# 34. 프로젝트 브리프와 아트 디렉션의 경계

반드시 명확하게 구분한다.

예:

```text id="0ypw4v"
PROJECT_BRIEF
"1인칭 추격 게임이며 플레이어는 빠르게 이동한다."

ART_DIRECTION
"빠른 이동 중에도 상대 실루엣이 즉시 읽히도록 큰 색 덩어리와 단순한 형태를 사용한다."
```

또는:

```text id="skxxvh"
PROJECT_BRIEF
"게임 배경은 1990년대 한국 지방 소도시다."

ART_DIRECTION
"실제 사진의 색을 그대로 복제하지 않고, 햇빛에 바랜 간판과 저채도 콘크리트 색을 중심으로 표현한다."
```

전자는 게임의 사실과 맥락이고, 후자는 그 사실을 어떻게 보이게 만들 것인가에 대한 방향이다.

---

# 35. 프로젝트 브리프와 Asset Manifest의 경계

`PROJECT_BRIEF`에서는 주요 자산 종류와 현재 우선순위만 다룬다.

다음처럼 수십 개의 자산을 상세 나열하지 않는다.

```text id="7zr63w"
CHR_001
CHR_002
MON_001
ENV_001
...
```

그것은 `ASSET_MANIFEST.md`의 역할이다.

---

# 36. 프로젝트 브리프와 게임 기획서의 경계

게임의 전체 규칙을 이 문서에 복제하지 않는다.

예를 들어 전투 시스템이 복잡하더라도 아트 제작에 필요한 정보만 가져온다.

다만 특정 규칙이 아트에 직접 영향을 준다면 기록한다.

예:

> 상대의 정확한 능력치는 숨겨져 있지만 팀 구분은 즉시 가능해야 한다.

이런 정보는 시각 설계에 중요하므로 포함할 가치가 있다.

---

# 37. 권장 템플릿 구조

최종 `PROJECT_BRIEF.md`는 대략 다음과 같은 규모의 섹션 구조를 갖도록 설계한다.

정확한 제목과 순서는 읽기 좋게 조정할 수 있다.

```text id="yy9qk0"
# PROJECT BRIEF

## 1. 프로젝트 정보
## 2. 한 문장 설명
## 3. 핵심 게임 경험
## 4. 장르와 플레이 구조
## 5. 플랫폼과 엔진
## 6. 카메라와 화면
## 7. 세계와 배경
## 8. 주요 시각 대상
## 9. 현재 아트 상태
## 10. 필요한 아트 범위
## 11. 플레이 가독성 요구
## 12. 기존 자료와 레퍼런스
## 13. 개발 상태
## 14. 기술적 제약
## 15. 현재 우선순위
## 16. 아직 결정되지 않은 것
## 17. 관련 문서
```

섹션 수를 불필요하게 늘리지 않는다.

실제 사람이 빠르게 채울 수 있는 형태로 정리한다.

---

# 38. 각 항목에 작성 힌트를 제공한다

템플릿이므로 빈 제목만 나열하지 않는다.

각 항목에는 짧은 HTML comment 또는 간단한 안내문을 넣어 무엇을 작성해야 하는지 알 수 있게 한다.

예:

```text id="j8tggx"
## 핵심 게임 경험

<!--
플레이어가 대부분의 시간 동안 무엇을 하는지,
아트 제작에 영향을 주는 핵심 플레이 경험만 3~5줄로 적는다.
-->
```

단, 안내문이 실제 문서보다 길어지지 않도록 한다.

---

# 39. 예시 값은 최소화한다

템플릿에 특정 게임의 예시가 너무 많이 들어가면 새 프로젝트에서 그대로 남거나 잘못된 기본값으로 작용할 수 있다.

따라서:

* placeholder
* 짧은 작성 힌트

를 중심으로 만든다.

예시가 필요하면 한두 개 정도의 추상적인 예시만 사용한다.

---

# 40. 체크박스를 남발하지 않는다

게임 브리프는 체크리스트가 아니다.

필요한 곳에는 간단한 리스트를 사용할 수 있지만 모든 항목을 선택식으로 만들지 않는다.

게임마다 필요한 설명이 다르므로 자연어 기술이 가능해야 한다.

---

# 41. 문서의 핵심 철학

`PROJECT_BRIEF.md`는 Art Studio가 “멋진 그림을 만들어 달라”는 요청만 받고 작업하는 것을 방지한다.

먼저 다음을 이해하게 한다.

```text id="21ro7u"
무엇을 만드는 게임인가
        ↓
플레이어는 그것을 어떻게 보는가
        ↓
어떤 정보가 화면에서 중요해야 하는가
        ↓
어떤 아트가 필요한가
```

화풍의 상세 설계는 그 다음 단계다.

---

# 42. 이 문서에서 다루지 않을 것

다음 내용은 이 템플릿에 상세하게 넣지 않는다.

* 화풍의 세부 정의
* 팔레트 규칙
* 픽셀 밀도
* 아웃라인 규칙
* 조명 세부 방향
* 캐릭터 디자인 언어 상세
* reference 분석
* 생성 도구 선택
* 생성 프롬프트
* candidate 관리
* asset lifecycle
* 리뷰 기록
* 상세 asset 목록
* engine export 설정

각각 다른 문서의 역할이다.

---

# 43. 최종 템플릿의 품질 기준

완성된 `PROJECT_BRIEF.md`는 다음 조건을 만족해야 한다.

### 새 게임을 처음 보는 Claude가 읽었을 때

5분 이내에 게임의 기본적인 아트 맥락을 이해할 수 있어야 한다.

### 디렉터가 작성할 때

게임 기획서를 다시 쓰는 느낌이 들어서는 안 된다.

### 다른 게임에 복제할 때

특정 장르나 플랫폼의 흔적이 남아 있어서는 안 된다.

### `ART_DIRECTION.md`와 함께 읽을 때

하나는 **무엇을 만드는 게임인가**, 다른 하나는 **그 게임이 어떻게 보여야 하는가**를 담당해야 한다.

---

# 44. 작성 원칙

* 한국어로 작성한다.
* 실제로 복제해서 사용할 수 있는 Markdown 템플릿을 만든다.
* 현재 Art Studio의 특정 게임 정보를 넣지 않는다.
* 특정 장르를 기본값으로 하지 않는다.
* 특정 플랫폼을 기본값으로 하지 않는다.
* Unity를 기본 엔진으로 하지 않는다.
* 모든 항목을 필수로 만들지 않는다.
* 미정 상태를 허용한다.
* 지나치게 많은 질문을 만들지 않는다.
* 게임 기획서 전체를 요구하지 않는다.
* 아트 제작에 영향을 주는 게임 정보만 남긴다.
* `ART_DIRECTION.md`와 역할이 겹치지 않게 한다.
* 후속 `STYLE_SPEC`, `ASSET_MANIFEST`와 역할이 겹치지 않게 한다.
* Art Studio가 실제 게임 플레이 맥락을 이해하는 데 도움이 되는 항목을 우선한다.
* 문서가 길어지더라도 작성할 때는 간결하게 채울 수 있는 구조로 만든다.

완성 후:

1. `templates/PROJECT_BRIEF.md`를 생성한다.
2. 전체 템플릿을 출력한다.
3. 마지막에 이 템플릿에서 **필수적으로 이해해야 하는 핵심 정보**와 **의도적으로 ART_DIRECTION으로 넘긴 정보**를 각각 짧게 요약한다.
4. 기존 문서를 수정하지 않는다.
5. 다른 문서나 폴더를 생성하지 않는다.
6. 다음 단계로 진행하지 말고 멈춘다.
