목표: **`docs/mockups/` 4장의 플레이 화면에 실제로 도달한다.**

## 0. 한 장 요약

| | 결론 |
|---|---|
| **art-studio** | **쓴다.** 프로세스(후보 → 디렉터 선택 → 승인 → export)가 바로 필요한 것이다. 다만 실행 코드가 없어 손은 게임 저장소와 이 문서가 채운다 |
| **2d-assets** | **떡락섬에는 쓰지 않는다.** 내용(도트·벡터·Unity·구매 파츠)이 하나도 안 맞는다. 결함이 아니라 다른 게임을 위해 만들어진 것이다 |
| **가져올 것** | 2d-assets의 **구조 다섯 가지** — 카탈로그 / 결정적 생성 / 후보 대조 시트 / 검증 / export 분리. 코드가 아니라 설계를 가져온다 |
| **가장 큰 발견** | **배경은 지금 게임에 넣을 수 없다.** 세로 그림과 가로 무대가 양립하지 않는다 (§3에서 화면으로 확인) |
| **그래서 순서** | 세로 UI 셸(Phase 2.5) → 배경 → 초상화 → 캐릭터. **셸이 먼저다** |

## 1. 두 저장소를 읽고 실제로 확인한 것

문서의 주장이 아니라 파일과 실행 결과로 확인한 값이다.

### art-studio

| 항목 | 실측 |
|---|---|
| 문서 | `CLAUDE.md` + `docs/01~11` + `templates/` 6종 = **8,714줄** |
| 실행 코드 | **0줄.** `studio/tools/`·`studio/workflows/` 폴더 자체가 없다 |
| `projects/` | **비어 있음.** 등록된 게임 없음 |
| 엔진 입장 | 중립. `05_TOOL_ROLES` §12가 Godot을 명시하고 "엔진은 프로젝트가 선택한다"고 못 박음 |
| 커밋 | 4개 (문서 체계 확정까지) |

**성격: 규약은 완성됐고 손이 없다.** 이건 결함이 아니라 설계다 — `01_STUDIO_IDENTITY` §4가 "이미지 생성 프로젝트가 아니다", §5가 "게임 개발 저장소도 아니다"라고 스스로 규정한다.

### 2d-assets

| 항목 | 실측 |
|---|---|
| 테스트 | `tools/tests/test_pipeline.py` **167개 전부 통과** (56초) |
| 의존성 | Python 3.9+ / Pillow 뿐 |
| 소스 팩 | LPC(도트 64px) · CC0 모듈러 벡터 · LimeZu Modern Interiors(16px 타일) · HD Survivor |
| 생성물 | PNG 223장, 카탈로그 4팩, 규칙 4개 |
| 생성 방식 | **구매/CC0 파츠의 조합 + 팔레트 교체.** seed 결정적, `Math.random()` 금지 |
| Export | **Unity 전용** (Sprite Library / Sprite Resolver / ScriptableObject) |
| 라이선스 | 팩마다 frontmatter로 게이트. **구매 에셋을 이미지 생성 AI에 넣는 것을 금지** |

**성격: 손은 아주 좋은데 다른 공예다.**

산출물을 눈으로 확인했다 — LPC는 탑다운 RPG 도트 마을사람, CC0는 벡터 만화 캐릭터. 둘 다 떡락섬의 회화적 화풍과 무관하다.

## 2. 겹치는 것과 안 겹치는 것

| 축 | 2d-assets | 떡락섬 | |
|---|---|---|---|
| 화풍 | 도트 64px / 벡터 만화 | **회화적 일러스트** | ✗ |
| 시점 | 탑다운 RPG | 사이드뷰 어드벤처 | ✗ |
| 엔진 | Unity | **Godot** | ✗ |
| 생산 방식 | 구매 파츠 조합 | **AI 생성 (자체 앵커)** | ✗ |
| 라이선스 경로 | 구매 에셋 → AI 금지 | 자체 생성물 → 제약 없음 | ✗ |
| 푸는 문제 | **대량 variation** (마을사람 100명) | **고유 장면** (황소항은 하나뿐) | ✗ |

여섯 축이 전부 어긋난다. 특히 마지막이 결정적이다 — **떡락섬은 대량 variation이 필요 없는 게임이다.** 명명된 인물이 8명이고 장면이 6개다. 조합 폭발이 아니라 한 장 한 장이 고유하다.

> **결론: 2d-assets를 떡락섬의 에셋 팩토리로 쓰지 않는다.**
> 이건 2d-assets를 버린다는 뜻이 아니다. DICE DOMINION처럼 병과·용병·가문 색이
> 조합으로 늘어나는 게임에는 지금 그대로 유효하다.

## 3. 게임 화면에서 확인한 것 — 배경을 지금 넣을 수 없다

받은 배경 `01_bull_harbor.png`(1024×1536)를 **실제로 게임에 넣고 찍어 봤다.**
파일 하나 넣었을 뿐인데 코드 수정 없이 로드됐다 — 폴백 구조는 설계대로 작동한다.

문제는 그다음이다.

### 시도 1 — 그대로 넣기 (찌그러짐)

세로 1024×1536(0.667)을 가로 320×135(2.37)에 그리면 **세로가 가로보다 3.56배 더 압축된다.**
황소 동상도 전광판도 환전소도 알아볼 수 없는 어두운 덩어리가 된다.

### 시도 2 — 비율 맞춰 잘라 넣기 (내용 상실)

320:135 비율로 자르면 1024×432 — **원본 세로의 28%만 남는다.**
왜곡은 사라지지만 남는 것은 바닥 돌바닥뿐이고, 주문서에 적은 오브젝트 6개가 전부 잘려 나간다.
핫스폿 사각형은 빈 포장도로를 가리킨다.

### 그래서

> **세로 그림과 가로 무대는 양립하지 않는다.**
> 배경을 쓰려면 **월드 스테이지가 세로가 되어야 한다** — 기획서 §05가 규정한 Modern UI Shell이다.

이것이 이 전략의 순서를 결정한다. 배경을 아무리 잘 뽑아도 **셸이 없으면 게임에 들어가지 못한다.**

증거 이미지: `reviews/2026-08-17_background-integration/`

## 4. 적용할 프로세스 — art-studio 라이프사이클을 떡락섬에

원하는 것은 「에셋 생성 → 변주 → 선택지 제시 → 디렉터 최종 선택」이다.
art-studio `06_ASSET_LIFECYCLE`가 이미 그 구조를 갖고 있다. 새로 만들 필요가 없다.

```text
REFERENCE   목업 4장 · 게임 스크린샷 · 외부 참고
    │
CONCEPT     방향 탐색 (화풍이 이미 정해졌으므로 떡락섬에서는 대체로 건너뛴다)
    │
CANDIDATE   ★ 한 자산당 3~4장. 여기가 «변주»다
    │
APPROVED    ★ 디렉터가 눈으로 고른 한 장. 여기가 «최종 선택»이다
    │
EXPORT      게임 저장소 assets/ 로. 규격 변환은 여기서
    │
RUNTIME     게임 화면에서 확인 → 아니면 CANDIDATE 로 되돌아간다
```

### 지금 무엇이 잘못돼 있는가

떡락섬 저장소 `docs/art/received/` 에 후보 2장이 들어 있다.
**후보가 게임 저장소에 쌓이고 있다.** art-studio `06` §9가 구분하라는 바로 그 지점이다.

| | 지금 | 바뀔 곳 |
|---|---|---|
| 목업(REFERENCE) | 게임 `docs/mockups/` | 스튜디오 `references/` (게임 쪽은 사본) |
| 후보(CANDIDATE) | 게임 `docs/art/received/` | **스튜디오 `candidates/`** |
| 승인본(APPROVED) | 없음 | 스튜디오 `approved/` |
| 게임용(EXPORT) | 없음 | 게임 `assets/backgrounds/` |
| 주문서 | 게임 `docs/art/ORDER_*.md` | 스튜디오 `brief/` (장면 데이터는 게임에서 읽는다) |

**게임 저장소에는 승인된 것만 들어간다.** 후보 3~4장 × 자산 40개 = 160장이 게임 이력에 쌓이면
저장소가 못 쓰게 된다. 지금 2장일 때 옮기는 게 싸다.

## 5. 변주를 어떻게 가하는가 — 자산 종류별

「변주」의 뜻이 자산마다 다르다. 2d-assets는 **조합 폭발**로 변주하지만, 떡락섬은 그 방식이 안 맞는다.

| 자산 | 변주의 뜻 | 몇 장 | 무엇이 달라지는가 |
|---|---|---|---|
| **배경** | 같은 장면의 다른 해석 | 3~4 | 시간대 · 카메라 높이 · 밀도 · 오브젝트 배치 |
| **초상화** | 같은 인물의 표정 | 표정당 2~3 | 눈썹 · 시선 · 입. **얼굴 정체성은 고정** |
| **아이템 아이콘** | 같은 물건의 형태 | 2~3 | 각도 · 낡음 정도 |
| **캐릭터** | §6 참조 — 여기가 어렵다 | | |

배경·초상화·아이콘은 **한 번에 3~4장 받아 고르면 끝난다.** 이미 절차가 있고(`docs/art/ORDER_*.md`),
프롬프트 끝에 「서너 장 만들어 줘」만 붙이면 된다.

## 6. 캐릭터 — 진짜 어려운 문제

배경은 장당 1장이면 되지만 캐릭터는 다르다. 게임의 `Actor.gd`가 요구하는 것을 실측했다.

```
걷기 방향당 6프레임 × 방향 4 = 24
대기 3 · 말하기 2
────────────────────────────────
인물 하나당 약 29프레임
명명 인물 5명 → 145프레임
```

> **2026-08-17 정정** — 「8명 → 230프레임」으로 적었는데 틀렸다.
> `data/characters/` 를 세어 보니 **5명**이다 (han_gaemi · boss · sera · park · broker).
> 기획서 §01의 「NPC 18~24명」은 **전체판** 수치이고 프롤로그가 아니다.
> [`brief/ASSET_MANIFEST.md`](brief/ASSET_MANIFEST.md) 의 145프레임이 맞다.

**AI 이미지 생성기는 이걸 일관되게 못 만든다.** 프레임마다 얼굴·옷·비율이 흔들린다.
목업에는 이 문제가 보이지 않는다 — 목업의 인물은 서 있거나 앉아 있고, **걷지 않기 때문이다.**

### 네 갈래

| | 방법 | 장점 | 대가 |
|---|---|---|---|
| **A** | **컷아웃 퍼펫** — 파츠(몸통·머리·팔·다리)를 한 벌 생성하고 Godot에서 변형으로 애니메이션 | 프레임 일관성 문제가 **사라진다.** 애니메이션 추가가 싸다 | `Actor.gd` 교체. 파츠 경계 처리 |
| **B** | **프레임 생성** — 각 프레임을 AI로 | 코드 변경 없음 | 일관성이 최대 위험. 230장 관리 |
| **C** | **프레임 줄이기** — 걷기 2~3프레임, 방향 2~3 | 가장 싸다 | 회화체에서 2프레임 걷기는 조악해 보일 수 있다 |
| **D** | **미룬다** — 배경·초상화 먼저, 캐릭터는 코드 자리표시자 유지 | 결정을 미룰 수 있고, 배경만으로 인상이 크게 바뀐다 | 캐릭터가 계속 도드라진다 |

**권장: D로 시작해 A로 간다.**

이유는 화면 면적이다. 목업에서 캐릭터가 차지하는 넓이는 화면의 5~8%이고 배경은 50~78%다.
**배경과 초상화만 바꿔도 인상의 대부분이 바뀐다.** 캐릭터 방식은 배경이 세로 셸에 얹힌 화면을
보고 나서 정하는 편이 낫다 — 그때 캐릭터가 얼마나 크게 보이는지 알 수 있기 때문이다.

> A로 갈 때 2d-assets의 `ap2d/compose.py` 설계가 닿는다.
> 코드를 가져오지는 못한다 — 그 모듈은 `modular_composition` 계약(사전 정렬된 파츠)을
> 요구하고 아닌 것을 `UnsupportedModeError`로 막는다. 우리 파츠는 그 계약을 만족하지 않는다.
> 가져오는 것은 **«파츠 + 규칙 + seed → 결정적 합성»이라는 구조**다.

## 7. 2d-assets에서 가져올 것 / 가져오지 않을 것

### 가져온다 (설계)

| 2d-assets의 것 | 떡락섬에서의 모습 |
|---|---|
| **카탈로그** — 소스를 스캔해 JSON으로 목록화 | 후보를 스캔해 `candidates/index.json`. 어떤 자산에 후보가 몇 장 있고 무엇이 승인됐는지 한눈에 |
| **대조 시트** (`make_contact_sheet.py`) | **후보 3~4장을 한 장에 모아 디렉터에게 제시.** 지금 가장 아쉬운 것이 이것이다 |
| **결정적 생성** (seed) | 프롬프트·앵커·날짜를 기록해 **같은 조건을 재현**할 수 있게 |
| **검증** — 규격·누락만 | 이미 `tests/check_assets.py`가 이 형태다 (화풍은 판정하지 않음) |
| **provenance / attribution** | 어느 후보가 어떤 프롬프트·앵커에서 나왔는지 기록 |

**대조 시트가 즉시 값이 있다.** 후보를 여러 장 받기로 했는데 나란히 놓고 볼 도구가 없다.

### 가져오지 않는다

- 조합 생성기 (`generate.py`) — 조합할 파츠가 없다
- 팔레트 교체 (`palette.py`) — 제한 팔레트를 버렸다
- Unity export — 엔진이 다르다
- 구매 에셋 자체 — 화풍이 다르고, 라이선스상 AI 앵커로 쓸 수도 없다

### 절대 섞지 않는 것

> **구매 에셋을 떡락섬 앵커로 쓰지 않고, 떡락섬 생성물을 2d-assets 파이프라인에 넣지 않는다.**
> 전자는 라이선스 위반이고(대부분 AI 입력 금지), 후자는 화풍 오염이다.
> art-studio `CLAUDE.md` §6 「스타일은 자동으로 전염시키지 않는다」가 같은 말을 한다.

## 8. 단계별 계획과 각 단계의 판정

각 단계에 **무엇을 어떻게 확인하는지**를 붙였다. 「좋아 보이면 통과」는 없다.

### Phase 0 — 자리 정리 (반나절, 결정 불필요)

- art-studio에 떡락섬 등록 (이 문서와 같은 위치)
- 후보 2장을 `candidates/`로 옮긴다. 게임 저장소는 승인본만 받는다
- 후보 대조 시트 도구 하나 만든다

**판정** — 후보를 한 장에 모아 볼 수 있는가. 게임 저장소 `git status`에 후보 PNG가 안 뜨는가.

### Phase 1 — 세로 셸 (기획서 Phase 2.5)

**배경보다 먼저다.** §3에서 확인했듯 셸이 없으면 배경이 게임에 못 들어간다.
다섯 화면 중 **탐색 하나만** 먼저 해도 배경 검증은 가능하다.

**판정** — 받은 배경 1024×1536을 넣고 게임 화면을 찍었을 때 **왜곡 없이, 오브젝트가 다 보이고,
핫스폿이 그림 위 제자리에 오는가.** 지금은 셋 다 실패한다.

### Phase 2 — 배경 6장

장면당 3~4 후보 → 대조 시트 → 디렉터 선택 → `approved/` → export.
주문서는 이미 여섯 장 다 있다.

**판정** — 게임 화면에서 앵커와 나란히 놓고 **같은 세계로 보이는가.** 눈으로 본다.

### Phase 3 — 초상화

인물 5명 × 표정 2~3. 대화·배틀에서만 뜨므로 배경 다음으로 면적이 크다.

**판정** — 같은 인물의 표정들이 **한 사람으로 보이는가.** 나란히 놓고 본다.

### Phase 4 — 캐릭터

§6의 A/B/C/D 중 이때 결정한다. 배경이 올라간 화면을 보고 정한다.

## 10. 확인하지 못한 것

추측을 사실로 적지 않기 위해 남긴다.

- **Unity 설치 여부** — `run_unity_tests.py`가 있지만 실행해 보지 않았다. 떡락섬에는 무관
- **MCP 이미지 생성 연결** — 지금 세션에 이미지 생성 도구가 없다. 붙일 수 있는지 미확인
- **PixelLab · Retro Diffusion 성능** — 도트를 만들지 않기로 했으므로 떡락섬에는 무관
- **컷아웃 퍼펫이 이 화풍에서 실제로 자연스러운가** — 파츠 한 벌을 만들어 보기 전에는 모른다
- **목업의 배틀·수첩 화면 월드 높이** — 자동 검출이 실패했다. 눈으로 재야 한다

## 11. 이 전략의 한 문장

> 2d-assets는 **다른 게임의 공장**이고, art-studio는 **아직 손이 없는 규약**이다.
> 떡락섬에 필요한 것은 art-studio의 **프로세스**(후보 → 선택 → 승인 → export)와
> 2d-assets의 **구조 감각**(카탈로그 · 대조 시트 · 결정적 재현)이지,
> 어느 쪽의 코드나 에셋이 아니다.
>
> 그리고 그 전에 **세로 셸이 와야 한다.** 그림이 아무리 좋아도 들어갈 무대가 없다.
