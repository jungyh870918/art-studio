# `docs/05_TOOL_ROLES.md`를 작성하라

현재 저장소는 여러 게임 프로젝트의 그래픽 아트 제작을 담당하는 독립적인 **Game Art Studio**다.

이번 작업에서는 다음 파일 하나만 작성한다.

`docs/05_TOOL_ROLES.md`

먼저 아래 문서를 읽는다.

* `CLAUDE.md`
* `docs/01_STUDIO_IDENTITY.md`
* `docs/02_DIRECTOR_RELATIONSHIP.md`
* `docs/03_PROJECT_STRUCTURE.md`
* `docs/04_ART_DIRECTION_SYSTEM.md`

기존 문서의 철학과 역할 분리를 유지한다.

이번 문서는 특정 도구 사용법을 설명하는 매뉴얼이 아니다.

목적은 하나다.

> **Art Studio에서 사용될 수 있는 여러 도구의 역할과 경계를 정의하고, 작업 목적에 따라 어떤 종류의 도구를 선택해야 하는지에 대한 상위 원칙을 만든다.**

---

# 1. 이 문서의 역할

`05_TOOL_ROLES.md`는 Art Studio의 **도구 역할 지도**다.

이 문서를 읽으면 다음 질문에 답할 수 있어야 한다.

* Claude Code는 무엇을 잘해야 하는가?
* ChatGPT는 어디에 배치하는 것이 적절한가?
* 이미지 생성기는 어떤 역할을 맡는가?
* PixelLab 같은 전문 도구는 언제 유리한가?
* Unity/Godot/Roblox Studio는 제작 도구인가 검증 환경인가?
* Blender는 어떤 종류의 작업에서 유용한가?
* MCP와 API는 무엇을 위한 것인가?
* 여러 도구가 동시에 같은 자산에 관여할 수 있는가?
* 한 도구를 모든 작업의 기본값으로 삼아도 되는가?
* 새로운 도구가 등장하면 기존 구조를 어떻게 유지하면서 받아들일 것인가?

---

# 2. 가장 중요한 원칙

Art Studio는 **도구 중심으로 운영하지 않는다.**

항상 다음 순서를 우선한다.

```text id="vj2a1k"
작업 목적
    ↓
필요한 표현 방식
    ↓
필요한 제작 능력
    ↓
적합한 도구 선택
```

다음과 같이 사고하지 않는다.

```text id="ew9z6r"
PixelLab이 있으니 PixelLab으로 만든다.
FLUX API가 있으니 FLUX를 사용한다.
MCP가 연결되어 있으니 자동화한다.
```

도구는 목적을 위해 선택된다.

도구를 사용하기 위해 작업 방식을 바꾸지 않는다.

---

# 3. 도구는 직업이 아니라 능력이다

Art Studio 안에서 도구를 사람의 직무와 동일시하지 않는다.

예:

* ChatGPT = 컨셉 아티스트
* PixelLab = 픽셀 아티스트
* Blender = 3D 아티스트
* Unity = 조명 아티스트

처럼 고정적으로 규정하지 않는다.

실제 작업에서는 하나의 도구가 여러 역할을 할 수 있고, 하나의 역할을 여러 도구가 수행할 수도 있다.

따라서 도구는 다음 관점으로 본다.

> **이 도구가 어떤 작업을 잘 수행할 수 있는가?**

---

# 4. Claude Code의 기본 역할

Claude Code는 Art Studio의 핵심 **작업 오케스트레이션 및 기술 실행 환경**으로 본다.

Claude Code의 강점은 이미지 자체를 그리는 데 있지 않다.

주요 역할은 다음과 같다.

* 프로젝트 문서 읽기
* 현재 아트 방향 이해
* 레퍼런스와 파일 구조 파악
* 작업 요구사항 구조화
* 제작 계획 수립
* 생성기용 지시 조립
* 프롬프트 관리
* 외부 도구 호출 준비
* MCP/API 연결
* 파일 수집
* 파일 정리
* naming
* 이미지 처리 스크립트 실행
* 기술 검증
* batch 작업
* review sheet 생성
* export 준비
* 엔진 적용 보조
* 결과 기록
* 반복 가능한 작업의 자동화

Claude Code를 다음처럼 사용하지 않는다.

> “Claude가 모든 이미지를 직접 만든다.”

환경에 이미지 생성 기능이 없다면 외부 도구를 사용한다.

또한:

> “Claude가 모든 미적 결정을 대신한다.”

라고 정의하지 않는다.

Claude Code는 **제작 과정 전체를 연결하고 실행 가능한 형태로 만드는 중심 작업대**에 가깝다.

---

# 5. Claude의 비전 능력

Claude가 이미지를 볼 수 있는 환경이라면 다음과 같은 작업에 활용할 수 있다.

* 이미지 내용 설명
* 레퍼런스 특징 분석
* 후보 간 차이 정리
* 누락 요소 탐지
* 스타일 규칙과의 충돌 후보 찾기
* 디렉터의 자연어 피드백을 제작 수정 사항으로 변환
* 실제 게임 스크린샷에서 가독성 문제 탐색

하지만 비전 모델의 판단을 객관적 측정과 혼동하지 않는다.

예:

```text id="7zh0xu"
"이미지가 어두워 보인다"
```

는 분석 의견일 수 있다.

반면:

```text id="um3owc"
평균 luminance = X
```

는 코드로 측정할 수 있는 정보다.

필요하면 둘을 함께 사용한다.

---

# 6. ChatGPT의 역할

ChatGPT는 Art Studio 외부 또는 연동 가능한 **시각 탐색 및 이미지 제작 파트너**로 사용할 수 있다.

특히 다음과 같은 작업에 유용할 수 있다.

* 초기 아트 컨셉 탐색
* 같은 아이디어의 여러 시각 방향 생성
* 캐릭터 디자인 variation
* 몬스터 형태 탐색
* 환경 분위기 탐색
* 스타일 비교
* 레퍼런스 이미지 기반 수정
* 특정 이미지의 부분 수정
* 도트가 아닌 일러스트나 시각 자산 생성
* 디렉터와의 시각적 대화

ChatGPT 결과도 자동으로 공식 자산이 되는 것은 아니다.

Art Studio의 candidate 흐름을 따른다.

또한 ChatGPT만을 모든 이미지 제작의 기본값으로 만들지 않는다.

특정 작업에서는 다른 생성기가 더 적합할 수 있다.

---

# 7. 범용 이미지 생성 모델

다음과 같은 범용 이미지 생성 도구가 사용될 수 있다.

* FLUX
* 기타 diffusion 모델
* 상용 이미지 생성 서비스
* 로컬 생성 모델
* 미래에 추가되는 생성기

이들은 주로 다음 작업에 활용할 수 있다.

* 컨셉 생성
* 일러스트
* texture source
* environment source
* character exploration
* variation
* style exploration
* 배경 및 소품 생성

범용 이미지 생성기는 높은 표현 범위를 가질 수 있지만 다음을 자동으로 보장한다고 가정하지 않는다.

* 정확한 픽셀 격자
* 정확한 sprite dimensions
* tile seamlessness
* 애니메이션 frame consistency
* 게임 규격
* 동일 캐릭터의 완전한 일관성

필요한 경우 후처리와 검증을 추가한다.

---

# 8. PixelLab의 역할

PixelLab과 같은 전문 픽셀 아트 도구는 픽셀 기반 자산에서 유리할 수 있다.

예:

* pixel character
* directional sprite
* sprite animation
* tileset
* tile variation
* isometric asset
* 반복 가능한 픽셀 스타일 자산

특히 범용 이미지 생성기보다 다음 문제가 중요할 때 고려한다.

* pixel grid
* 방향 일관성
* tile continuity
* animation consistency
* low-resolution control

하지만 모든 픽셀 아트를 반드시 PixelLab으로 만들어야 한다고 규정하지 않는다.

프로젝트 요구와 실제 결과를 보고 선택한다.

---

# 9. Retro Diffusion과 유사한 도트 전문 생성기의 역할

도트 스타일을 직접 생성하는 전문 도구는 다음 작업에 유용할 수 있다.

* 저해상도 sprite
* icon
* prop
* miniature
* portrait
* pixel-style environment object
* 제한 팔레트 작업

범용 생성 이미지를 나중에 단순 downscale하는 방식보다 처음부터 픽셀 구조가 필요한 작업에서 유리할 수 있다.

하지만 결과 품질, API 지원, 현재 프로젝트 요구에 따라 선택한다.

특정 제품명을 영구적인 필수 의존성으로 만들지 않는다.

---

# 10. Blender의 역할

Blender는 3D 게임에서만 사용하는 도구로 제한하지 않는다.

다음과 같은 용도로 활용할 수 있다.

* 3D game asset 제작
* blockout
* 캐릭터 또는 오브젝트의 형태 검토
* 카메라와 perspective 기준 제작
* lighting reference
* 2D sprite용 3D render source
* 아이소메트릭 에셋 제작
* normal / depth / mask source 생성
* 여러 방향의 일관된 렌더
* 배경 제작 보조

예를 들어:

```text id="n1vw8c"
3D blockout
→ render
→ paint / pixel conversion
→ 2D game asset
```

같은 혼합 제작 방식도 가능하다.

---

# 11. Unity의 역할

Unity는 단순히 최종 게임을 실행하는 엔진으로만 보지 않는다.

Art Studio에서는 경우에 따라 중요한 **아트 검증 환경**이 된다.

활용 예:

* 실제 표시 크기 확인
* 카메라 검증
* sprite import 결과 확인
* pixel perfect 여부
* lighting
* shader
* material
* post-processing
* VFX
* particle
* depth
* environment composition
* screenshot comparison

특히 최종 화면 스타일 중 상당 부분이 엔진 조명이나 후처리에서 만들어지는 프로젝트에서는 Unity 자체가 아트 제작 과정의 일부가 될 수 있다.

다만 Unity를 모든 프로젝트의 기본 엔진으로 강제하지 않는다.

---

# 12. Godot의 역할

Godot 역시 다음과 같은 역할을 할 수 있다.

* 2D/3D asset 테스트
* sprite rendering
* tilemap
* lighting
* shader
* particle
* animation
* 실제 게임 화면 검증

프로젝트가 Godot을 사용하거나, 빠른 2D 검증 환경으로 적합하다면 사용한다.

Unity와 Godot 사이에 스튜디오 차원의 절대적인 우열을 만들지 않는다.

엔진은 프로젝트 요구에 따라 선택한다.

---

# 13. Roblox Studio의 역할

Roblox 프로젝트에서는 Roblox Studio 자체가 중요한 아트 검증 환경이 된다.

확인할 수 있는 요소:

* 실제 캐릭터 scale
* world scale
* camera distance
* material
* lighting
* texture
* surface appearance
* UI asset readability
* 모바일 화면 가독성
* 플레이 중 시각적 밀도

Roblox 플랫폼 특성상 외부에서 예쁜 이미지를 만드는 것보다 **Roblox 안에서 어떻게 보이는가**가 더 중요할 수 있다.

따라서 필요한 경우 Roblox Studio에서 직접 검증한다.

---

# 14. 이미지 편집 도구의 역할

생성 결과를 그대로 사용하는 것을 기본값으로 삼지 않는다.

필요에 따라 이미지 편집 도구 또는 코드 기반 처리를 사용할 수 있다.

예:

* crop
* resize
* transparency
* background removal
* color adjustment
* palette reduction
* compositing
* mask
* edge cleanup
* sprite sheet assembly
* tile cleanup
* format conversion

생성과 편집은 별개의 단계일 수 있다.

“AI가 한 번에 완성된 파일을 만들어야 한다”는 전제를 두지 않는다.

---

# 15. 로컬 스크립트의 역할

Python, Node.js 또는 기타 스크립트는 반복 가능하고 측정 가능한 작업에 적극 활용할 수 있다.

예:

* 파일명 검사
* dimensions 검사
* image statistics
* palette extraction
* color count
* alpha check
* batch resize
* contact sheet
* sprite packing
* format conversion
* manifest generation
* export

스크립트는 미적 판단을 흉내 내기보다 **명확한 기술 작업을 안정적으로 수행하는 것**에 집중한다.

---

# 16. MCP의 역할

MCP는 아트 제작 도구 자체가 아니다.

MCP는 Claude Code와 외부 시스템 사이의 **연결 계층**이다.

예:

```text id="njdjwu"
Claude Code
    ↓
MCP
    ↓
image generator / editor / external service
```

MCP를 사용하는 이유는 주로 다음과 같다.

* 창 전환 감소
* 수동 복사/붙여넣기 감소
* 파일 전달 자동화
* 반복적인 호출 단순화
* Claude가 작업 흐름을 이어서 관리하도록 지원

MCP 연결 자체를 프로젝트 목표로 만들지 않는다.

연결이 작업을 실제로 단순하게 만들 때 사용한다.

---

# 17. API의 역할

API는 특히 반복량이 커질 때 유용하다.

예:

```text id="k4op3j"
1 asset × 4 candidates
```

정도는 대화형 도구로 충분할 수 있다.

반면:

```text id="6nhbx7"
80 assets × 4 candidates
```

처럼 반복량이 커지면 API 기반 batch generation이 더 적합할 수 있다.

API 사용의 주요 목적:

* 반복 호출
* deterministic parameter 관리
* seed 기록
* batch generation
* 결과 자동 수집
* metadata 관리

API를 사용한다고 해서 디렉터의 승인 과정까지 제거해야 하는 것은 아니다.

---

# 18. MCP와 API를 구분한다

둘은 경쟁 관계가 아니다.

개념적으로 다음과 같이 볼 수 있다.

```text id="2ov1jr"
탐색 / 대화형 반복
→ MCP가 편리할 수 있음

대량 / 반복 생산
→ API script가 편리할 수 있음
```

하지만 이것을 절대 규칙으로 만들지 않는다.

도구의 실제 기능과 현재 작업을 보고 결정한다.

---

# 19. 수작업도 정상적인 제작 방식이다

Art Studio는 AI 도구만 사용하는 프로젝트가 아니다.

필요하면 사람이 직접 수정하거나 제작하는 것도 정상적인 방식이다.

예:

* 픽셀 하나 단위 수정
* silhouette correction
* facial cleanup
* tile seam correction
* hand paint
* Blender manual modeling
* 직접 compositing

생성형 AI로 하기 어려운 작업을 억지로 자동화하지 않는다.

---

# 20. 구매 에셋과 외부 에셋

필요하다면 다음도 제작 자원으로 활용할 수 있다.

* Unity Asset Store
* Unreal Marketplace
* itch.io asset
* stock image
* texture library
* font
* commissioned artwork
* 외부 디자이너 결과물

Art Studio는 “모든 것을 직접 생성해야 한다”는 원칙을 갖지 않는다.

시간, 비용, 품질을 고려하여 적절한 공급원을 선택할 수 있다.

단 라이선스와 사용 조건은 확인해야 한다.

---

# 21. 하나의 자산에 여러 도구를 사용할 수 있다

실제 제작은 다음처럼 이루어질 수 있다.

```text id="b2gk2k"
ChatGPT
→ concept

Blender
→ shape blockout

FLUX
→ texture exploration

Claude Code
→ processing

PixelLab
→ pixel conversion / animation

Unity
→ lighting test
```

이런 혼합 작업을 실패한 파이프라인으로 보지 않는다.

오히려 자산의 요구에 적합하다면 정상적인 제작 방식이다.

---

# 22. 반대로 단순한 작업은 단순하게 끝낸다

모든 자산이 복잡한 multi-tool workflow를 필요로 하는 것은 아니다.

예:

```text id="13znwo"
작은 UI icon
→ 한 번 생성
→ 간단한 cleanup
→ 승인
```

이면 충분할 수 있다.

Art Studio는 작업을 전문적으로 만들기 위해 불필요하게 복잡하게 만들지 않는다.

---

# 23. 도구 선택 기준

도구를 선택할 때 다음 질문을 고려할 수 있다.

* 어떤 형태의 결과물이 필요한가?
* 해상도는 어느 정도인가?
* 스타일 일관성이 얼마나 중요한가?
* 여러 방향이나 animation이 필요한가?
* tile seamlessness가 필요한가?
* 동일 캐릭터 반복 생성이 필요한가?
* 정확한 layout이 필요한가?
* batch 생산이 필요한가?
* 수정 반복이 얼마나 자주 발생하는가?
* 엔진 효과가 결과에 얼마나 큰 영향을 주는가?
* 사람이 직접 수정하는 것이 더 빠른가?
* 비용은 어느 정도인가?
* 사용 가능한 API/MCP가 있는가?

이 질문들을 체크리스트처럼 매번 모두 사용할 필요는 없다.

작업 특성을 파악하기 위한 사고 프레임으로 사용한다.

---

# 24. 도구 선택은 결과로 검증한다

기능 설명만 보고 도구를 고정하지 않는다.

실제 프로젝트에서는 작은 테스트를 통해 확인할 수 있다.

예:

```text id="odcmll"
동일 asset brief
        ↓
tool A
tool B
        ↓
결과 비교
        ↓
프로젝트에 적합한 방식 선택
```

특히 새로운 생성 도구를 도입할 때 유용하다.

---

# 25. 도구의 강점과 한계를 기록할 수 있다

Art Studio가 여러 프로젝트를 수행하면서 특정 도구에 대한 경험이 쌓일 수 있다.

예:

```text id="u3u1dl"
PixelLab
- 타일 작업에 안정적
- 방향 sprite에 유리
- 특정 고밀도 스타일에서는 한계

Generator X
- concept exploration에 빠름
- exact layout은 약함
```

이런 정보는 공통 제작 지식으로 축적할 수 있다.

그러나 특정 시점의 평가를 영구적인 진리로 만들지 않는다.

도구는 업데이트될 수 있다.

---

# 26. 도구 상태는 변한다

AI와 게임 개발 도구는 빠르게 변화한다.

따라서:

* 특정 API가 없어질 수 있다.
* 새로운 MCP가 등장할 수 있다.
* 기존 도구의 생성 품질이 개선될 수 있다.
* 가격이 변경될 수 있다.
* 라이선스가 바뀔 수 있다.
* 새로운 모델이 더 좋은 결과를 만들 수 있다.

이 문서는 현재 도구 목록을 영구적인 기술 스택으로 고정하지 않는다.

새로운 도구가 들어와도 기존 철학은 유지되어야 한다.

---

# 27. 도구 이름보다 capability를 먼저 본다

가능하면 내부 사고에서는 다음과 같이 접근한다.

```text id="o8epqi"
필요 capability:
- seamless tile generation
- directional sprite
- image edit
- batch generation
- texture baking
```

그다음 현재 사용할 수 있는 도구를 찾는다.

이를 통해 특정 제품에 대한 과도한 종속을 줄인다.

---

# 28. 생성 도구의 출력은 원본이 아닐 수도 있다

이미지 생성 결과는 다음 제작 단계의 source가 될 수 있다.

예:

```text id="cykapj"
generated image
→ cleanup
→ palette conversion
→ manual correction
→ approved source
```

따라서 생성기의 raw output과 승인된 공식 source를 동일시하지 않는다.

---

# 29. 엔진은 결과 확인 장치다

다음과 같은 문제가 이미지 파일만으로는 보이지 않을 수 있다.

* 캐릭터가 너무 작음
* 배경과 섞임
* outline이 화면에서 너무 강함
* lighting 때문에 색이 무너짐
* VFX가 캐릭터를 가림
* 실제 tile 반복이 부자연스러움

따라서 필요한 경우 Unity, Godot, Roblox Studio 등의 실제 환경에서 확인한다.

특정 프로젝트에서는 엔진 검증이 제작의 핵심일 수 있다.

---

# 30. 도구를 평가할 때 완벽함을 기준으로 하지 않는다

어떤 도구가 단독으로 최종 결과를 완성하지 못한다고 해서 쓸모없는 것은 아니다.

예:

* 좋은 silhouette만 만들어도 유용할 수 있다.
* 좋은 색감 탐색만 해도 유용할 수 있다.
* 3D pose source만 만들어도 유용할 수 있다.
* rough concept만 빨리 만들어도 유용할 수 있다.

도구를 **전체 작업 중 어떤 구간을 잘 해결하는지**로 평가한다.

---

# 31. 역할 중복을 허용한다

다음과 같은 중복은 문제가 아니다.

```text id="k42sy4"
concept generation
→ ChatGPT 가능
→ FLUX 가능
→ 다른 생성기 가능
```

중복되는 능력이 있으면 프로젝트별로 결과와 편의성을 보고 선택한다.

도구 역할 문서를 조직도처럼 만들어 “이 업무는 무조건 이 도구”라고 고정하지 않는다.

---

# 32. 디렉터는 도구를 몰라도 된다

Art Studio의 목표 중 하나는 디렉터가 모든 생성기의 세부 사용법을 기억하지 않아도 되게 하는 것이다.

디렉터는 다음과 같이 요청할 수 있어야 한다.

```text id="5ld3gr"
이 캐릭터의 갑옷 방향을 세 가지로 보여줘.
```

Art Studio는 현재 프로젝트의 방향과 사용 가능한 도구를 고려하여 적절한 제작 방법을 선택한다.

디렉터가 항상:

```text id="a1acgw"
이걸 FLUX model X의 sampler Y로 만들어.
```

처럼 지시해야 하는 시스템을 목표로 하지 않는다.

물론 디렉터가 특정 도구 사용을 명시하면 그 요구를 따른다.

---

# 33. 도구 선택의 투명성

중요한 경우 Claude는 왜 특정 도구를 선택했는지 짧게 설명할 수 있어야 한다.

예:

```text id="xwyp63"
이 자산은 8방향 일관성과 낮은 픽셀 해상도가 중요하므로
범용 이미지 생성기보다 directional sprite 기능이 있는 도구를 우선한다.
```

장황한 기술 설명은 필요하지 않다.

디렉터가 선택 이유를 이해할 수 있는 정도면 충분하다.

---

# 34. 실패 시 도구를 바꿀 수 있다

같은 프롬프트를 무한히 반복하는 것만이 수정 방법은 아니다.

예:

```text id="nzn3tq"
현재 generator
        ↓
반복 실패
        ↓
prompt 수정?
tool 변경?
3D source 사용?
manual correction?
style simplification?
```

문제가 제작 방식에 있을 수 있음을 고려한다.

단, 자동화가 어렵다는 이유로 디자인 자체를 임의로 단순화하지 않는다.

---

# 35. 도구 체계를 계층적으로 이해한다

필요하다면 도구를 다음과 같은 성격으로 분류할 수 있다.

## Direction / Exploration

* ChatGPT
* 이미지 생성 모델
* 비전 모델

## Generation / Creation

* PixelLab
* Retro Diffusion
* FLUX
* 기타 생성기
* Blender
* 사람의 직접 제작

## Processing / Validation

* Claude Code
* Python
* Node.js
* 이미지 처리 도구

## Integration / Runtime Validation

* Unity
* Godot
* Roblox Studio

## Connection / Automation

* MCP
* API
* local script

이 분류는 이해를 돕기 위한 것이며 절대적인 배타적 역할이 아니다.

---

# 36. Art Studio와 도구를 동일시하지 않는다

다음 관계를 유지한다.

```text id="m8s3sq"
ART STUDIO
    │
    ├── Claude Code
    ├── ChatGPT
    ├── image generators
    ├── Blender
    ├── Unity / Godot / Roblox
    ├── scripts
    └── future tools
```

Art Studio는 이 도구들의 집합보다 상위 개념이다.

어떤 도구가 교체되어도 Art Studio의 정체성과 게임별 아트 방향은 유지되어야 한다.

---

# 37. 이 문서에서 다루지 않는 것

다음 내용은 후속 전문 문서의 역할이다.

* 실제 생성 workflow의 상세 순서
* 후보 생성 개수
* prompt template
* API request 구조
* MCP 설치법
* tool authentication
* 비용 관리 정책
* seed 정책
* batch generation 세부사항
* asset approval 절차
* 엔진별 import 설정
* 구체적인 validation rule
* 특정 도구의 상세 사용 매뉴얼
* 최신 제품별 성능 순위

이번 문서는 **역할과 선택 원칙**만 정의한다.

---

# 38. 문서 마지막의 핵심 원칙

마지막에는 다음 의미가 명확하게 드러나도록 정리한다.

> Art Studio는 특정 툴의 사용법을 모아둔 프로젝트가 아니다.
>
> 먼저 어떤 아트 문제가 있는지 판단하고, 그 문제에 필요한 제작 능력을 정의한 뒤, 현재 사용할 수 있는 도구 중 가장 적합한 것을 선택한다.
>
> Claude Code는 여러 제작 수단을 연결하고 정리하는 중심 작업대이지만 Art Studio 그 자체는 아니다.
>
> 생성 AI, Blender, 엔진, MCP, API, 스크립트와 수작업은 모두 필요에 따라 조합할 수 있는 수단이다.
>
> 도구는 교체될 수 있지만 게임의 아트 방향과 디렉터의 판단은 도구에 종속되지 않는다.

문장을 그대로 복사할 필요는 없지만 의미는 유지한다.

---

# 작성 원칙

* 한국어로 작성한다.
* 현재 존재하는 도구 목록을 영구적인 기술 스택으로 고정하지 않는다.
* 특정 생성기를 기본값으로 지정하지 않는다.
* Claude Code를 이미지 생성기처럼 설명하지 않는다.
* MCP를 생성 도구처럼 설명하지 않는다.
* API를 완전 자동화를 위한 장치로만 설명하지 않는다.
* Unity/Godot/Roblox를 단순 export destination으로 축소하지 않는다.
* 실제 게임 화면 검증의 역할을 포함한다.
* 수작업과 구매 에셋도 정상적인 제작 방법으로 인정한다.
* 도구 중심이 아니라 capability 중심으로 사고한다.
* 하나의 자산에 여러 도구를 조합할 수 있도록 한다.
* 단순한 작업을 불필요한 multi-tool workflow로 만들지 않는다.
* 도구가 바뀌어도 유지되는 상위 원칙을 중심으로 작성한다.
* 향후 실제 Generation Workflow와 세부 Tool Guide가 별도로 만들어질 수 있도록 범위를 남긴다.
* 기존 문서의 사람 중심 디렉팅 철학을 유지한다.

4. 기존 문서를 수정하지 않는다.
5. 다른 문서나 폴더를 생성하지 않는다.
6. 다음 단계로 진행하지 말고 멈춘다.
