## 1. 결정이 필요한 것

내가 정하면 안 되는 것들이다. 순서는 **막혔을 때 멈추는 것의 크기** 순.

### D1. 기준 캔버스 — 가장 먼저

모든 규격이 여기서 파생된다. 인물 크기 · 초상화 크기 · 아이콘 크기 · 검사기의 크기 검사.

- 후보: **1080×1920** (9:16 표준, 목업을 1.148배) / **941×1672** (목업 그대로) / 그 외
- **배경은 이 결정을 기다리지 않아도 된다** — 크게 받아 줄이면 되므로
- **인물·초상화·아이콘은 기다려야 한다** — 배경 대비 몇 픽셀인지가 여기서 나온다

> 막히면: 인물·초상화·아이콘 발주가 전부 멈춘다. 배경만 진행 가능.

### D2. 세로 전환의 범위

목업은 전부 세로다. 그런데 게임은 지금 가로(320×135)다.

- (a) **세로 전용** — 데스크톱도 세로 창. 기존 6장면 좌표를 다시 배치해야 한다
- (b) **세로 + 가로 병행** — 배경을 두 벌 그리거나, 세로 배경을 가로로 크롭
- (c) 세로 배경을 가로 무대에 맞춰 **다시 발주**

내 측정으로는 (c)가 목업과 어긋나고, (b)는 배경 장수가 배가 된다.
**하지만 이건 아트 방향 결정이므로 내가 고르지 않는다.**

> 막히면: **배경을 받아도 게임에 넣지 못한다.** 증거는 [`reviews/2026-08-17_background-integration/`](reviews/2026-08-17_background-integration/)

### D3. 캐릭터 제작 방식

인물 하나당 약 29프레임 × 5명 = **145프레임.** AI 생성으로는 프레임 일관성이 안 나온다.

`05_TOOL_ROLES` §10을 읽고 다섯 갈래가 됐다.

| | 방법 | 비고 |
|---|---|---|
| A | 컷아웃 퍼펫 (파츠 + 변형) | `Actor.gd` 교체 필요 |
| B | 프레임 생성 | 일관성이 최대 위험 |
| C | 프레임 축소 | `04` §17 — 프레임 수는 **화풍 결정**이라고 읽었다 |
| D | 미룸 (배경·초상화 먼저) | 내 권장 시작점 |
| **E** | **3D blockout → render → paint** | 문서가 「형태가 흔들리면 안 되는 작업」에 권하는 경로 |

> 막히면: 인물 5명이 색 블록으로 남는다. 배경만 바뀌면 **대비가 더 도드라진다.**

### D4. 프레임 수 — D3에 딸린 결정

`04` §17이 **「4프레임 걷기와 8프레임 걷기는 다른 화풍」**이라고 규정한다.
지금 코드는 걷기 6 · 대기 3 · 말하기 2인데, 이건 **폐기된 도트 규격에서 온 숫자**다.
회화적 화풍에서 몇 프레임이 맞는지는 아트 결정이다.

### D5. 화풍의 밀도가 화면마다 달라도 되는가 — **새로 발견**

수첩 화면(§3)의 인물 흉상은 **배경보다 훨씬 도트에 가깝다.**
같은 게임 안에서 배경은 회화적이고 수첩 안의 인물은 도트풍이다.

이게 의도인지, 목업 생성 과정의 흔들림인지 **내가 판단할 수 없다.**
의도라면 자산 종류마다 다른 발주 규격이 필요하고, 아니라면 통일해야 한다.

### D6. 후보 장수

지금 3~4장으로 잡았는데 **근거는 내가 정한 것뿐**이다. 자산 종류별로 다를 수 있다.

## 2. 받아야 할 자료

게임이 읽는 **정확한 경로와 규격**이다. 코드에서 확인했다.

### 2-1. 배경 — 6장

```
assets/backgrounds/<scene_id>.png
```

| scene_id | 장면 | 주문서 | 상태 |
|---|---|---|---|
| `bull_harbor_entrance` | 황소항 입구 | ORDER_01 | 후보 1장 |
| `subway_night` | 심야 지하철 | ORDER_05 | 후보 1장 |
| `office_meeting_room` | 회의실 | ORDER_02 | — |
| `office_corridor` | 복도 | ORDER_03 | — |
| `office_pantry` | 탕비실 | ORDER_04 | — |
| `studio_room` | 원룸 | ORDER_06 | — |

규격: 세로 **2:3 이상**, 폭 1024px 이상, 바닥 띠 세로 60~95%
— **그 띠의 위쪽 끝이 73%보다 내려가면 안 된다.** 아래가 UI에 덮이므로,
바닥을 맨 밑에만 두면 대화 중에 인물이 화면 밖으로 나간다 —
인물·UI 없음. (주문서 6장은 게임 저장소 `docs/art/ORDER_*.md` 에 이미 작성돼 있다)

### 2-2. 초상화 — 인물 5명 × 표정

```
assets/sprites/portraits/<character_id>.png     현재 규격 96×96
```

`han_gaemi` · `sera` · `boss` · `park` · `broker`

- **표정 수는 내가 대사 데이터에서 뽑아 드리겠다** (아직 안 했다 — 내 숙제)
- 96×96은 폐기된 도트 규격이다. **D1 이후 재산출 필요**
- **배경·셸과 독립적이라 지금 진행 가능한 유일한 항목**

### 2-3. 캐릭터 — D3 결정 후

```
assets/sprites/characters/<character_id>.png    스프라이트시트
```

시트 규약: `hframes × vframes`, **열 = 애니메이션 프레임, 행 = 방향**.
프레임 크기는 캐릭터 데이터의 `frame_size` 로 지정 (현재 32×48).

> A(컷아웃)나 E(3D) 로 가면 **이 규약 자체가 바뀐다.** 그때 코드를 고치는 건 내가 한다.

### 2-4. 아이템 아이콘 — 12개

```
assets/ui/items/<item_id>.png      현재 규격 16×16
```

`last_chance_flyer` `cash_envelope` `loss_receipt` `refund_coins` `sera_card` `id_card`
`phone` `stale_report` `decaf_pack` `strong_label` `decaf_cup` `disguised_cup`

16×16은 옛 규격. 세로 셸의 가방 시트에서 훨씬 크게 보인다 → **D1 이후 재산출**

### 2-5. UI 부품 — **목업 분석으로 새로 나온 것**

§3에서 확대해 본 결과다. **크롬은 코드가 그릴 수 있지만 아래는 그림이 필요하다.**

| 부품 | 쓰이는 곳 | 비고 |
|---|---|---|
| **행동 아이콘** 4~6종 | 행동 메뉴 | 말풍선(대화) · 돋보기(조사) · 가방(아이템) · 발(이동) 등. **단색 실루엣** |

### 2-6. 타이틀

```
assets/ui/title.png                현재 320×180 → D1 이후 재산출
```

### 2-7. 받지 않아도 되는 것

- **`assets/ui/command_panel.png`** — Classic 셸 전용. 세로 셸로 가면 불필요
- **효과음 · 배경음악** — 코드가 런타임 합성한다. 아트 범위 밖
- **UI 크롬 전체** (패널 · 버튼 · 카드 배경) — §3 참고, 코드로 그린다

## 3. 목업 UI를 실제로 재 봤다 — 새 사실

발주 범위를 정하려고 목업을 확대해 분석했다.

### 3-1. 크롬은 코드로 재현 가능하다

행동 메뉴 버튼을 확대해 보니 구성이 단순하다.

- **평면 채움** (민트 · 노랑 · 붉은색). 그라데이션 없음
- **둥근 모서리**, 1px 어두운 테두리, 윗변에 밝은 1~2px 하이라이트
- **도트 폰트 + 어두운 외곽선**
- 아이콘은 **단색 실루엣**

→ Godot 이 전부 그릴 수 있다. **UI를 그림으로 받을 필요가 없다.**
받아야 하는 건 **아이콘과 장식**뿐이다 (2-5).

### 3-2. 그런데 기획서 §06이 목업과 어긋난다

내가 쓴 «Pixel Modernism» 규정에 **「20px 라운드 금지 · 반경 0」**이라고 적혀 있다.
**목업은 둥근 모서리를 쓴다.** 그림이 기준이므로(§23) **문서가 틀렸다.**

> 고쳐도 되는지 확인 요청. 내 판단으로는 **«반경 0» → «작은 반경 허용, 20px 같은 큰 라운드는 금지»**
> 정도가 맞다. 다만 UI 규정은 아트 총괄의 영역이라 내가 바꾸지 않고 둔다.

### 3-3. 수첩 화면이 자산을 가장 많이 먹는다

내 `ASSET_MANIFEST` 가 수첩을 **과소평가**하고 있었다. 확대해 보니
프레임 장식 · 종이 텍스처 2종 · 링 · VS 형태 · NEW 리본 · **인물 흉상**이 들어간다.
게다가 **수첩 화면은 게임에 아직 존재하지도 않는다.**

→ 수첩은 **가장 나중**이 맞다. 다만 자산 견적에 넣어 둬야 한다.

## 5. 순서 제안

내 판단이며, 총괄이 다르게 보면 따른다.

```
① D1 기준 캔버스        → 규격이 파생된다
② D2 세로 전환 범위      → 배경을 넣을 수 있게 된다
   (동시에) 초상화 발주   → 셸과 독립적이라 기다릴 필요 없다
③ 배경 6장             → 화면의 50~78%가 바뀐다
④ D3·D4 캐릭터 방식     → 배경이 올라간 화면을 보고 정한다
⑤ UI 아이콘 · 장식      → 셸 구현과 함께
⑥ 수첩                 → 화면부터 만들어야 한다
```

**②의 초상화가 지금 유일하게 막히지 않은 항목이다.**
D1만 정해지면 오늘이라도 발주할 수 있다.

## 6. 한 줄

> 내가 못 하는 것은 **그림을 만드는 것**과 **아트 방향을 정하는 것** 둘이다.
> 나머지 — 조립 · 배치 · 검사 · 게임에 붙이기 · 화면으로 확인하기 — 는 내가 한다.
> 위 D1~D6이 정해지고 2-1~2-6이 오면, 목업에 도달하는 데 내 쪽 장애물은 없다.
