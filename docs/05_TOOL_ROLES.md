# 05. Tool Roles

이 문서는 Art Studio에서 사용될 수 있는 여러 도구의 **역할과 경계**를 정의한다.

앞의 네 문서가 "이 스튜디오는 무엇인가", "누가 무엇을 결정하는가", "파일 위에서 어떻게 분리하는가", "아트 방향을 어떤 언어로 이해하는가"를 다뤘다면, 이 문서는 그 방향을 **실제로 무엇으로 만들 것인가**를 다룬다.

이 문서는 특정 도구의 사용 매뉴얼이 아니다. 설치법, 인증, 프롬프트 작성법, API 요청 구조, 비용 정책은 여기서 다루지 않는다.
여기서 정하는 것은 **작업의 성격에 따라 어떤 종류의 도구를 고르는가**에 대한 상위 원칙뿐이다.

---

## 1. 이 문서가 답해야 하는 질문

- Claude Code는 무엇을 잘해야 하는가
- ChatGPT는 어디에 배치하는 것이 적절한가
- 이미지 생성기는 어떤 역할을 맡는가
- PixelLab 같은 전문 도구는 언제 유리한가
- Unity · Godot · Roblox Studio는 제작 도구인가 검증 환경인가
- Blender는 어떤 종류의 작업에서 유용한가
- MCP와 API는 각각 무엇을 위한 것인가
- 여러 도구가 하나의 자산에 동시에 관여해도 되는가
- 한 도구를 모든 작업의 기본값으로 삼아도 되는가
- 새 도구가 등장했을 때 기존 구조를 어떻게 유지하면서 받아들이는가

---

## 2. 도구가 아니라 목적에서 출발한다

Art Studio는 도구 중심으로 운영하지 않는다.
사고의 순서는 언제나 다음과 같다.

```text
작업 목적
    ↓
필요한 표현 방식
    ↓
필요한 제작 능력
    ↓
적합한 도구 선택
```

다음과 같은 사고는 순서가 뒤집힌 것이다.

```text
PixelLab이 있으니 PixelLab으로 만든다.
FLUX API가 연결되어 있으니 FLUX로 생성한다.
MCP가 붙어 있으니 자동화한다.
```

도구는 목적을 위해 선택된다. **도구를 쓰기 위해 작업 방식을 바꾸지 않는다.**

이것은 `02` 15장에서 경계한 "수단이 목적의 자리를 차지하는" 문제의 도구판이다.
"이 생성기가 가장 잘하므로 항상 이것을 쓴다"는 추론은 여기서도 그대로 잘못이다.

---

## 3. 도구는 직업이 아니라 능력이다

도구를 사람의 직무처럼 고정해서 부르지 않는다.

```text
ChatGPT = 컨셉 아티스트
PixelLab = 픽셀 아티스트
Blender  = 3D 아티스트
Unity    = 조명 아티스트
```

이런 도식은 편리해 보이지만 실제 제작과 맞지 않는다.
하나의 도구가 여러 역할을 할 수 있고, 하나의 역할을 여러 도구가 수행할 수도 있다.

그래서 도구를 볼 때 던지는 질문은 하나다.

> **이 도구가 어떤 종류의 작업을 잘 수행할 수 있는가?**

직함을 부여하는 순간 그 도구는 자기 영역의 작업을 자동으로 배정받게 되고, 그때부터 선택은 사라지고 관성만 남는다.

---

## 4. Claude Code의 역할

Claude Code는 Art Studio의 **작업 오케스트레이션 및 기술 실행 환경**이다.

Claude Code의 강점은 이미지를 직접 그리는 데 있지 않다.
여러 제작 수단과 자료와 규칙을 한자리에 모아 **실행 가능한 형태로 연결하는 것**에 있다.

주로 담당하는 작업:

> 프로젝트 문서 읽기 · 현재 아트 방향 이해 · 레퍼런스와 파일 구조 파악 · 작업 요구사항 구조화 · 제작 계획 수립 · 생성기용 지시 조립 · 프롬프트 관리 · 외부 도구 호출 준비 · MCP/API 연결 · 파일 수집과 정리 · naming · 이미지 처리 스크립트 실행 · 기술 검증 · batch 작업 · review sheet 생성 · export 준비 · 엔진 적용 보조 · 결과 기록 · 반복 작업의 자동화

반대로 Claude Code를 다음처럼 정의하지 않는다.

**"Claude가 모든 이미지를 직접 만든다."**
환경에 이미지 생성 기능이 없다면 그 사실을 숨기거나 흉내 내지 않는다. 실제로 그 작업을 수행할 수 있는 외부 도구를 연결한다.

**"Claude가 모든 미적 결정을 대신한다."**
`02`에서 정한 경계는 도구가 늘어나도 변하지 않는다. Claude Code가 제작 과정의 중심에 있다는 사실이 미적 결정권을 주지 않는다.

Claude Code는 그림을 그리는 손이라기보다 **여러 손이 같은 방향으로 움직이도록 정리하는 작업대**에 가깝다.

---

## 5. Claude의 비전 능력

Claude가 이미지를 볼 수 있는 환경이라면 다음에 활용할 수 있다.

- 이미지 내용 설명
- 레퍼런스 특징 분석
- 후보 간 차이 정리
- 누락 요소 탐지
- 스타일 규칙과 충돌하는 후보 찾기
- 디렉터의 자연어 피드백을 제작 수정 사항으로 변환
- 실제 게임 스크린샷에서 가독성 문제 탐색

다만 비전 모델의 판단을 객관적 측정과 혼동하지 않는다.

```text
"이미지가 어두워 보인다"        → 분석 의견
평균 luminance = 0.21           → 측정 가능한 사실
```

두 층은 서로를 대체하지 않는다. 필요하면 함께 쓴다.
측정은 사실을 확정하고, 비전 판단은 그 사실이 왜 문제인지 설명한다. 그리고 `04` 20장대로, 어느 쪽도 디렉터의 판단을 대신하지 않는다.

---

## 6. ChatGPT의 역할

ChatGPT는 Art Studio 외부에 있거나 연동 가능한 **시각 탐색 및 이미지 제작 파트너**로 쓸 수 있다.

유용할 수 있는 작업:

> 초기 아트 컨셉 탐색 · 같은 아이디어의 여러 시각 방향 생성 · 캐릭터 디자인 variation · 몬스터 형태 탐색 · 환경 분위기 탐색 · 스타일 비교 · 레퍼런스 이미지 기반 수정 · 특정 이미지의 부분 수정 · 도트가 아닌 일러스트 계열 자산 생성 · 디렉터와의 시각적 대화

특히 디렉터와 직접 주고받으며 방향을 좁혀가는 단계에서 강하다.

두 가지는 분명히 해둔다.

첫째, ChatGPT의 결과도 자동으로 공식 자산이 되지 않는다. `03` 12장의 candidate 흐름을 그대로 따른다.

둘째, ChatGPT를 모든 이미지 제작의 기본값으로 만들지 않는다. 픽셀 격자, 방향 일관성, 타일 연속성이 중요한 작업에서는 다른 도구가 더 적합할 수 있다.

---

## 7. 범용 이미지 생성 모델

FLUX, 기타 diffusion 모델, 상용 생성 서비스, 로컬 생성 모델, 그리고 앞으로 추가될 생성기들이 여기에 해당한다.

주로 활용할 수 있는 작업:

> 컨셉 생성 · 일러스트 · texture source · environment source · character exploration · variation · style exploration · 배경과 소품 생성

표현 범위가 넓다는 것이 이 계열의 강점이다.
다만 다음이 자동으로 보장된다고 가정하지 않는다.

- 정확한 픽셀 격자
- 정확한 sprite dimensions
- tile seamlessness
- 애니메이션 frame consistency
- 프로젝트의 기술 규격
- 동일 캐릭터의 완전한 일관성

이 항목들은 대체로 `04`에서 STYLE_SPEC으로 환원되는 값들이고, 생성 단계가 아니라 후처리와 검증 단계에서 확보해야 하는 경우가 많다.
**"생성기가 규격을 지켜줄 것"이라는 전제 위에 작업 계획을 세우지 않는다.**

---

## 8. PixelLab 같은 픽셀 전문 도구

픽셀 기반 자산에서는 전문 도구가 유리할 수 있다.

> pixel character · directional sprite · sprite animation · tileset · tile variation · isometric asset · 반복 가능한 픽셀 스타일 자산

특히 다음 문제가 결과 품질을 좌우하는 작업에서 먼저 고려한다.

```text
pixel grid
방향 일관성
tile continuity
animation consistency
low-resolution control
```

이 문제들은 "잘 그렸는가"와는 다른 종류의 문제다. 범용 생성기가 아무리 좋은 그림을 만들어도 격자가 어긋나면 픽셀 아트로 쓸 수 없다.

다만 모든 픽셀 아트를 반드시 이 계열 도구로 만들어야 한다고 규정하지 않는다.
프로젝트의 요구와 실제 결과를 보고 선택한다.

---

## 9. 도트 전문 생성기

Retro Diffusion 계열처럼 도트 스타일을 직접 생성하는 도구는 다음에 유용할 수 있다.

> 저해상도 sprite · icon · prop · miniature · portrait · pixel-style environment object · 제한 팔레트 작업

범용 이미지를 만든 뒤 단순 downscale하는 방식은 픽셀 구조가 결과의 핵심인 작업에서 자주 무너진다. 처음부터 픽셀을 전제로 생성하는 쪽이 나은 경우가 있다.

선택은 결과 품질, API 지원 여부, 현재 프로젝트의 요구를 보고 한다.
**특정 제품명을 영구적인 필수 의존성으로 만들지 않는다.**

---

## 10. Blender의 역할

Blender를 3D 게임 전용 도구로 제한하지 않는다.

> 3D game asset 제작 · blockout · 형태 검토 · 카메라와 perspective 기준 제작 · lighting reference · 2D sprite용 3D render source · 아이소메트릭 에셋 제작 · normal/depth/mask source 생성 · 여러 방향의 일관된 렌더 · 배경 제작 보조

2D 프로젝트에서도 유용한 경우가 많다. 특히 **여러 방향이나 여러 프레임에서 형태가 흔들리면 안 되는 작업**에서 3D 소스는 강력한 기준점이 된다.

```text
3D blockout
→ render
→ paint / pixel conversion
→ 2D game asset
```

`01` 8장에서 예시로 든 혼합 경로가 바로 이 형태다. 이런 제작 방식은 예외가 아니라 정상적인 선택지다.

---

## 11. Unity의 역할

Unity를 "최종 결과를 실행하는 곳"으로만 보지 않는다.
Art Studio에서 Unity는 경우에 따라 중요한 **아트 검증 환경**이며, 프로젝트에 따라서는 제작 과정의 일부다.

확인할 수 있는 것:

> 실제 표시 크기 · 카메라 검증 · sprite import 결과 · pixel perfect 여부 · lighting · shader · material · post-processing · VFX · particle · depth · environment composition · screenshot 비교

`04` 13장과 18장에서 정한 대로, 어떤 프로젝트에서는 최종 화면 인상의 상당 부분이 에셋이 아니라 엔진 조명과 후처리에서 만들어진다. 그런 프로젝트에서 Unity를 빼놓고 아트를 판단하는 것은 완성되지 않은 화면을 보고 판단하는 것과 같다.

다만 Unity를 모든 프로젝트의 기본 엔진으로 강제하지 않는다.

---

## 12. Godot의 역할

Godot도 같은 성격의 역할을 할 수 있다.

> 2D/3D asset 테스트 · sprite rendering · tilemap · lighting · shader · particle · animation · 실제 게임 화면 검증

프로젝트가 Godot을 쓰거나, 빠른 2D 검증 환경으로 적합하다면 사용한다.

Unity와 Godot 사이에 스튜디오 차원의 우열을 만들지 않는다.
**엔진은 프로젝트가 선택하는 것이지 스튜디오가 정해두는 것이 아니다.**

---

## 13. Roblox Studio의 역할

Roblox 프로젝트에서는 Roblox Studio 자체가 핵심적인 아트 검증 환경이 된다.

> 실제 캐릭터 scale · world scale · camera distance · material · lighting · texture · surface appearance · UI asset readability · 모바일 화면 가독성 · 플레이 중 시각적 밀도

이 플랫폼에서는 외부에서 잘 만든 이미지보다 **Roblox 안에서 어떻게 보이는가**가 결정적인 경우가 많다. 재질과 조명 처리, 실제 플레이 거리, 모바일 화면 비중이 결과를 크게 바꾸기 때문이다.

따라서 필요한 경우 파일 단계에서 판단을 끝내지 않고 Roblox Studio에서 직접 확인한다.

---

## 14. 이미지 편집 도구

생성 결과를 그대로 쓰는 것을 기본값으로 삼지 않는다.
필요에 따라 이미지 편집 도구나 코드 기반 처리를 사용한다.

> crop · resize · transparency · background removal · color adjustment · palette reduction · compositing · mask · edge cleanup · sprite sheet assembly · tile cleanup · format conversion

**생성과 편집은 별개의 단계일 수 있다.**
"AI가 한 번에 완성된 파일을 내놓아야 한다"는 전제를 두지 않는다. 그 전제를 두면 도구가 못 하는 마지막 5%를 위해 나머지 95%를 다시 생성하는 일이 반복된다.

---

## 15. 로컬 스크립트

Python, Node.js 등의 스크립트는 반복 가능하고 측정 가능한 작업에 적극적으로 쓴다.

> 파일명 검사 · dimensions 검사 · image statistics · palette extraction · color count · alpha check · batch resize · contact sheet · sprite packing · format conversion · manifest generation · export

이런 도구는 `03` 21장의 기준대로 `studio/tools/`에 쌓일 수 있다. 다만 특정 게임의 규격을 코드에 박아 넣지 않는다는 원칙도 함께 유지된다.

스크립트는 미적 판단을 흉내 내려 하지 않는다.
**명확한 기술 작업을 안정적으로, 같은 방식으로 반복하는 것**이 스크립트의 강점이다.

---

## 16. MCP의 역할

MCP는 아트 제작 도구가 아니다. Claude Code와 외부 시스템 사이의 **연결 계층**이다.

```text
Claude Code
    ↓
MCP
    ↓
image generator / editor / external service
```

MCP를 쓰는 이유는 대체로 이렇다.

- 창 전환 감소
- 수동 복사·붙여넣기 감소
- 파일 전달 자동화
- 반복적인 호출 단순화
- Claude가 작업 흐름을 끊지 않고 이어서 관리

MCP가 붙었다고 해서 새로운 표현력이 생기는 것은 아니다. 생기는 것은 **연결의 편의**다.

그래서 MCP 연결 자체를 프로젝트 목표로 만들지 않는다.
연결이 실제로 작업을 단순하게 만들 때 사용한다.

---

## 17. API의 역할

API는 반복량이 커질 때 유용하다.

```text
1 asset × 4 candidates      → 대화형 도구로 충분할 수 있다
80 assets × 4 candidates    → API 기반 batch가 적합할 수 있다
```

주요 목적:

> 반복 호출 · deterministic parameter 관리 · seed 기록 · batch generation · 결과 자동 수집 · metadata 관리

여기서 중요한 것은 batch generation만이 아니라 **재현 가능성**이다. 어떤 파라미터와 seed로 만들어졌는지 남아 있으면, 마음에 든 결과를 다시 만들 수 있고 변형도 통제할 수 있다.

다만 API를 완전 자동화 장치로 이해하지 않는다.
생성량이 늘어난다고 해서 디렉터의 판단 단계가 사라지는 것이 아니다. 오히려 후보가 많아질수록 `02` 16장의 "비교 가능한 형태로 제시하기"가 더 중요해진다.

---

## 18. MCP와 API는 경쟁 관계가 아니다

둘은 성격이 다르다.

```text
탐색 / 대화형 반복      →  MCP가 편할 수 있음
대량 / 반복 생산        →  API script가 편할 수 있음
```

이것을 절대 규칙으로 만들지 않는다. 실제 도구의 기능과 현재 작업을 보고 결정한다.
같은 프로젝트에서 탐색 단계는 MCP로, 확정된 규격의 대량 생산은 API로 처리하는 조합도 자연스럽다.

---

## 19. 수작업도 정상적인 제작 방식이다

Art Studio는 AI 도구만 사용하는 프로젝트가 아니다. 사람이 직접 손대는 것도 정상적인 제작 방식이다.

> 픽셀 단위 수정 · silhouette correction · facial cleanup · tile seam correction · hand paint · Blender manual modeling · 직접 compositing

특히 마지막 마감 구간에서는 사람이 5분 만에 끝낼 일을 자동화하려다 훨씬 오래 걸리는 경우가 흔하다.

**생성형 AI로 하기 어려운 작업을 억지로 자동화하지 않는다.**
`CLAUDE.md` 4장의 원칙대로, 자동화 대상은 반복적이고 기계적인 부분이지 작업 전체가 아니다.

---

## 20. 구매 에셋과 외부 에셋

필요하다면 다음도 제작 자원으로 쓸 수 있다.

> Unity Asset Store · Unreal Marketplace · itch.io asset · stock image · texture library · font · commissioned artwork · 외부 디자이너 결과물

Art Studio는 "모든 것을 직접 생성해야 한다"는 원칙을 갖지 않는다.
시간, 비용, 품질을 고려해 적절한 공급원을 선택할 수 있다.

단 **라이선스와 사용 조건은 반드시 확인한다.** 이것은 미적 판단이 아니라 기술적·법적 확인 사항이며, 확인 결과는 사실로 보고한다.

---

## 21. 하나의 자산에 여러 도구를 쓸 수 있다

실제 제작은 이런 형태가 될 수 있다.

```text
ChatGPT      → concept
Blender      → shape blockout
FLUX         → texture exploration
Claude Code  → processing
PixelLab     → pixel conversion / animation
Unity        → lighting test
```

이런 혼합 경로를 실패한 파이프라인으로 보지 않는다.
자산의 요구에 맞는다면 이것이 정상적인 제작 방식이다.

`03` 23장에서 정한 대로 저장소 구조의 중심은 게임과 자산이지 도구가 아니다.
같은 캐릭터가 여러 도구를 거쳐도 그 자산의 정체성은 하나이며, 어떤 도구를 거쳤는지는 기록으로 남긴다.

---

## 22. 단순한 작업은 단순하게 끝낸다

모든 자산이 복잡한 multi-tool workflow를 필요로 하지 않는다.

```text
작은 UI icon
→ 한 번 생성
→ 간단한 cleanup
→ 승인
```

이 정도로 충분한 작업이 많다.

**작업을 전문적으로 보이게 만들기 위해 불필요하게 복잡하게 만들지 않는다.**
도구 단계가 늘어날수록 재현과 수정 비용도 함께 늘어난다. 21장과 22장은 모순이 아니라 같은 기준의 양쪽이다. 자산의 요구가 경로의 길이를 정한다.

---

## 23. 도구 선택 기준

도구를 고를 때 다음 질문들을 고려할 수 있다.

- 어떤 형태의 결과물이 필요한가
- 해상도는 어느 정도인가
- 스타일 일관성이 얼마나 중요한가
- 여러 방향이나 animation이 필요한가
- tile seamlessness가 필요한가
- 동일 캐릭터의 반복 생성이 필요한가
- 정확한 layout이 필요한가
- batch 생산이 필요한가
- 수정 반복이 얼마나 자주 발생하는가
- 엔진 효과가 최종 결과에 얼마나 큰 영향을 주는가
- 사람이 직접 수정하는 편이 더 빠른가
- 비용은 어느 정도인가
- 지금 사용할 수 있는 API나 MCP가 있는가

이것을 매번 전부 확인하는 체크리스트로 쓰지 않는다.
`04` 4장의 축 목록과 마찬가지로, **작업의 성격을 파악하기 위한 사고 프레임**이다.

---

## 24. 도구 선택은 결과로 검증한다

기능 설명만 보고 도구를 고정하지 않는다.
실제 프로젝트에서는 작은 테스트로 확인할 수 있다.

```text
동일한 asset brief
        ↓
tool A          tool B
        ↓
결과 비교
        ↓
이 프로젝트에 적합한 방식 선택
```

새 생성 도구를 도입할 때 특히 유용하다.
이때도 비교 조건은 `02` 16장의 원칙을 따른다. 조건이 다른 두 결과를 놓고 도구를 판단하면 도구가 아니라 조건을 비교하게 된다.

---

## 25. 도구의 강점과 한계는 기록할 수 있다

여러 프로젝트를 거치면 특정 도구에 대한 경험이 쌓인다.

```text
PixelLab
- 타일 작업에 안정적
- 방향 sprite에 유리
- 특정 고밀도 스타일에서는 한계

Generator X
- concept exploration이 빠름
- exact layout은 약함
```

이런 정보는 `01` 9장에서 말한 축적 대상, 즉 스타일이 아니라 **제작 능력에 대한 지식**이다. 프로젝트 사이를 옮겨 다녀도 오염을 일으키지 않는다.

다만 특정 시점의 평가를 영구적인 진리로 만들지 않는다. 도구는 업데이트된다.

---

## 26. 도구 상태는 변한다

AI와 게임 개발 도구는 빠르게 바뀐다.

- 특정 API가 없어질 수 있다
- 새로운 MCP가 등장할 수 있다
- 기존 도구의 생성 품질이 크게 개선될 수 있다
- 가격이 바뀔 수 있다
- 라이선스 조건이 바뀔 수 있다
- 새 모델이 더 좋은 결과를 만들 수 있다

이 문서는 현재의 도구 목록을 영구적인 기술 스택으로 고정하지 않는다.
여기 적힌 이름들은 **현재 시점의 예시**이며, 목록이 바뀌어도 2장부터 3장까지의 원칙은 그대로 유지되어야 한다.

새 도구가 들어올 때 물어야 할 것은 "무엇을 대체하는가"가 아니라 **"어떤 capability를 새로 제공하는가"**다.

---

## 27. 도구 이름보다 capability를 먼저 본다

내부 사고에서는 가능하면 이렇게 접근한다.

```text
필요한 capability:
- seamless tile generation
- directional sprite
- image edit
- batch generation
- texture baking
```

그다음 현재 사용할 수 있는 도구 중에서 그 능력을 가진 것을 찾는다.

이 순서를 유지하면 두 가지가 확보된다.
특정 제품에 대한 과도한 종속이 줄고, 도구가 교체되어도 작업 정의가 그대로 살아남는다.

---

## 28. 생성 결과는 원본이 아닐 수 있다

이미지 생성 결과는 최종물이기보다 **다음 단계의 source**인 경우가 많다.

```text
generated image
→ cleanup
→ palette conversion
→ manual correction
→ approved source
```

`03` 12장과 16장의 원칙이 그대로 적용된다.
생성기의 raw output과 승인된 공식 source를 동일시하지 않는다. 생성되었다는 사실은 만들어졌다는 뜻이지 채택되었다는 뜻이 아니다.

---

## 29. 엔진은 결과 확인 장치다

다음 문제들은 이미지 파일만 봐서는 드러나지 않는다.

- 캐릭터가 화면에서 너무 작다
- 배경과 섞여 구분되지 않는다
- outline이 실제 화면에서 과하게 강하다
- 조명 때문에 색이 무너진다
- VFX가 캐릭터를 가린다
- 타일 반복이 부자연스럽다

`04` 30장에서 정한 대로 최종 기준은 개별 파일이 아니라 실제 게임 화면이다.
따라서 필요한 경우 Unity, Godot, Roblox Studio 등 실제 환경에서 확인한다. 프로젝트에 따라서는 이 검증이 제작의 핵심 단계다.

---

## 30. 완벽함을 도구 평가의 기준으로 삼지 않는다

어떤 도구가 혼자서 최종 결과를 완성하지 못한다고 해서 쓸모없는 것은 아니다.

- 좋은 실루엣만 만들어줘도 유용하다
- 색감 탐색만 빠르게 해줘도 유용하다
- 3D pose source만 제공해도 유용하다
- rough concept를 빠르게 뽑아줘도 유용하다

도구는 **전체 작업 중 어느 구간을 잘 해결하는가**로 평가한다.
"한 번에 완성본을 내놓는가"를 기준으로 삼으면 실제로 쓸모 있는 도구 대부분이 탈락한다.

---

## 31. 역할 중복을 허용한다

다음과 같은 중복은 문제가 아니다.

```text
concept generation
→ ChatGPT 가능
→ FLUX 가능
→ 다른 생성기 가능
```

중복되는 능력이 있으면 프로젝트별로 결과와 편의성을 보고 고른다.

이 문서를 조직도처럼 만들어 "이 업무는 무조건 이 도구"로 고정하지 않는다.
고정하는 순간 24장의 비교도, 26장의 교체도 불가능해진다.

---

## 32. 디렉터는 도구를 몰라도 된다

`01` 12장이 지향하는 상태 — 디렉터가 기술적 잡무 때문에 아트 판단의 흐름을 잃지 않는 것 — 는 도구 영역에도 적용된다.

디렉터는 이렇게 요청할 수 있어야 한다.

```text
이 캐릭터의 갑옷 방향을 세 가지로 보여줘.
```

Art Studio는 현재 프로젝트의 아트 방향과 사용 가능한 도구를 고려해 적절한 제작 방법을 고른다.

디렉터가 항상 이렇게 지시해야 하는 시스템을 목표로 하지 않는다.

```text
이걸 FLUX model X의 sampler Y로 만들어.
```

물론 디렉터가 특정 도구 사용을 명시하면 그 요구를 따른다. 이것은 디렉터의 선택지를 줄이자는 말이 아니라, **도구를 몰라도 디렉팅이 가능한 상태**를 기본으로 두자는 말이다.

---

## 33. 도구 선택의 투명성

중요한 경우 Claude는 왜 그 도구를 골랐는지 짧게 설명할 수 있어야 한다.

```text
이 자산은 8방향 일관성과 낮은 픽셀 해상도가 중요하므로
범용 이미지 생성기보다 directional sprite 기능이 있는 도구를 우선했습니다.
```

장황한 기술 설명은 필요 없다. 디렉터가 선택의 이유를 이해하고, 필요하면 다른 방향을 요구할 수 있을 정도면 충분하다.

`02` 10장의 원칙과 같다. 자율적으로 진행하는 것과 조용히 진행하는 것은 다르다.

---

## 34. 실패했을 때 도구를 바꿀 수 있다

같은 프롬프트를 무한히 반복하는 것만이 수정 방법은 아니다.

```text
현재 generator
        ↓
반복 실패
        ↓
prompt 수정?
tool 변경?
3D source 사용?
manual correction?
```

문제가 지시에 있는 것이 아니라 **제작 방식 자체에 있을 수 있다**는 가능성을 항상 열어둔다.
어떤 표현이 특정 도구에서 잘 나오지 않는다면, `04` 31장대로 그것은 도구 선택의 문제이지 방향의 결함이 아니다.

단 하나의 예외 없는 금지가 있다.
**자동화가 어렵다는 이유로 디자인 자체를 임의로 단순화하지 않는다.** 그것은 `02` 15장이 명시한 잘못된 추론이다.

---

## 35. 도구 체계를 성격별로 이해한다

필요하면 도구를 이런 성격으로 묶어 볼 수 있다.

**Direction / Exploration** — ChatGPT · 이미지 생성 모델 · 비전 모델

**Generation / Creation** — PixelLab · Retro Diffusion · FLUX · 기타 생성기 · Blender · 사람의 직접 제작

**Processing / Validation** — Claude Code · Python · Node.js · 이미지 처리 도구

**Integration / Runtime Validation** — Unity · Godot · Roblox Studio

**Connection / Automation** — MCP · API · local script

이 분류는 이해를 돕기 위한 것이며 배타적인 역할 배정이 아니다.
Blender는 검증에도 쓰이고, Unity는 제작에도 쓰이고, 이미지 생성 모델은 탐색과 생성 양쪽에 걸쳐 있다. 3장의 원칙이 여기서도 유지된다.

---

## 36. Art Studio와 도구를 동일시하지 않는다

```text
ART STUDIO
    │
    ├── Claude Code
    ├── ChatGPT
    ├── image generators
    ├── Blender
    ├── Unity / Godot / Roblox
    ├── scripts
    └── future tools
```

`01` 11장에서 정한 관계가 이 문서 전체의 전제다.

> Art Studio ≠ Claude Code
> Art Studio ≠ AI 이미지 생성

어떤 도구가 사라지거나 교체되어도 Art Studio의 정체성과 각 게임의 아트 방향은 그대로 유지되어야 한다.
도구 목록이 바뀔 때 프로젝트 문서를 다시 써야 한다면, 그것은 방향이 도구에 종속되어 있었다는 뜻이다.

---

## 37. 이 문서가 다루지 않는 것

다음은 각각의 후속 문서에서 정의한다.

- 실제 생성 workflow의 상세 순서
- 후보 생성 개수
- prompt template
- API request 구조
- MCP 설치와 tool authentication
- 비용 관리 정책
- seed 정책
- batch generation 세부사항
- asset approval 절차
- 엔진별 import 설정
- 구체적인 validation rule
- 특정 도구의 상세 사용 매뉴얼
- 최신 제품별 성능 순위

이 문서는 **역할과 선택 원칙**만 정의한다.

---

## 38. 핵심

> Art Studio는 특정 툴의 사용법을 모아둔 프로젝트가 아니다.
>
> 먼저 어떤 아트 문제가 있는지 판단하고, 그 문제에 필요한 제작 능력을 정의한 뒤, 지금 사용할 수 있는 도구 중 가장 적합한 것을 고른다.
>
> Claude Code는 여러 제작 수단을 연결하고 정리하는 중심 작업대이지만 Art Studio 그 자체는 아니다.
>
> 생성 AI, Blender, 엔진, MCP, API, 스크립트, 수작업, 외부 에셋은 모두 필요에 따라 조합할 수 있는 수단이다.
>
> 도구는 교체될 수 있다. 그러나 게임의 아트 방향과 디렉터의 판단은 도구에 종속되지 않는다.

---

## 부록. 도구 요약

현재 시점의 예시이며, 고정된 기술 스택이 아니다.
