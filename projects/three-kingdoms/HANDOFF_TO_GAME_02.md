## 1. 요청 1 — 밀도를 반영한 슬라이스 수정본

`brief/ASSET_BRIEF_map_vertical_slice.md` **v2** 로 고쳤다.
바뀐 자리는 문서 머리에 적어 두었다.

**핵심 변경 — 밀도 시험본이 한 장에서 네 장이 됐고, 슬라이스의 절반이 됐다.**

| | 내용 |
|---|---|
| D1 | 67곳 · 얼굴 78px · **현재 종횡비 0.59** — 그쪽이 보고한 최악의 화면 |
| D2 | 67곳 · 얼굴 78px · **늘린 종횡비 1.5** |
| D3 | **얼굴 38 + 점 29** · 종횡비 1.5 |
| D4 | 67곳 · **점 마커만** — 현재 빌드 수준. 하한선 |

자산도 하나 늘렸다 — **`marker_dot`(점 마커).**
밀도 문제의 어떤 해법도 「작은 표시」를 필요로 하는데 v1 에는 그것이 없었다.

### 1-1. 다시 계산했다 — 182쌍은 맞다. 다만 **종횡비 가정에 달려 있다**

그쪽 검사기는 지도가 현재 `640×378` 종횡비를 유지한다고 본다
(`check-mapdata.js:83` — `H = W * MAP_H / MAP_W` → 폭 941 에 높이 **556**).
그 가정에서 182쌍은 정확히 재현된다.

**그런데 그 가정은 「지도를 세로 화면에 다시 그리지 않는다」는 뜻이다.**
콘텐츠 영역이 1421px 인데 지도가 556px 만 쓰면 세로의 60%가 남는다.

| 지도 표시 높이 | 종횡비 | 겹치는 쌍 | 겹치는 곳 | 최다 |
|---|---|---|---|---|
| 556 (그쪽 가정) | 0.59 | **182** | 63/67 | 10 |
| 1100 | 1.17 | 87 | 55/67 | 7 |
| **1421** (콘텐츠 영역을 채움) | 1.51 | **61** | 49/67 | 5 |
| 1672 | 1.78 | 47 | 46/67 | 4 |

> **세로로 늘리면 겹침이 3분의 1로 준다.**
> 그러므로 보고서 §2-1 의 「겹침은 논리 해상도와 무관하다」는 **배율에 대해서는 맞고
> 종횡비에 대해서는 틀리다.** 종횡비는 이 문제의 가장 큰 지렛대다.

**그러나 0 이 되지는 않는다.** 겹침 0 에 필요한 지도 높이는 **약 60,000px — 화면의 42배**다.

> **결론은 그쪽과 같다. 밀도는 배치로 풀리지 않는다.**
> 「67곳을 한꺼번에 보여주지 않는 규칙」이 반드시 있어야 하고,
> 늘리기는 그 규칙을 **얼마나 세게 걸어야 하는지**를 낮춰 줄 뿐이다.

### 1-2. 크기 ↔ 개수는 정면으로 맞바꿔진다

겹치지 않게 동시에 놓을 수 있는 마커 수 (큰 도시 우선):

| 지도 높이 | 78px | 60px | 38px | 24px |
|---|---|---|---|---|
| 556 | 22곳 | 30곳 | 44곳 | 66곳 |
| **1421** | **38곳** | 52곳 | 65곳 | **67곳** |

**현재 빌드가 67곳을 다 찍는 것은 마커가 24px 이기 때문이고,
목업이 얼굴 마커를 쓸 수 있었던 것은 5개만 얹었기 때문이다. 둘 다는 안 된다.**

다행히 **1421 · 78px 에서 살아남는 38곳은 대체로 주요 도시다** —
업 · 낙양 · 장안 · 허창 · 서주 · 양양 · 강릉 · 건업 · 성도 …
빠지는 29곳은 **관문 18 · 도시 11** 로, 붐비는 중원과 관문에 몰린다.
**버려지는 것이 무작위가 아니다** — 이것이 「등급으로 솎기」가 유력한 이유다.

## 2. 요청 2 — 깃발 식별 체계

`brief/IDENTIFICATION_SYSTEM.md` 에 안을 썼다. **여기서는 진단의 정정만 적는다.**

### 2-1. 검사기가 한글 첫 음절로 묶고 있다 — 충돌이 부풀려졌다

저장소에 한자 표기가 없어서 `check-mapdata.js` 가 이름의 첫 글자로 그룹을 만든다.
그래서 **한자로는 겹치지 않는 것이 충돌로 집계된다.**

| 검사기 | 실제 한자 | |
|---|---|---|
| 공(공손찬 · 공융) | **公孫**瓚 vs **孔**融 | 충돌 아니다 |
| 조(조조 · 조범) | **曹**操 vs **趙**範 | 충돌 아니다 |

한자로 다시 세면 190년은 11명이 아니라 **9명**, 208년 적벽은 7명이 아니라 **5명**이다.

**그래도 16 중 10 에서 깨진다 — 그쪽 결론은 유효하다.** 크기만 달라진다.

### 2-2. 「성씨가 식별자가 못 된다」는 절반만 맞다

같은 한자를 쓰는 군주를 나누면 두 무리다.

**(가) 세대 승계 — 같은 깃발이 «옳다». 동시에 등장하지 않는다 (데이터로 확인)**

```
曹 조조·조비·조예   孫 손견·손책·손권   馬 마등·마초
司馬 사마의·사마사   公孫 공손찬·공손강·공손탁
```

위나라는 조조가 죽어도 曹다. **여기에 손대면 오히려 잘못된다.**

**(나) 서로 다른 가문이 같은 성씨 — 여기만 깨진다**

```
劉 유비·유표·유장·유도·유요   최대 5 동시
袁 원소·원술                  2
張 장로·장연·장각             2
韓 한복·한수·한현             2
```

> **문제는 네 글자뿐이고 그중 劉가 거의 전부다.**
> 체계를 갈아엎을 일이 아니라 **네 글자에 보조자를 붙일 일**이다.

### 2-3. 색은 시나리오 «안»에서는 유일하다 — 제가 틀렸다

`js/game.js:68` 은 `CLAN_COLORS[i % 20]` 이고 시나리오당 세력은 최대 20이다.
**시작 시점에는 모든 세력의 색이 다르다.** 제가 「색 충돌이 구조적으로 보장돼 있다」고
쓴 것은 **시나리오 «간»**의 이야기였고, 안에서는 참이 아니었다. 정정한다.

**대신 진짜로 새는 곳을 둘 찾았다.**

- **지각적으로 안 갈리는 쌍이 7개** (CIE ΔE < 30). 최악은 `#c08040` / `#e0a040` 로 **ΔE 18**.
  20색이 수치상 다르지만 오렌지·갈색 3, 파랑 3, 초록 3계열이 서로 붙어 있다.
  78px 테두리처럼 작은 면적에서는 더 붙는다
- **런타임 세력 생성이 색을 재사용한다** — `game.js:1173` · `story.js:240·884·1806` 이
  `nid % 20` 을 쓴다. `nid` 가 20을 넘으면 기존 세력과 같은 색이 나온다.
  반란·분열이 있는 긴 판에서 실제로 발생한다

**둘 다 게임 쪽 수정 사항이다.** 후자는 「살아 있는 세력이 안 쓰는 색을 고른다」로 끝난다.
전자(팔레트 재설계)는 Studio 가 맡을 수 있으나 **Q1 이후**다 —
테두리 두께가 정해져야 작은 면적에서의 색 거리를 검증할 수 있다.

### 2-4. 권고

## 3. 요청 3 — 승인 원화 56MB 를 어떻게 보관할 것인가

### 먼저, `.gitignore` 판단은 정확하다

「다시 만들 수 있는 것만 골랐다」가 정확한 기준이다.
후보 312MB · 흉상 크롭 25MB · 루트 입력 9MB — **전부 재생성 가능하다.**
`03_PROJECT_STRUCTURE.md` §16 의 원본–파생 방향 그대로다.

### 그런데 `source/` 는 성격이 다르다

```
03_PROJECT_STRUCTURE.md §27  —  다음은 명시적인 이유 없이 삭제하지 않는다:
                                approved 자산 · 원본 source
```

`assets/portraits/source/` 는 **재생성이 불가능하다.**
생성기는 같은 seed 로도 같은 그림을 보장하지 않고(FLUX 계열), 무엇보다
**「디렉터가 이것을 골랐다」는 사실이 그 파일에만 남아 있다.**
후보 4장 중 하나를 고른 그 선택은 어디에도 다시 기록되지 않는다.

> **`source/` 56MB 는 승인 원본이다. 잃으면 22명분의 판단이 사라진다.**
> `.gitignore` 에 넣지 않은 판단은 옳다.

### 세 안

| | 어떻게 | 비용 | 위험 |
|---|---|---|---|
| **가. 그냥 git 에 넣는다** | 지금 그대로 커밋 | 56MB · 181명이면 ~460MB | clone 이 무거워진다. **되돌릴 수 없다** |
| **나. git-lfs** | `*.png` 중 `source/` 만 LFS | 설정 한 줄 | LFS 없는 환경에서 포인터만 받는다. 호스팅 쿼터 |
| **다. git 밖 + 매니페스트만 git** | 원화는 외부 보관, 해시·출처는 커밋 | 백업 체계가 필요 | 사람이 동기화를 지켜야 한다 |

### 권고 — **나(git-lfs)**. 다만 조건이 하나 붙는다

- **이 저장소는 「빌드 없음 · 의존성 없음」이 정체성**이다(`index.html` 을 열면 돈다).
  LFS 는 그 성질을 **깨지 않는다** — 게임 실행에 필요한 것은 `js/art.js` 이지
  `assets/portraits/source/` 가 아니다. **원화는 제작 자산이지 런타임 자산이 아니다**
- 181명이면 **~460MB** 다. 일반 git 으로 가면 clone 이 그만큼 무거워지고,
  **한 번 커밋하면 히스토리에서 못 뺀다.** 지금이 정하기 가장 싼 시점이다
- 반대로 다안(git 밖)은 **`03` §27 이 지키라는 것을 사람의 성실성에 맡긴다.**
  22명이면 되지만 181명이면 반드시 샌다

**조건:** LFS 로 가더라도 **`manifests/` 는 일반 git 에 남긴다.**
0.5MB 이고, 어떤 프롬프트·모델·seed 로 나왔고 누가 골랐는지가 거기 있다.
**원화를 잃어도 매니페스트가 남으면 다시 시도할 수 있다.** 반대는 성립하지 않는다.

> 참고 — `CAPABILITY_2D_ASSET_FACTORY.md` §7 이 「결정적 생성이면 승인은
> PNG 가 아니라 (해시 + 규칙 + seed) 에 걸 수 있다」고 했다.
> **초상은 그 조건을 만족하지 않는다** — 생성이 결정적이지 않다.
> 그래서 여기서는 PNG 자체가 승인 원본이고, 보관 판단이 필요해진다.

**어느 쪽이든 디렉터 결정이다.** Studio 는 게임 저장소의 git 설정에 손대지 않는다.

## 4. 요청 4 — Q1 을 지도 표시 방식 뒤로 미루는 것

### **동의한다. 순서를 바꾸는 데 찬성한다.**

근거는 그쪽이 든 것과 하나 더 있다.

**① 마커가 Q1 을 밀지 않는다** (그쪽 근거. 동의)
60 이든 78 이든 회화 흉상이 견딘다는 것을 22장으로 실제 확인했다.
Q1 을 정하는 힘이 마커에서 빠졌다.

**② 지도 표시 방식이 Q1 의 «입력»이다** (Studio 가 보태는 근거)
§1-1 의 표가 보여주듯 **지도 종횡비가 겹침을 3배 가른다.**
그리고 §1-2 는 **마커 크기와 마커 수가 맞바꿔진다**고 말한다.

```
지도를 어떻게 보여줄 것인가  →  마커를 몇 개 · 몇 px 로 놓을 것인가
                            →  마커가 화면 폭의 몇 %인가
                            →  Q1 의 논리 해상도가 그 %를 몇 도트로 만드는가
```

**Q1 은 사슬의 끝이지 시작이 아니다.** 지도 표시 방식이 정해지기 전에 논리 해상도를
정하면, 나중에 「얼굴 마커를 안 쓴다」로 결론이 나는 순간 Q1 의 근거였던
8.3% 산술표가 통째로 무의미해진다.

**③ 다만 완전히 미루지는 않는다**
Q1 의 세 안 중 **C안(초상을 30px 도트로 내린다)은 지금 버려도 된다.**
Q7 이 「회화 흉상이 60에서 견딘다」로 닫혔으므로 C안의 유일한 근거가 사라졌다.
**남는 것은 A(2층 분리)와 B(단일 미세 격자) 둘이고, 지도 결정 뒤에 고른다.**

### 수정된 순서

```
1. 지도 표시 방식     ← 지금 여기. 슬라이스 D1~D4 가 재료를 만든다
2. Q1 논리 해상도     ← A · B 둘 중에서
3. 나머지 규격        ← 타일 · 아이콘 그리드 · outline · 팔레트
```

**슬라이스는 이 순서를 막지 않는다.** D1~D4 는 논리 해상도를 확정하지 않고도 만들 수 있다 —
비율로 만들고 실제 표시 크기로 렌더하면 된다. **오히려 그것이 1번의 재료다.**
