# `templates/ART_DIRECTION.md`를 작성하라

현재 저장소는 여러 게임 프로젝트의 그래픽 아트 제작을 담당하는 독립적인 **Game Art Studio**다.

이번 작업에서는 다음 파일 하나만 작성한다.

`templates/ART_DIRECTION.md`

먼저 아래 문서를 모두 읽는다.

* `CLAUDE.md`
* `docs/01_STUDIO_IDENTITY.md`
* `docs/02_DIRECTOR_RELATIONSHIP.md`
* `docs/03_PROJECT_STRUCTURE.md`
* `docs/04_ART_DIRECTION_SYSTEM.md`
* `docs/05_TOOL_ROLES.md`
* `templates/PROJECT_BRIEF.md`

이 문서는 지금까지 만든 Core 문서 체계의 마지막 문서다.

기존 문서에서 정의한 철학과 역할 경계를 유지한다.

새로운 시스템을 추가하거나 기존 구조를 재설계하지 않는다.

이번 문서의 목적은 하나다.

> **각 게임 프로젝트에서 “이 게임은 어떻게 보여야 하는가”를 디렉터와 Art Studio가 공유하기 위한 실전용 아트 디렉션 템플릿을 만든다.**

---

# 1. `ART_DIRECTION.md`의 역할

`ART_DIRECTION.md`는 해당 게임의 **시각적 방향을 기록하는 프로젝트별 핵심 문서**다.

이 문서는 다음 질문에 답할 수 있어야 한다.

* 이 게임을 처음 봤을 때 어떤 인상을 받아야 하는가?
* 어떤 정서와 분위기를 가져야 하는가?
* 무엇이 이 게임의 시각적 정체성을 만드는가?
* 캐릭터는 어떤 방식으로 보여야 하는가?
* 환경과 맵은 어떤 방식으로 보여야 하는가?
* 캐릭터와 배경은 어떤 관계를 가져야 하는가?
* UI 그래픽과 월드는 어떤 관계를 가져야 하는가?
* 어떤 종류의 디테일을 강조하고 무엇을 억제해야 하는가?
* 어떤 레퍼런스에서 무엇을 참고하는가?
* 무엇은 절대 피해야 하는가?
* 실제 게임 화면에서 무엇이 가장 중요하게 읽혀야 하는가?
* 현재 확정된 방향과 아직 탐색 중인 방향은 무엇인가?

이 문서는 단순 이미지 생성 프롬프트가 아니다.

---

# 2. 다른 문서와의 역할 경계

반드시 다음 문서들과 역할을 구분한다.

## `PROJECT_BRIEF.md`

설명하는 것:

> 이 게임은 무엇인가?

예:

* 장르
* 플랫폼
* 카메라
* 핵심 플레이
* 세계
* 주요 자산
* 현재 개발 상태

---

## `ART_DIRECTION.md`

설명하는 것:

> 이 게임은 어떻게 보여야 하는가?

예:

* 인상
* 감정
* 형태 언어
* 색감 방향
* 캐릭터 디자인 방향
* 환경 디자인 방향
* 가독성
* 레퍼런스 해석
* 금지사항

---

## 향후 `STYLE_SPEC.md`

설명하는 것:

> 이 방향을 반복 제작하기 위해 어떤 측정 가능한 규칙을 사용하는가?

예:

* sprite size
* tile size
* palette target
* outline width
* texture dimensions
* animation frame range
* technical rendering constraints

`ART_DIRECTION.md` 안에 기술 수치를 과도하게 넣지 않는다.

필요한 수치가 있더라도 방향 이해에 필요한 정도만 기록하고, 상세 규격은 `STYLE_SPEC.md`로 넘길 수 있도록 한다.

---

# 3. 아트 디렉션은 “스타일 이름”이 아니다

다음처럼 한 줄로 끝내지 않는다.

```text
픽셀 아트
```

또는:

```text
옥토패스풍
```

또는:

```text
90년대 일본 RPG풍
```

이런 표현은 탐색 단계의 shorthand로 사용할 수 있지만 충분한 아트 디렉션이 아니다.

가능하면 다음과 같이 프로젝트 자체의 언어로 환원한다.

예:

```text
낮은 해상도의 캐릭터 스프라이트를 사용하지만
조명과 공간감은 엔진에서 적극적으로 만든다.

캐릭터는 작은 화면에서도 실루엣이 먼저 읽혀야 하며
배경은 캐릭터보다 시각적 대비를 낮춘다.
```

---

# 4. 문서 상단 — Direction Summary

문서 시작 부분에는 전체 방향을 빠르게 이해할 수 있는 짧은 요약을 둔다.

예시 구조:

```text
# ART DIRECTION

## Direction Summary

이 게임의 화면은 ...
```

2~5문단 정도로 작성할 수 있게 한다.

이 부분만 읽어도 Art Studio가 전체적인 방향을 대략 이해할 수 있어야 한다.

마케팅 카피처럼 쓰지 않는다.

실제 제작 판단에 도움이 되는 문장으로 작성한다.

---

# 5. 핵심 시각 키워드

필요하다면 3~8개 정도의 핵심 시각 키워드를 기록할 수 있게 한다.

예:

```text
- 거칠다
- 소박하다
- 장난감 같다
- 따뜻하지만 약간 음침하다
- 큰 형태가 먼저 읽힌다
```

키워드만으로 전체 방향을 정의하지 않는다.

이후 설명의 압축된 인덱스로 사용한다.

---

# 6. 첫인상

게임 화면을 처음 본 사람이 어떤 느낌을 받아야 하는지 기록한다.

예:

* 오래된 골목을 뛰어다니는 느낌
* 작은 장난감 세계를 내려다보는 느낌
* 무거운 역사화 속 인물이 움직이는 느낌
* 밝고 친근하지만 어딘가 이상한 느낌
* 단순하고 귀엽지만 전투에서는 강하게 읽히는 느낌

이 항목은 아트 방향의 정서적 기준점이 된다.

---

# 7. 정서와 분위기

필요에 따라 다음을 설명할 수 있게 한다.

* 밝음 / 어두움
* 긴장 / 편안함
* 유머 / 진지함
* 현실적 / 동화적
* 깨끗함 / 거침
* 따뜻함 / 차가움
* 활기 / 정적
* 친근함 / 위협적임

이를 단순 슬라이더 점수처럼 만들지 않는다.

프로젝트에 필요한 축만 자연어로 설명한다.

---

# 8. 시각적 우선순위

화면에서 무엇이 먼저 보여야 하는지 정리한다.

예:

```text
1. 플레이어와 적
2. 상호작용 가능한 오브젝트
3. 진행 방향
4. 환경 디테일
```

또는:

```text
인물의 얼굴과 표정이 가장 중요하다.
복장 디테일은 두 번째다.
배경은 인물보다 눈에 띄면 안 된다.
```

시각적 위계는 게임 아트에서 중요하므로 명시적으로 다룬다.

---

# 9. 형태 언어

프로젝트 전체에서 반복되는 형태적 성격을 설명한다.

예:

* 큰 덩어리 우선
* 둥근 형태 중심
* 각진 형태 중심
* 짧고 굵은 비율
* 긴 실루엣
* 단순한 외곽 + 제한된 내부 디테일
* 과장된 장비
* 현실적인 비율
* 비대칭 요소 적극 사용

필요하다면 캐릭터, 환경, UI가 서로 다른 형태 언어를 가질 수 있다.

---

# 10. 실루엣

게임플레이에서 실루엣이 얼마나 중요한지 기록한다.

예:

* 멀리서 직업이 구분되어야 한다.
* 몬스터 종류를 색보다 외곽 형태로 먼저 구분한다.
* 작은 화면에서는 머리, 무기, 몸통의 큰 형태만으로 식별 가능해야 한다.
* 중요한 건물은 지붕 형태만으로 구분되어야 한다.

실루엣이 중요하지 않은 프로젝트라면 억지로 규칙을 만들지 않는다.

---

# 11. 캐릭터 방향

캐릭터 디자인의 전체적인 기준을 기록할 수 있게 한다.

필요에 따라 다음을 포함한다.

* 신체 비율
* 얼굴의 중요도
* 실루엣
* 의상 복잡도
* 장비 크기
* 직업 구분 방법
* 캐릭터 간 형태 차이
* 과장 수준
* 현실성 수준
* 재질 표현
* 표정 방향

모든 항목을 반드시 채우게 하지 않는다.

---

# 12. 주요 캐릭터와 일반 캐릭터의 차이

프로젝트에 필요하다면 구분한다.

예:

```text
주요 캐릭터:
얼굴과 장비에서 개성이 강하게 드러난다.

일반 NPC:
형태는 단순하며 색과 소품 차이로 변주한다.
```

또는:

```text
보스:
화면 점유율과 실루엣을 크게 사용한다.

일반 적:
빠른 식별을 위해 형태 종류를 제한한다.
```

---

# 13. 몬스터와 적 디자인

해당 프로젝트에 몬스터 또는 적이 있다면 방향을 기록할 수 있게 한다.

예:

* 인간형 / 비인간형
* 귀여움 / 혐오 / 위협
* 변형 정도
* 형태 반복
* 약점이 시각적으로 보이는가
* 공격 방식이 실루엣에서 읽히는가
* 세계관의 다른 생물과 어떤 관계를 갖는가

몬스터가 없는 게임이라면 섹션을 제거할 수 있도록 한다.

---

# 14. 환경과 맵의 방향

환경이 어떤 인상을 가져야 하는지 설명한다.

예:

* 밀도
* 크기감
* 공간의 깊이
* 반복 정도
* 생활감
* 장식의 양
* 랜드마크 강도
* 플레이 경로의 가독성
* 배경과 전경의 차이

레벨 디자인 자체를 정의하지 않는다.

Art Studio 관점의 시각 설계만 다룬다.

---

# 15. 랜드마크

맵을 탐색하는 게임에서는 랜드마크가 중요한 아트 요소일 수 있다.

필요한 경우 다음을 적는다.

* 멀리서도 식별되는 형태
* 지역별 대표 색이나 구조
* 길 찾기에 사용되는 시각 단서
* 반복되는 건물과 차별되는 요소

---

# 16. 소품과 게임 오브젝트

소품이 게임 세계의 분위기를 만드는 방식도 기록할 수 있다.

예:

* 생활감이 중요하다.
* 모든 소품을 세밀하게 만들지 않는다.
* 상호작용 오브젝트는 형태가 더 명확하다.
* 장식용 소품은 배경에 묻혀야 한다.
* 특정 시대의 물건을 적극 사용한다.

---

# 17. 색의 방향

구체적인 RGB/HEX 목록이 아니라 **색을 사용하는 방향**을 설명한다.

예:

* 전체적으로 낮은 채도
* 캐릭터는 배경보다 채도가 높음
* 위험 요소에만 강한 따뜻한 색 사용
* 그림자는 단순히 검게 만들지 않음
* 지역마다 제한적인 색 정체성을 가짐

세부 팔레트 수치와 색상 표는 향후 `STYLE_SPEC`로 분리할 수 있다.

---

# 18. 명암과 대비

다음을 설명할 수 있게 한다.

* 강한 명암 / 부드러운 명암
* 큰 덩어리의 명암 우선
* 얼굴 강조
* 그림자 깊이
* 배경 대비
* 캐릭터 대비
* 상호작용 요소의 대비

특히 게임플레이 가독성과 연결한다.

---

# 19. 외곽선과 엣지

프로젝트의 외곽 형태가 어떤 식으로 처리되는지 방향을 적을 수 있다.

예:

* 강한 하드 outline
* 부분 outline
* 색이 있는 outline
* outline 없음
* 재질에 따라 edge 처리 차이
* 작은 sprite에서는 hard edge
* 일러스트에서는 부드러운 edge

구체적인 픽셀 두께는 후속 Style Spec에서 정할 수 있다.

---

# 20. 질감과 표면감

필요에 따라 다음을 설명한다.

* 깨끗한 flat surface
* 거친 brush
* grain
* 손그림 흔적
* dithering
* 재질별 texture 차이
* 오래된 표면
* polished / matte

게임 전체를 같은 texture로 덮는 식의 단순 규칙을 만들지 않는다.

---

# 21. 디테일 밀도

어디에 디테일을 쓰고 어디에서 줄이는지 설명한다.

예:

```text
얼굴과 무기:
높은 정보 밀도

몸통:
중간

배경의 반복 오브젝트:
낮음
```

또는:

> 실루엣과 큰 색 덩어리가 먼저 읽힌 후 가까이에서만 작은 디테일이 보이게 한다.

“디테일이 많을수록 좋다”는 방향을 만들지 않는다.

---

# 22. 조명

조명이 스타일에 어떻게 기여하는지 설명한다.

반드시 다음 가능성을 구분할 수 있게 한다.

## 에셋 안에 그려지는 조명

예:

* sprite 내부 highlight
* baked shadow
* painted rim light

## 엔진에서 만들어지는 조명

예:

* dynamic light
* bloom
* fog
* volumetric effect
* color grading
* shadows

## 혼합

둘이 역할을 나눈다.

필요하면 다음 질문에 답한다.

> 이 게임의 인상을 만드는 빛은 주로 어디에서 만들어지는가?

---

# 23. 카메라와 표시 크기

카메라 정보 자체는 `PROJECT_BRIEF`에 있을 수 있다.

`ART_DIRECTION`에서는 그 카메라 때문에 어떤 디자인 방향이 필요한지 적는다.

예:

```text
캐릭터가 화면에서 작게 보이므로
얼굴 디테일보다는 머리, 몸통, 무기의 큰 형태를 우선한다.
```

또는:

```text
카메라가 얼굴 가까이 접근하므로
눈, 피부, 머리카락의 표현 품질이 중요하다.
```

---

# 24. 캐릭터와 배경의 관계

중요한 섹션으로 둔다.

예:

* 캐릭터가 배경보다 대비가 강해야 한다.
* 배경 채도를 낮춘다.
* 배경의 edge density를 줄인다.
* 캐릭터 주변에 시각적 여백을 둔다.
* 밝은 배경에서는 캐릭터 outline을 강화한다.

모든 프로젝트가 동일한 방법을 쓸 필요는 없다.

---

# 25. 플레이 가독성

아트 디렉션은 미적 방향만 다루지 않는다.

게임에서 읽혀야 하는 정보를 기록한다.

예:

* 적/아군
* 직업
* 위험
* 공격 범위
* 상호작용 가능 여부
* 중요 아이템
* 이동 경로
* 체력 상태
* 팀 색
* 몬스터 종류

필요한 정보가 시각적 스타일과 충돌할 경우 가독성을 우선할 수도 있다.

구체적인 우선순위는 프로젝트가 결정한다.

---

# 26. UI 그래픽 방향

UI 자체의 UX 구조를 설계하는 문서로 만들지 않는다.

Art Studio 관점에서 필요한 정도만 기록한다.

예:

* 월드와 동일한 형태 언어 사용
* UI만 더 깨끗하게 표현
* 손으로 그린 패널
* pixel icon
* flat icon
* world graphics와 HUD의 대비 수준

필요 없다면 간결하게 유지한다.

---

# 27. 타이포그래피와 텍스트 요소

게임 아트 방향에 영향을 줄 경우에만 기록한다.

예:

* 간판과 세계 내 텍스트는 시대감을 따라야 함
* HUD font는 별도 UI 시스템에서 관리
* pixel font 여부
* 장식성이 강한 제목과 본문을 구분

구체적인 font licensing이나 UI typography system까지 확대하지 않는다.

---

# 28. 애니메이션 방향

애니메이션이 중요한 게임이면 다음과 같은 방향을 기록할 수 있다.

* snappy
* smooth
* exaggerated
* restrained
* limited frames
* realistic
* cartoon timing
* strong anticipation
* short impact frames

프레임 수 같은 기술값은 후속 규격 문서에서 상세화한다.

---

# 29. VFX 방향

필요할 경우 다음을 설명한다.

* 공격 효과의 크기
* 화면을 가리는 정도
* bloom 사용
* impact 표현
* particle density
* 마법과 물리 공격의 구분
* 색상의 역할
* 가독성과 화려함의 우선순위

---

# 30. 레퍼런스 섹션

중요한 레퍼런스를 기록할 수 있는 구조를 만든다.

단순히 이미지 이름이나 작품 이름만 나열하지 않는다.

가능하면 각 레퍼런스에서 **무엇을 참고하는지** 기록한다.

예:

```text
### Reference A

참고:
- 캐릭터 비율
- 단순한 실루엣

참고하지 않음:
- 색감
- UI
```

또는:

```text
### Reference B

참고:
- 야간 조명
- 안개를 통한 깊이감
```

---

# 31. 레퍼런스의 위계

여러 레퍼런스가 있는 경우 모두 같은 중요도로 취급하지 않을 수 있다.

필요하다면 다음과 같은 상태를 표현할 수 있게 한다.

* primary
* secondary
* detail reference
* technical reference

하지만 복잡한 scoring system은 만들지 않는다.

---

# 32. “따라하지 않을 것”도 기록한다

레퍼런스와 비슷해지는 과정에서 원하지 않는 요소가 따라올 수 있다.

예:

```text
Reference A에서 가져올 것:
- 밀도
- 실루엣

가져오지 않을 것:
- 고채도
- 귀여운 얼굴 비율
```

이 구분은 매우 유용하다.

---

# 33. 금지사항

별도의 명확한 섹션을 둔다.

예:

* 지나친 사실주의 금지
* glossy plastic 느낌 금지
* 과도한 미세 장식 금지
* 읽을 수 없는 실루엣 금지
* AI 특유의 무의미한 세부 패턴 금지
* world setting과 맞지 않는 현대 요소 금지
* UI처럼 보이는 환경 오브젝트 금지

금지사항은 프로젝트마다 완전히 달라질 수 있다.

---

# 34. 안티 레퍼런스

필요하다면 “이 방향으로 가면 안 된다”는 시각 자료도 기록할 수 있다.

이를 단순히 나쁜 이미지라고 부르지 않는다.

어떤 속성이 문제인지 함께 적는다.

예:

```text
이 이미지는 사용하지 않는다:
캐릭터 비율이 아니라 과도한 재질 광택 때문에 방향과 맞지 않는다.
```

---

# 35. 확정된 것

현재 디렉터가 확정한 중요한 방향을 별도로 정리할 수 있게 한다.

예:

```text
## 확정된 방향

- 캐릭터는 큰 실루엣을 우선한다.
- 배경은 캐릭터보다 시각적 대비가 낮다.
- 조명은 엔진의 역할이 크다.
```

이 섹션은 Claude가 탐색 중인 아이디어와 확정 규칙을 혼동하는 것을 줄여준다.

---

# 36. 탐색 중인 것

별도의 섹션으로 둔다.

예:

```text
## 탐색 중

- outline 강도
- 캐릭터 머리 비율
- 야간 맵 색감
```

아직 결정되지 않은 내용을 억지로 표준으로 만들지 않는다.

---

# 37. 보류된 방향

필요하다면 현재 사용하지 않지만 완전히 폐기하지 않은 방향을 기록할 수 있다.

예:

```text
보류:
고밀도 캐릭터 sprite.

현재 prototype에서는 저밀도 방향을 먼저 검증한다.
```

템플릿을 지나치게 복잡하게 만들지 않도록 선택적 섹션으로 둔다.

---

# 38. 전역 규칙과 국소 규칙

중요한 결정에는 가능하면 적용 범위를 알 수 있게 한다.

예:

```text
Project-wide:
배경은 캐릭터보다 낮은 대비.

Character family:
기사 계열은 넓은 어깨 실루엣.

Individual asset:
보스 A만 outline 없음.
```

모든 문장마다 scope label을 붙이게 하지는 않는다.

혼동 가능성이 있을 때만 명확하게 적을 수 있도록 한다.

---

# 39. 디렉터의 언어를 보존한다

디렉터가 사용하는 감각적인 표현을 모두 기술 용어로 치환하지 않는다.

예:

```text
"조금 싸구려 놀이공원 같다"
"너무 잘 만든 느낌이면 안 된다"
"한 번 보면 잊히지 않는 얼굴"
"무겁지만 답답하면 안 된다"
```

이런 표현은 실제 아트 판단에 매우 중요한 기준이 될 수 있다.

필요하면 그 아래에 기술적인 해석을 추가할 수 있다.

예:

```text
디렉터 표현:
"너무 깨끗하면 안 된다."

실무 해석:
- 표면 variation 허용
- 완전히 균일한 gradient 지양
- 생활감 있는 마모 표현
```

원래 표현을 삭제하지 않는다.

---

# 40. 디렉터의 언어와 Claude의 해석을 구분할 수 있다

필요한 경우 다음처럼 구분한다.

```text
Director intent:
...

Working interpretation:
...
```

이렇게 하면 Claude의 해석이 디렉터의 공식 결정으로 변질되는 것을 막을 수 있다.

모든 항목에 이를 강제하지 않는다.

---

# 41. 프로젝트 자체의 언어를 발전시킨다

초기에는 유명 작품을 레퍼런스로 사용할 수 있다.

하지만 프로젝트가 진행될수록 다음처럼 자체적인 언어가 축적되어야 한다.

초기:

```text
셀레스트와 비슷한 밀도
```

이후:

```text
낮은 sprite 밀도
큰 실루엣
제한된 내부 디테일
강한 캐릭터/배경 대비
```

초기:

```text
옥토패스 같은 빛
```

이후:

```text
sprite 자체 shading은 절제하고
엔진 조명, bloom, fog로 공간감을 만든다.
```

`ART_DIRECTION.md`는 시간이 지날수록 이러한 자체 언어가 축적되는 곳이다.

---

# 42. 스타일을 하나의 레퍼런스로 고정하지 않는다

한 작품의 모든 요소를 따라가려 하지 않는다.

예:

```text
A → 캐릭터 밀도
B → 조명
C → 환경 색감
D → 애니메이션 템포
```

처럼 복수 레퍼런스를 의도적으로 조합할 수 있다.

중요한 것은 각 요소가 왜 선택되었는지를 이해하는 것이다.

---

# 43. 아트 디렉션은 변경될 수 있다

이 문서는 처음 작성한 뒤 영원히 고정되는 규칙집이 아니다.

실제 제작과 게임 적용 과정에서 방향이 발전할 수 있다.

예:

```text
concept
→ prototype
→ game screenshot
→ director review
→ direction refinement
```

단, 매번 작은 피드백을 전체 Art Direction 변경으로 확대하지 않는다.

---

# 44. 변경 이유를 남길 수 있다

큰 방향 변경이 있을 경우 짧게 이유를 기록할 수 있게 한다.

예:

```text
2026-XX-XX

변경:
배경 디테일 밀도를 낮춤.

이유:
실제 플레이 화면에서 캐릭터 가독성이 부족했음.
```

상세 리뷰 이력은 후속 `REVIEW_LOG.md`가 담당한다.

여기에는 현재 방향을 이해하는 데 필요한 큰 변화만 남긴다.

---

# 45. 실제 게임 화면 섹션

필요하다면 현재 방향을 대표하는 게임 화면이나 screenshot 위치를 연결할 수 있게 한다.

예:

```text
## Current Visual Target

- `reviews/vertical-slice-01.png`
- `reviews/night-lighting-test.png`
```

개별 에셋보다 실제 게임 화면이 더 강력한 아트 기준이 될 수 있다.

---

# 46. 대표 기준 자산

프로젝트가 진행되면 특정 승인 에셋이 스타일 기준 역할을 할 수 있다.

예:

```text
캐릭터 기준:
approved/characters/hero.png

환경 기준:
approved/environment/street_01.png
```

하지만 한 자산이 모든 스타일 규칙을 완전히 대표한다고 가정하지 않는다.

---

# 47. 스타일 드리프트 방지

아트 방향 문서는 생성 모델을 통제하기 위한 것이 아니라 **프로젝트가 여러 작업을 거치면서 조금씩 다른 스타일로 흘러가는 것을 방지하기 위한 기억 장치**이기도 하다.

새 자산을 만들 때 다음을 비교할 수 있다.

* 현재 Art Direction
* 대표 레퍼런스
* 승인된 기존 자산
* 실제 게임 screenshot

필요하면 차이를 분석한다.

---

# 48. 생성 프롬프트와 분리한다

이 문서 안에 특정 생성기의 완성형 prompt를 중심 내용으로 넣지 않는다.

관계는 다음과 같다.

```text
ART_DIRECTION.md
        ↓
ASSET_BRIEF
        ↓
tool selection
        ↓
tool-specific prompt
```

하나의 생성기가 바뀌어도 `ART_DIRECTION.md`는 유지되어야 한다.

---

# 49. 기술 규격과 분리한다

예를 들어 다음 정보는 아트 방향에서 의미가 있을 수 있다.

```text
캐릭터는 낮은 픽셀 밀도를 사용한다.
```

하지만 다음 수준은 후속 `STYLE_SPEC.md`가 더 적합하다.

```text
base sprite = 48×64 px
outline = 1 px
palette <= 32 colors
```

아트 방향 문서를 수치표로 만들지 않는다.

---

# 50. 좋은 아트 디렉션 문장의 기준

좋은 문장은 실제 제작 판단에 영향을 줄 수 있어야 한다.

나쁜 예:

```text
예쁘고 세련된 그래픽.
```

좋은 예:

```text
배경은 세밀하지만 플레이어 주변에서는 작은 디테일을 줄여
캐릭터 실루엣이 먼저 읽히게 한다.
```

나쁜 예:

```text
레트로한 느낌.
```

좋은 예:

```text
현대적인 고해상도 일러스트를 낮은 해상도로 축소한 느낌이 아니라,
처음부터 제한된 픽셀 수 안에서 큰 형태와 색 덩어리를 설계한 느낌을 목표로 한다.
```

---

# 51. 모순을 숨기지 않는다

아트 방향에는 서로 긴장되는 요구가 있을 수 있다.

예:

```text
캐릭터는 단순해야 한다.
하지만 주요 캐릭터는 개성이 강해야 한다.
```

이를 억지로 하나로 합치지 않는다.

오히려 어떻게 균형을 잡을지 설명할 수 있다.

예:

```text
기본 몸체는 단순하게 유지하고,
머리 형태와 대표 장비에서 개성을 만든다.
```

---

# 52. 모든 축을 반드시 채우지 않는다

`04_ART_DIRECTION_SYSTEM.md`에서 정의한 모든 시각 축을 템플릿에 강제하지 않는다.

프로젝트에 의미 있는 항목만 사용한다.

예:

* UI가 없는 게임이면 UI 섹션을 생략할 수 있다.
* 캐릭터가 없는 게임이면 캐릭터 섹션을 생략한다.
* 엔진 조명이 없는 게임이면 조명 설명을 단순화한다.

템플릿은 범용적이어야 하지만 문서는 프로젝트에 맞게 가벼워질 수 있어야 한다.

---

# 53. 권장 템플릿 구조

최종 템플릿은 대략 다음 구조를 기반으로 정리한다.

정확한 제목이나 세부 그룹은 가독성을 위해 조정해도 된다.

```text
# ART DIRECTION

## 1. Direction Summary
## 2. 핵심 시각 키워드
## 3. 목표하는 첫인상과 정서
## 4. 시각적 우선순위
## 5. 형태 언어와 실루엣
## 6. 캐릭터 방향
## 7. 적 / 몬스터 방향
## 8. 환경과 맵 방향
## 9. 소품과 게임 오브젝트
## 10. 색 / 명암 / 질감
## 11. 조명과 엔진 표현
## 12. 카메라에 따른 아트 방향
## 13. 캐릭터와 배경의 관계
## 14. 플레이 가독성
## 15. UI / VFX / 애니메이션 방향
## 16. References
## 17. Anti-References / 금지사항
## 18. 확정된 방향
## 19. 탐색 중인 방향
## 20. 대표 기준 화면 / 에셋
## 21. 주요 변경 기록
```

프로젝트가 단순하면 섹션을 축소할 수 있어야 한다.

---

# 54. 각 섹션의 작성 힌트

템플릿이므로 각 섹션에 짧은 HTML comment를 사용하여 작성 목적을 설명한다.

예:

```text
## 형태 언어와 실루엣

<!--
큰 형태, 비율, 반복되는 실루엣 규칙 등을 적는다.
기술적인 픽셀 수치는 STYLE_SPEC으로 넘긴다.
-->
```

안내문이 본문보다 더 복잡해지지 않도록 한다.

---

# 55. 예시를 과도하게 넣지 않는다

현재 이 프롬프트에는 이해를 돕기 위해 많은 예시가 있지만 실제 템플릿에서는 예시를 대폭 줄인다.

이유:

* 특정 장르의 흔적이 남을 수 있다.
* 예시가 잘못된 기본값처럼 작동할 수 있다.
* 새로운 게임의 창작 방향을 제한할 수 있다.

실제 `ART_DIRECTION.md`에는:

* 작성 힌트
* placeholder
* 필요한 경우 매우 짧은 추상적 예시

정도만 남긴다.

---

# 56. 문서의 길이

템플릿 자체는 충분히 깊어야 하지만, 실제 프로젝트에서 모든 항목을 길게 채워야 한다고 느껴지면 실패다.

초기 프로젝트에서는 핵심 섹션만 채워도 작업을 시작할 수 있어야 한다.

프로젝트가 성장하면서 방향을 추가할 수 있어야 한다.

즉:

> 처음부터 완성된 Art Bible을 요구하지 않는다.

---

# 57. 초기 작성과 성숙한 문서 모두 지원한다

초기에는 다음 정도일 수 있다.

```text
Direction Summary
References
Character Direction
Environment Direction
Do Not
Exploring
```

프로젝트가 성숙하면:

* 색
* 조명
* VFX
* 형태 언어
* category별 방향
* 대표 승인 자산

등이 추가될 수 있다.

같은 템플릿이 둘 다 지원해야 한다.

---

# 58. 미정 상태를 허용한다

다음과 같이 기록할 수 있어야 한다.

```text
조명:
현재 탐색 중.

캐릭터 비율:
A/B 두 방향 테스트 예정.

UI:
아직 아트 방향 미정.
```

Claude가 템플릿의 빈칸을 보고 임의로 채우지 않도록 한다.

---

# 59. 디렉터가 실제로 사용하는 문서여야 한다

이 문서는 Claude를 위한 데이터 파일만이 아니다.

게임 디렉터가 읽고 수정할 수 있어야 한다.

따라서:

* 지나치게 기계적인 schema를 만들지 않는다.
* 모든 내용을 표로 만들지 않는다.
* JSON처럼 작성하지 않는다.
* 자연어 설명을 충분히 허용한다.

필요하면 나중에 `STYLE_SPEC`이나 structured data로 기술 정보를 파생할 수 있다.

---

# 60. 이 문서에서 다루지 않는 것

다음은 후속 문서에서 다룬다.

* asset별 상세 발주
* 정확한 sprite dimensions
* tile dimensions
* palette count
* naming convention
* animation frame specification
* asset lifecycle
* candidate 수
* 승인 workflow
* 생성 prompt
* MCP/API 사용법
* generator parameter
* engine import settings
* validation script
* 상세 review history
* 전체 asset 목록

`ART_DIRECTION.md`는 이 모든 문서가 공유해야 하는 **시각적 방향의 상위 기준**이다.

---

# 61. 템플릿 마지막에 둘 짧은 섹션

문서 마지막에는 다음 두 영역을 두는 것을 권장한다.

## Current Direction in One Paragraph

현재 프로젝트의 방향을 한 문단으로 압축한다.

이 문장은 다른 도구나 새로운 작업자가 프로젝트 방향을 빠르게 파악할 때 사용할 수 있다.

## What Matters Most

현재 프로젝트에서 절대 잃으면 안 되는 시각적 특징을 3~5개 정도 기록할 수 있게 한다.

예:

```text
- 캐릭터 실루엣
- 배경과 플레이 대상의 분리
- 거친 시대감
```

실제 예시는 템플릿에서는 placeholder 중심으로 만든다.

---

# 62. 핵심 철학

완성된 템플릿은 다음 철학을 반영해야 한다.

> Art Direction은 이미지 생성 프롬프트가 아니다.
>
> 게임의 시각적 의도와 판단 기준을 사람과 제작 도구가 공유하기 위한 문서다.
>
> 감각적인 언어와 분석 가능한 시각 규칙은 함께 존재할 수 있다.
>
> 디렉터의 표현은 기술 용어로 완전히 지워지지 않는다.
>
> 레퍼런스는 복제 대상이 아니라 어떤 요소를 선택할지 판단하기 위한 자료다.
>
> 확정된 방향과 탐색 중인 방향을 구분한다.
>
> 상세 수치는 Style Specification으로 분리한다.
>
> 최종 판단 기준은 개별 이미지가 아니라 실제 게임 화면에서 만들어지는 경험이다.

# 작성 원칙

* 한국어로 작성한다.
* 실제 프로젝트에 복제해 사용할 수 있는 Markdown 템플릿을 작성한다.
* Core 문서들의 철학을 보존한다.
* `PROJECT_BRIEF.md`의 게임 설명을 반복하지 않는다.
* `STYLE_SPEC.md` 역할을 미리 흡수하지 않는다.
* 특정 게임 장르를 기본값으로 만들지 않는다.
* 특정 화풍을 기본값으로 만들지 않는다.
* 픽셀 아트에만 치우치지 않는다.
* 이미지 생성 AI용 프롬프트 문서로 만들지 않는다.
* 레퍼런스 작품명을 나열하는 문서로 만들지 않는다.
* 디렉터의 감각적 표현을 보존할 수 있게 한다.
* Claude의 해석과 디렉터의 결정을 혼동하지 않게 한다.
* 확정 / 탐색 중 상태를 구분할 수 있게 한다.
* 미정 상태를 정상적으로 허용한다.
* 자산 종류별 방향을 필요할 때 확장할 수 있어야 한다.
* 게임플레이 가독성을 아트 방향의 일부로 다룬다.
* 엔진 조명, VFX, 카메라가 최종 인상에 기여할 수 있음을 반영한다.
* 실제 게임 screenshot과 승인 자산이 향후 reference 역할을 할 수 있도록 한다.
* 템플릿은 깊지만 작성 부담은 낮아야 한다.
* 모든 항목을 필수로 만들지 않는다.
* AI 시스템 설계 문서처럼 보이지 않게 한다.
* 실제 게임 아트 디렉터가 사용하는 작업 문서처럼 만들어라.

완성 후:

1. `templates/ART_DIRECTION.md`를 생성한다.
2. 전체 템플릿을 출력한다.
3. 이 템플릿에서 **초기 프로젝트에서도 최소한 채워야 할 핵심 섹션**이 무엇인지 짧게 정리한다.
4. `PROJECT_BRIEF.md`와 역할이 어떻게 다른지 짧게 설명한다.
5. 기존 문서를 수정하지 않는다.
6. 다른 문서나 폴더를 생성하지 않는다.
7. 후속 문서를 만들지 않는다.
8. **Core 8 문서가 완료되었다는 사실만 알리고 멈춘다.**
