# `docs/04_ART_DIRECTION_SYSTEM.md`를 작성하라

현재 저장소는 여러 게임 프로젝트의 그래픽 아트 제작을 담당하는 독립적인 **Game Art Studio**다.

이번 작업에서는 다음 파일 하나만 작성한다.

`docs/04_ART_DIRECTION_SYSTEM.md`

먼저 아래 문서를 읽는다.

* `CLAUDE.md`
* `docs/01_STUDIO_IDENTITY.md`
* `docs/02_DIRECTOR_RELATIONSHIP.md`
* `docs/03_PROJECT_STRUCTURE.md`

기존 문서의 원칙과 역할 분리를 유지한다.

이번 문서는 앞선 문서의 내용을 요약하거나 반복하는 문서가 아니다.

목적은 하나다.

> **각 게임 프로젝트의 아트 디렉션을 어떤 개념과 속성으로 이해하고, 기록하고, 다른 제작 도구에 전달할 것인지 정의한다.**

---

# 1. 이 문서의 역할

`04_ART_DIRECTION_SYSTEM.md`는 게임별 아트 방향을 다루는 **상위 개념 체계**다.

이 문서를 읽으면 다음 질문에 답할 수 있어야 한다.

* 게임의 “화풍”을 무엇으로 분해해서 이해하는가?
* 레퍼런스 이미지는 어떤 역할을 하는가?
* 감각적인 디렉팅 언어와 측정 가능한 기술 규격은 어떻게 함께 다루는가?
* 한 장의 컨셉아트에서 무엇을 읽어낼 수 있고 무엇은 사람이 결정해야 하는가?
* 캐릭터, 배경, 맵, UI, 조명 등이 하나의 아트 방향 안에서 어떻게 연결되는가?
* 프로젝트의 스타일이 발전하거나 변경될 때 어떻게 다루는가?
* 아트 디렉션을 특정 생성기의 프롬프트로 축소하지 않으려면 어떻게 해야 하는가?

이 문서에서는 특정 게임의 실제 스타일을 정하지 않는다.

---

# 2. 기본 원칙

Art Studio 자체에는 고정 화풍이 없다.

각 게임은 자신의 아트 방향을 가진다.

따라서:

```text id="cvhh4s"
ART STUDIO
    └── 고정 스타일 없음

GAME PROJECT
    ├── PROJECT_BRIEF
    ├── ART_DIRECTION
    ├── REFERENCES
    ├── STYLE SPEC
    └── DIRECTOR DECISIONS
```

게임의 스타일은 하나의 숫자나 하나의 프롬프트로 정의되지 않는다.

다음 정보들이 함께 작동한다.

> 의도 + 레퍼런스 + 시각적 규칙 + 기술적 제약 + 실제 게임 화면에서의 판단

---

# 3. 아트 디렉션과 스타일 규격을 구분한다

다음 두 개념을 명확하게 분리한다.

## Art Direction

게임이 **어떻게 보여야 하고 어떤 인상을 주어야 하는지**를 설명한다.

예:

* 밝지만 싸구려 놀이공원 같은 느낌
* 오래된 한국 골목의 따뜻함과 약간의 음침함
* 장난감처럼 단순하지만 전투에서는 실루엣이 강해야 함
* 역사화처럼 무겁고 인물의 권위가 느껴져야 함
* 귀엽지만 지나치게 유아적으로 보이면 안 됨

이 정보는 감각적이고 서술적일 수 있다.

---

## Style Specification

그 방향을 실제 제작에 적용하기 위해 사용할 수 있는 **측정 가능하거나 반복 가능한 특성**이다.

예:

```text id="novzsp"
character height
tile size
aspect ratio
palette range
outline treatment
value steps
texture density
animation frame count
camera angle
lighting method
```

둘은 같은 것이 아니다.

Art Direction이 이유와 목표를 설명한다면 Style Specification은 제작 시 반복 가능한 형태로 환원된 규칙을 설명한다.

---

# 4. 스타일은 여러 축의 조합이다

화풍을 하나의 장르 이름으로만 표현하지 않는다.

예를 들어:

```text id="pdy0mh"
"픽셀 아트"
"애니풍"
"반실사"
"HD-2D"
```

만으로는 실제 제작에 필요한 정보가 부족하다.

대신 여러 시각적 축의 조합으로 이해한다.

다음 분류를 기본적인 분석 프레임으로 사용할 수 있다.

---

# 5. 표현 방식

가장 먼저 에셋의 기본 표현 방식을 파악한다.

예:

* pixel art
* raster illustration
* vector-like graphic
* hand-painted
* 3D rendered
* low-poly
* sprite-based
* 3D geometry + 2D sprite
* mixed media

한 게임 안에서도 자산 종류에 따라 표현 방식이 다를 수 있다.

예:

```text id="nvcu5w"
characters → pixel sprite
background → 3D geometry
portraits → painted illustration
UI icons → clean raster graphic
```

전체 게임을 하나의 제작 방식으로 억지로 통일하지 않는다.

---

# 6. 해상도와 시각 밀도

해상도는 단순한 출력 크기가 아니라 화풍의 일부일 수 있다.

특히 픽셀 아트에서는 원본 해상도와 캐릭터 크기가 시각 언어에 직접적인 영향을 준다.

분석 가능한 요소:

* 내부 렌더 해상도
* 캐릭터 화면 점유율
* sprite pixel dimensions
* tile dimensions
* 오브젝트당 평균 디테일
* 배경 정보 밀도
* 실루엣 대비 내부 디테일의 비율

예를 들어:

```text id="6vmula"
low density
←────────────────────────→
high density

큰 픽셀 / 단순한 면
                       작은 픽셀 / 세밀한 형태
```

이를 “좋고 나쁨”의 척도로 사용하지 않는다.

각 게임에 적합한 위치가 다르다.

---

# 7. 형태 언어

자산의 형태가 어떤 규칙을 따르는지 본다.

예:

* 둥근 형태 중심
* 각진 형태 중심
* 큰 머리 / 작은 몸
* 현실적인 인체 비율
* 과장된 무기
* 넓은 실루엣
* 길고 가는 형태
* 단순한 덩어리
* 복잡한 장식

특히 다음을 분석할 수 있다.

```text id="k1szrx"
silhouette
proportion
shape repetition
shape contrast
detail placement
exaggeration
```

캐릭터와 환경이 서로 완전히 다른 형태 언어를 사용하지 않는지 확인할 수 있다.

---

# 8. 실루엣과 가독성

게임 아트에서는 세부 묘사보다 실루엣이 중요한 경우가 많다.

특히:

* 작은 화면
* 빠른 전투
* 모바일
* Roblox
* 픽셀 아트
* 여러 캐릭터가 동시에 등장하는 게임

에서는 중요도가 더 높아질 수 있다.

분석 요소:

* 캐릭터의 외곽 형태
* 무기 식별
* 직업 구분
* 적/아군 구분
* 크기 단계
* 자세 차이
* 랜드마크 구분

가독성은 스타일의 일부로 다룬다.

---

# 9. 외곽선

다음 요소를 구분해서 기록할 수 있다.

* outline 존재 여부
* outline 두께
* 전면 outline / 부분 outline
* 검은 outline / 색 outline
* 내부 선의 사용
* 조명에 따른 outline 변화
* pixel hard edge
* antialiased edge

특히 픽셀 아트에서는 1px 차이도 스타일에 큰 영향을 줄 수 있다.

---

# 10. 팔레트

팔레트는 단순한 대표색 목록이 아니다.

다음과 같이 볼 수 있다.

* 전체 색 수
* 자산당 색 수
* saturation range
* value range
* hue bias
* shadow hue
* highlight hue
* neutral colors
* accent colors
* faction colors
* environment / character separation

필요하다면 코드로 측정할 수 있다.

하지만 측정된 팔레트가 자동으로 아트 방향을 결정하지는 않는다.

---

# 11. 명암과 램프

색 하나가 몇 단계로 변화하는지를 분석할 수 있다.

예:

```text id="a81nix"
shadow
↓
mid shadow
↓
base
↓
light
↓
highlight
```

분석 요소:

* 램프 단계 수
* shadow depth
* highlight strength
* hue shifting
* ambient light
* contrast
* material-specific shading

픽셀 아트에서는 램프 길이가 밀도와 화풍에 직접적인 영향을 줄 수 있다.

---

# 12. 질감

이미지가 어떤 표면감을 갖는지 본다.

예:

* 완전히 평평한 색
* 거친 브러시
* 캔버스 질감
* grain
* dithering
* noise
* 깨끗한 디지털 면
* 재질별 texture
* hand-painted variation

질감은 모든 자산에 동일한 방식으로 적용될 필요는 없다.

---

# 13. 조명

조명은 특히 중요한 축이다.

다음을 구분한다.

## 에셋 내부 조명

이미지 자체에 그려진 빛.

예:

* baked highlight
* painted shadow
* sprite 내부 rim light

## 엔진 조명

Unity, Godot, Roblox 등의 런타임에서 적용되는 빛.

예:

* directional light
* point light
* 2D light
* rim light
* bloom
* fog
* post-processing

어떤 게임에서는 에셋 자체의 shading이 대부분의 분위기를 만든다.

다른 게임에서는 엔진 조명이 화풍의 상당 부분을 만든다.

따라서 다음 질문을 항상 구분한다.

> **빛을 그림이 만드는가, 엔진이 만드는가, 둘이 나누어 만드는가?**

---

# 14. 카메라와 관찰 거리

같은 에셋도 카메라에 따라 완전히 다르게 읽힌다.

따라서 아트 방향에는 필요에 따라 다음 정보가 포함될 수 있다.

* top-down
* isometric
* side view
* first person
* third person
* orthographic
* perspective
* camera distance
* field of view
* typical on-screen character size

아트 자산은 최종 표시 크기를 고려해서 설계한다.

---

# 15. 배경과 캐릭터의 관계

캐릭터와 배경을 각각 예쁘게 만드는 것만으로 충분하지 않다.

둘의 관계를 정의해야 한다.

예:

* 캐릭터가 항상 배경보다 대비가 강하다.
* 배경은 캐릭터보다 한 단계 낮은 채도를 사용한다.
* 주요 상호작용 오브젝트만 강한 highlight를 갖는다.
* 배경 디테일은 이동 경로 근처에서 줄인다.

이는 미적 규칙인 동시에 플레이 가독성 규칙이 될 수 있다.

---

# 16. UI와 게임 월드의 관계

UI 그래픽도 게임 전체 시각 언어의 일부다.

그러나 UI/UX 설계 전체를 Art Studio가 담당한다고 가정하지 않는다.

아트 관점에서는 다음을 볼 수 있다.

* icon rendering style
* border language
* material feel
* shape language
* typography와 그래픽의 관계
* in-world graphic과 HUD graphic의 차이

UI가 게임 월드와 지나치게 다른 시각 언어를 사용하는지 확인할 수 있다.

---

# 17. 애니메이션 스타일

정지 이미지뿐 아니라 움직임도 화풍에 포함된다.

예:

* frame count
* snappy / smooth
* pose exaggeration
* anticipation
* smear
* squash & stretch
* limited animation
* realistic motion
* stepped animation

픽셀 아트의 경우 프레임 수와 움직임 간격 자체가 스타일의 일부가 될 수 있다.

---

# 18. VFX와 후처리

화풍의 일부는 원본 에셋이 아니라 런타임 효과에서 만들어질 수 있다.

예:

* bloom
* fog
* particles
* screen shake
* color grading
* depth of field
* distortion
* outline shader
* lighting
* shadow
* weather effects

따라서 최종 화면 스타일을 분석할 때 **에셋과 엔진 효과를 구분해서 본다.**

---

# 19. 레퍼런스의 역할

레퍼런스는 단순히 “이것처럼 만들어라”는 복제 명령이 아니다.

레퍼런스는 방향을 분석하기 위한 자료다.

레퍼런스마다 참고하려는 속성이 다를 수 있다.

예:

```text id="5osgfn"
Reference A
→ 색감 참고

Reference B
→ 캐릭터 비율 참고

Reference C
→ 배경 밀도 참고

Reference D
→ 조명 참고
```

가능하면 어떤 레퍼런스에서 무엇을 참고하는지 구분한다.

여러 레퍼런스를 아무 기준 없이 섞지 않는다.

---

# 20. 레퍼런스에서 측정 가능한 것과 없는 것

코드나 비전 모델을 사용하면 다음과 같은 요소를 분석할 수 있다.

예:

* dominant colors
* palette size
* brightness distribution
* contrast
* edge density
* approximate sprite size
* outline characteristics
* composition
* texture density

그러나 다음과 같은 질문은 측정만으로 정답이 나오지 않는다.

* 왜 이 그림이 매력적인가
* 이 게임에 어떤 스타일이 가장 적합한가
* 어느 정도의 과장이 좋은가
* 어떤 캐릭터 디자인을 최종 채택할 것인가

분석 결과를 디렉터의 판단을 대체하는 정답으로 취급하지 않는다.

---

# 21. “스타일 추출”이라는 표현을 조심한다

레퍼런스에서 스타일을 완전히 추출할 수 있다고 가정하지 않는다.

정확한 표현은 다음에 가깝다.

> 레퍼런스에서 관찰 가능한 특징을 구조화하고, 제작 가능한 규칙으로 환원한다.

예:

```text id="3jvvkc"
관찰
↓
측정
↓
특징 정리
↓
제작 규칙 후보
↓
테스트
↓
디렉터 판단
```

이 과정을 통해 Art Direction이 점차 구체화될 수 있다.

---

# 22. 하나의 숫자로 스타일을 정의하지 않는다

예를 들어 픽셀 아트에서 캐릭터 높이가 64px이라고 해서 스타일이 정의된 것은 아니다.

같은 64px에서도 다음이 다를 수 있다.

* 색 수
* outline
* shading
* proportion
* texture
* animation
* silhouette
* contrast

따라서 스타일은 여러 축의 조합으로 기록한다.

---

# 23. 스펙트럼으로 생각할 수 있다

일부 특성은 이진 값보다 스펙트럼으로 보는 것이 유용하다.

예:

```text id="oy17k7"
낮은 디테일 ───────── 높은 디테일

제한 팔레트 ───────── 넓은 팔레트

하드 outline ──────── outline 없음

에셋 중심 조명 ─────── 엔진 중심 조명

단순 형태 ─────────── 복잡한 형태
```

이 스펙트럼은 순위를 의미하지 않는다.

각 프로젝트가 어느 위치에 있는지를 이해하기 위한 좌표다.

---

# 24. 숫자는 디렉팅 언어를 보조한다

가능하다면 일부 스타일 요소를 측정할 수 있다.

예:

```text id="iltoz0"
sprite height: 48–64px
palette target: 24–40 colors
value steps: 4–5
outline: 1px
animation: 6–8 frames
```

하지만 숫자가 디렉팅을 대체하지 않는다.

예:

```text id="31yyo3"
BAD:
64px이므로 올바른 스타일이다.

GOOD:
현재 64px 밀도에서는 얼굴과 무기 실루엣이 잘 읽히며,
디렉터가 원하는 단순하고 장난감 같은 인상과도 맞는다.
```

---

# 25. `ART_DIRECTION.md`와 `STYLE_SPEC.md`

향후 각 게임 프로젝트에는 필요에 따라 다음 두 문서를 사용할 수 있다.

```text id="kgf74j"
ART_DIRECTION.md
STYLE_SPEC.md
```

## ART_DIRECTION

주로 다음을 담는다.

* 비주얼 목표
* 분위기
* 주요 레퍼런스
* 형태 언어
* 캐릭터 방향
* 환경 방향
* 금지사항
* 디렉터가 중요하게 생각하는 감각적 기준

## STYLE_SPEC

주로 다음을 담는다.

* dimensions
* palette constraints
* outline
* tile size
* animation frame ranges
* texture dimensions
* engine-related art constraints

두 문서의 구체적인 템플릿은 별도로 정의한다.

---

# 26. 초기에는 모르는 값이 있어도 된다

새 게임의 아트 방향이 시작부터 완성되어 있다고 가정하지 않는다.

예:

```text id="8csg9k"
outline: undecided
palette size: exploratory
character proportion: 3 candidates
lighting: engine test required
```

같은 상태가 존재할 수 있다.

불확실한 값을 억지로 확정해서 빈칸을 채우지 않는다.

Art Direction은 제작과 검토를 통해 발전할 수 있다.

---

# 27. 결정의 성숙도를 구분할 수 있다

필요하다면 방향의 상태를 개념적으로 다음과 같이 이해할 수 있다.

```text id="vn43hu"
exploring
→ preferred
→ decided
→ established
```

다만 이번 문서에서 복잡한 상태 관리 시스템을 만들지 않는다.

핵심은:

> 탐색 중인 아이디어와 확정된 아트 규칙을 동일하게 취급하지 않는 것

이다.

---

# 28. 국소 규칙과 전역 규칙을 구분한다

특정 자산에 대한 결정이 게임 전체의 규칙이라는 보장은 없다.

예:

> “이 보스는 outline 없이 만들자.”

가 곧:

> “이 게임의 모든 캐릭터에서 outline을 제거한다.”

라는 뜻은 아니다.

다음 범위를 구분한다.

```text id="rtosym"
project-wide
category-wide
asset-family
individual asset
```

디렉터의 지시를 필요 이상으로 일반화하지 않는다.

---

# 29. 금지사항도 아트 디렉션이다

무엇을 원하는지만큼 무엇을 원하지 않는지도 중요하다.

예:

* 지나치게 사실적인 얼굴 금지
* glossy 3D 느낌 금지
* 과도한 bloom 금지
* 너무 많은 미세 디테일 금지
* 모바일 게임 광고 같은 표현 금지
* 특정 시대와 맞지 않는 요소 금지

이런 정보는 제작 실패를 줄이는 중요한 방향 정보다.

---

# 30. 실제 게임 화면이 최종 기준이다

아트 방향은 개별 에셋만으로 완성되지 않는다.

필요한 경우:

```text id="6aaqhc"
asset
+
camera
+
environment
+
lighting
+
VFX
+
UI
=
actual game image
```

로 판단한다.

따라서 스타일 규칙이 이미지 파일에서는 맞아 보이더라도 실제 게임 화면에서 실패하면 다시 조정할 수 있다.

---

# 31. 생성기 프롬프트와 아트 디렉션을 동일시하지 않는다

특정 생성기용 프롬프트는 Art Direction의 **파생물**이다.

예:

```text id="n8s0wp"
ART DIRECTION
      ↓
asset requirement
      ↓
tool-specific instruction
      ↓
generator prompt
```

생성기를 변경했다고 해서 게임의 아트 방향이 바뀌어서는 안 된다.

한 프로젝트가 여러 생성기를 동시에 사용할 수도 있다.

---

# 32. 특정 유명 작품 이름에 지나치게 의존하지 않는다

초기 탐색에서는 다음과 같은 표현이 유용할 수 있다.

```text id="24muh5"
셀레스트 정도의 밀도
옥토패스처럼 조명을 활용
90년대 역사 전략게임 초상화 느낌
```

하지만 방향이 확정될수록 이를 프로젝트 자체의 언어로 환원한다.

예:

```text id="eb4wpl"
캐릭터 높이 48–64px
제한 팔레트
강한 실루엣
엔진 중심의 volumetric lighting
배경은 캐릭터보다 낮은 contrast
```

이를 통해 특정 레퍼런스에 종속되지 않고 자체적인 아트 기준을 만든다.

---

# 33. 자산 종류별로 같은 속성의 중요도가 다르다

모든 아트 축을 모든 자산에 똑같이 적용하지 않는다.

예:

## 캐릭터

중요:

* silhouette
* proportion
* face readability
* animation
* equipment readability

## 배경

중요:

* density
* depth
* color hierarchy
* lighting
* navigation readability

## UI icon

중요:

* readability
* shape
* edge
* contrast
* consistency

## VFX

중요:

* timing
* brightness
* silhouette
* blending
* motion

필요한 속성만 사용한다.

---

# 34. 스타일 시스템은 창작을 막는 규격표가 아니다

Art Direction을 너무 엄격한 체크리스트로 만들어 새로운 아이디어를 막지 않는다.

규칙은 다음을 위해 존재한다.

* 방향을 기억한다.
* 여러 자산의 일관성을 유지한다.
* 다른 도구로 전달한다.
* 반복되는 실패를 줄인다.
* 디렉터의 판단을 명확히 한다.

새로운 시도가 더 좋은 결과를 만든다면 디렉터 판단을 통해 규칙을 변경할 수 있다.

---

# 35. 이 문서에서 다루지 않는 것

다음은 다른 문서의 역할이다.

* 특정 도구를 언제 사용하는가
* 이미지 생성 과정의 실제 순서
* 후보 생성 개수
* 승인 절차
* asset lifecycle
* 파일 naming
* export 규격
* Unity/Godot/Roblox 상세 설정
* prompt template
* 스타일 검사 자동화의 구체적인 구현
* `ART_DIRECTION.md`의 실제 템플릿 내용
* `STYLE_SPEC.md`의 실제 템플릿 내용

이번 문서는 **아트 방향을 어떤 언어와 구조로 이해할 것인가**만 정의한다.

---

# 36. 문서 마지막의 핵심 원칙

마지막에는 다음 의미가 드러나도록 정리한다.

> 화풍은 하나의 이름이나 생성 프롬프트가 아니라 여러 시각적 축과 디렉터의 의도가 결합된 결과다.
>
> Art Studio는 그 방향을 관찰하고 구조화하고 측정 가능한 부분을 규격화할 수 있지만, 스타일의 최종 의미를 자동으로 결정하지 않는다.
>
> 감각적인 Art Direction과 기술적인 Style Specification을 함께 사용한다.
>
> 레퍼런스는 복제 대상이 아니라 방향을 이해하기 위한 자료다.
>
> 최종 기준은 개별 이미지가 아니라 실제 게임에서 만들어지는 시각적 경험이다.

문장을 그대로 복사할 필요는 없지만 의미는 유지한다.

---

# 작성 원칙

* 한국어로 작성한다.
* 기존 문서들의 역할을 반복하지 않는다.
* “화풍”을 구체적인 시각적 축으로 분해하는 데 집중한다.
* 특정 스타일을 기본값으로 정하지 않는다.
* 특정 게임을 기준으로 일반화하지 않는다.
* 픽셀 아트에만 치우치지 않는다.
* 2D와 3D, 캐릭터와 환경, 에셋과 엔진 효과를 모두 고려한다.
* 감각적인 언어와 측정 가능한 규격을 모두 인정한다.
* 모든 것을 숫자로 환원하려 하지 않는다.
* 반대로 모든 것을 주관적 표현으로만 남기지도 않는다.
* 레퍼런스를 그대로 복제하는 사고방식을 만들지 않는다.
* 생성기 프롬프트를 프로젝트의 아트 방향 자체로 취급하지 않는다.
* 아직 결정되지 않은 값을 억지로 채우지 않는다.
* 실제 게임 화면에서 다시 판단할 수 있는 구조를 유지한다.
* 후속 `ART_DIRECTION.md`, `STYLE_SPEC.md`, Generation Workflow 문서가 세부사항을 확장할 수 있도록 범위를 지킨다.

완성 후:

1. `docs/04_ART_DIRECTION_SYSTEM.md`를 생성한다.
2. 전체 내용을 출력한다.
3. 이 문서가 정의한 주요 아트 방향 축을 짧게 요약한다.
4. 기존 문서를 수정하지 않는다.
5. 다른 문서나 폴더를 생성하지 않는다.
6. 다음 단계로 진행하지 말고 멈춘다.
