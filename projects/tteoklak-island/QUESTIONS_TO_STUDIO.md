# 스튜디오에 묻는다 — 떡락섬 제작에서 막힌 것

작성 2026-08-17 · 보낸 곳: 게임 저장소 쪽 작업 세션
전략: [`PRODUCTION_STRATEGY.md`](PRODUCTION_STRATEGY.md) · 자산 목록: [`brief/ASSET_MANIFEST.md`](brief/ASSET_MANIFEST.md)

목표는 흔들리지 않는다 — **`references/` 4장의 플레이 화면에 실제로 도달하는 것.**
아래는 지금 그 길에서 막혀 있는 것과, 스튜디오가 답해 주면 풀리는 것이다.

문서를 먼저 읽고 썼다. **이미 답이 있는 것은 묻지 않았고, 아래 §0에 적어 두었다.**

## 0. 문서에서 이미 답을 찾은 것 (묻지 않는다)

| 내가 막혔던 것 | 문서의 답 |
|---|---|
| 캔버스가 미정인데 검사기를 어떻게 두나 | `09` §5 **「미정 값을 FAIL 조건으로 만들지 않는다」** — 그대로 따랐다. 크기 검사를 비워 두고 경고도 안 낸다 |
| 후보와 승인본을 어떻게 가르나 | `06` 전체. 그대로 채택했고 `candidates/` · `approved/` 를 만들었다 |
| 프레임 수를 몇으로 하나 | `04` §17 **「4프레임 걷기와 8프레임 걷기는 부드러움의 차이가 아니라 다른 화풍」** — 규격이 아니라 화풍 결정이라는 뜻으로 읽었다 |
| 형태가 프레임마다 흔들리는 문제 | `05` §10 **「여러 방향이나 여러 프레임에서 형태가 흔들리면 안 되는 작업에서 3D 소스는 강력한 기준점」** — 이건 §3에서 다시 묻는다 |

## 1. 그림을 만들 수단이 없다 — 가장 큰 문제

**증상.** 자산 하나마다 사람이 손으로 왕복한다.

```
내가 주문서를 조립 → 사람이 복사 → ChatGPT 에 붙여넣기 → 앵커 4장 첨부
→ 생성 → 내려받기 → 나에게 파일 경로를 알려 줌 → 내가 배치
```

지금까지 배경 2장에 이 왕복을 두 번 했다. 남은 자산은 **배경 4 · 초상화 5명×표정 · 캐릭터 5명 ·
아이콘 12** 다. 후보를 3~4장씩 받기로 했으므로 왕복 횟수는 **100회를 넘는다.**

**내가 확인한 것.** 이 세션에 이미지 생성 도구가 없다. `05` §16이 MCP를 **연결 계층**으로 규정하고
있고 「생기는 것은 연결의 편의」라고 적혀 있는데, **그 연결이 실제로 붙어 있지 않다.**

**묻는 것**

1. 이 스튜디오에서 **승인된 이미지 생성 연결 방식**이 있는가? (MCP 서버 / API / 로컬 도구 중 무엇)
2. 없다면, **붙이는 것이 스튜디오의 일인가 게임 쪽의 일인가?** `03` 은 `studio/tools/` 를
   공통 자산으로 두는데, 생성기 연결도 거기 속하는가
3. 붙일 수 없다면 — 왕복 100회를 줄이는 다른 방법이 있는가.
   (예: 한 대화에서 여러 장면을 연속 주문하는 것이 R4 「주문 하나 = 새 대화 하나」와 충돌한다)

**이게 안 풀리면 나머지는 전부 느려진다.**

## 2. `studio/tools/` 가 비어 있다 — 무엇을 어디에 쌓나

**현재.** 실행 파일이 **1개**다. 어젯밤 내가 넣은 `contact_sheet.py`.
`05` §15가 필요한 목록을 이미 알고 있다 — 「dimensions 검사 · palette extraction · alpha check ·
batch resize · **contact sheet** · sprite packing · format conversion · manifest generation · export」.

**내가 이미 만든 것들이 두 저장소에 흩어져 있다.**

| 도구 | 지금 위치 | 하는 일 |
|---|---|---|
| `contact_sheet.py` | **스튜디오** `studio/tools/` | 후보를 앵커와 나란히 한 장으로 |
| `check_assets.py` | **게임** `tests/` | 크기 · 알파 · 가장자리 잔여 (화풍은 판정 안 함) |
| `tone_match.py` | **게임** `tools/` | 채도 보정. **만들다 멈췄다** — 판정 도구로 흐를 위험이 있어서 |

**묻는 것**

1. `check_assets.py` 는 스튜디오로 올라와야 하는가? `11` §3 「기술은 공통화하고 값은 프로젝트에
   남긴다」로 보면 **검사 능력은 공통, 규격 값은 프로젝트**인데, 지금은 통째로 게임에 있다
2. `tone_match.py` 를 **살릴 것인가 지울 것인가.** 디렉터가 「아트워크는 눈으로 본다」고 못 박았고
   나는 그 뒤로 손대지 않았다. 다만 §11 「이미지 편집 도구」는 색 보정을 정상 단계로 본다.
   **보정 도구를 갖는 것과 판정하지 않는 것이 양립하는가?**
3. 앞으로 만들 도구(배경 세로 크롭 · 스프라이트시트 조립)는 어느 쪽에 두는가

## 3. 캐릭터 145프레임 — 방법을 모른다

**측정한 것.** 게임의 `Actor.gd` 가 요구하는 것:

```
걷기 방향당 6프레임 × 방향 4 = 24 · 대기 3 · 말하기 2
인물 하나당 약 29프레임 × 명명 인물 5명 = 145프레임
```

**AI 생성기는 이걸 일관되게 못 만든다.** 프레임마다 얼굴·옷·비율이 흔들린다.
그리고 **앵커에는 이 문제가 보이지 않는다 — 앵커의 인물은 걷지 않기 때문이다.**

**내가 정리한 네 갈래** — 컷아웃 퍼펫 / 프레임 생성 / 프레임 축소 / 미룸.
`04` §17을 읽고 나서 **프레임 수를 「규격」이 아니라 「화풍 결정」으로 다시 보게 됐다.**

그리고 `05` §10을 읽고 다섯 번째가 생겼다.

```
3D blockout → render → paint → 2D game asset
```

**묻는 것**

1. **이 화풍(회화적 일러스트, 도트 아님)에서 3D blockout 경로가 성립하는가?**
   문서는 「여러 방향·프레임에서 형태가 흔들리면 안 되는 작업」에 쓰라고 한다. 정확히 내 상황이다.
   다만 앵커의 붓질과 밀도를 3D 렌더 위에 얹는 것이 현실적인지 판단이 안 선다
2. 컷아웃 퍼펫(파츠 분리 + 변형)과 3D blockout 중 **이 화풍에 어느 쪽이 맞는가.**
   스튜디오에 비슷한 제작 경험이 쌓여 있는가 (`11` 이 말하는 그 축적)
3. 아니면 **프레임 수 자체를 화풍 결정으로 다시 잡아야 하는가** — 6프레임 걷기가 이 화풍의 전제가
   아닐 수 있다. 그렇다면 그건 디렉터 결정 사항이 되고, 나는 선택지를 만들어 올려야 한다

## 4. 후보를 몇 장 받아야 하는가

**현재.** 3~4장으로 정했다. **근거가 없다.** 내가 그냥 정했다.

한 장씩 받았을 때 「고를 것이 없다」는 문제가 실제로 생겼고, 그래서 늘렸다.
다만 몇 장이 적정인지는 모른다 — 많으면 왕복 비용이 늘고(§1), 적으면 선택이 안 된다.

**묻는 것** — `08` 이 「후보를 제시하는 방식」을 다루는데, **장수에 대한 기준이 있는가?**
자산 종류마다 다른가 (배경 vs 초상화 vs 아이콘).

## 5. 두 저장소 사이를 누가 옮기나

**결정된 것.** 후보는 스튜디오, 승인본만 게임으로 (전략 §4).

**결정 안 된 것.** `approved/` → `exports/` → 게임 `assets/` 의 실제 이동을 **누가 언제 하는가.**
지금은 내가 손으로 복사한다. `10` 이 Export 를 다루지만 **파일을 옮기는 주체**는 안 적혀 있다.

**묻는 것**

1. export 를 **스크립트로 만들어야 하는가**, 아니면 수동이 정상인가
2. 게임 저장소에 들어간 자산이 나중에 스튜디오에서 갱신되면 **어느 쪽이 정본인가**
3. `REVIEW_LOG.md` 를 **누가 쓰는가.** 템플릿은 있는데 아직 한 줄도 없다.
   내가 후보를 올릴 때 쓰는가, 디렉터가 고른 뒤에 쓰는가

## 6. 화풍이 그림에서 나오는 프로젝트를 어떻게 다루나

**상황.** 이 게임의 아트 정본은 **디렉터가 만든 콘셉트 4장**이다. 문서가 아니라 그림이 최상위다.
(기획서 §23 · 2026-08-12 결정)

그래서 `STYLE_SPEC.md` 를 아직 안 만들었다. 만들면 **그림에서 읽은 것을 글로 옮기는 일**이 되는데,
그 글이 그림과 어긋나는 순간 규격이 거짓말이 된다. 실제로 그런 일이 있었다 —
내가 「밀도가 실제 화면보다 높다」고 적었다가 재보니 사실이 아니었다.

**묻는 것**

1. **그림이 정본인 프로젝트에서 `STYLE_SPEC` 은 어떤 성격이어야 하는가?**
   측정값만 적는 문서인가, 아니면 안 만드는 게 맞는가
2. `04` §31 「생성기 프롬프트를 아트 디렉션과 동일시하지 않는다」를 지키면서,
   **앵커 첨부가 화풍 지정의 유일한 수단**인 상태를 어떻게 문서화하는가

## 7. 배경이 게임에 안 들어간다 (참고 — 스튜디오 일이 아닐 수 있다)

**확인한 것.** 세로 배경(1024×1536)을 가로 무대(320×135)에 넣으면
찌그러지거나(세로 3.56배 압축) 잘린다(원본 세로의 28%만 남음).
화면 증거: [`reviews/2026-08-17_background-integration/`](reviews/2026-08-17_background-integration/)

**이건 엔진 쪽 문제다.** `10` §13 「문제 위치를 구분한다」로 보면 Source 가 아니라 Engine 이고,
`STUDIO_USAGE_CONTEXT` §7 은 스튜디오가 개발 코드를 흡수하지 않는다고 한다.

**그래서 묻는 것은 하나뿐이다** — 이 상태에서 **배경 주문을 계속해도 되는가?**
내 판단으로는 «주문은 해도 되고 통합만 못 한다» 인데(일러스트는 크게 받아 줄이면 되므로),
스튜디오가 다르게 보면 순서를 바꿔야 한다.

## 덧 — 내가 이미 지키고 있는 것

스튜디오가 확인하고 싶을 수 있어 적어 둔다.

- **미적 판단을 하지 않는다.** 톤 거리로 그림을 «불합격» 시키는 게이트를 만들었다가 디렉터에게
  제지당했고, 걷어냈다. 지금 검사기는 크기·알파만 본다 (`02` §4의 경계)
- **후보와 승인본을 구분한다** (`06`)
- **게임 화면에서 확인한다** — 파일만 보고 끝내지 않았다 (`08` §11 · `10` §9)
- **측정과 의견을 구분한다** — 숫자는 재고 적었고, 못 잰 것은 「확인 필요」로 남겼다 (`05` §5)
- **게임 저장소의 코드를 임의로 바꾸지 않았다** (`CLAUDE.md` §9). 배경 통합 시험 후 원상복구했다
