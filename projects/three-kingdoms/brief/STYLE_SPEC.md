## 1. 현재 적용 범위

**규칙이 있는 영역:**

- 화면 비율과 3단 구조 (목업 4장에서 회수 · §3)
- 런타임 제약 (게임 코드에서 확인 · §14)
- 자산 전달 형태와 용량 (§14 · §16)
- 초상 — **게임 저장소가 소유한다.** 여기서는 참조만 (§3 Portrait)

**아직 정의하지 않은 영역:**

- **픽셀 배율** — 앵커에서 결정 (§3 · §19)
- 지도 타일 크기 및 타일 사용 여부
- 전투 타일 크기 (격자 «성격»은 판정됨 · §9)
- Outline 두께 · 색
- 팔레트 (목업 실측값은 있으나 확정 팔레트가 아니다 · §5)
- 아이콘 그리드 · 선 두께
- 9-slice 규격
- 애니메이션 전반
- 광원 방향

## 2. 표현 방식

- 기본 표현 방식: **hybrid — 이것이 이 프로젝트의 미해결 지점이다**
  - 월드(지도·전투·UI) = 픽셀 아트 지향
  - 초상 = 회화 (반신 유화) → 현재는 95×110 도트로 변환해 넣는다
  - 목업은 둘을 한 화면에 얹었다. 접점 규칙은 §17 · REQUEST Q1
- Source type: PNG. 초상만 생성기 원화(대형) → 도트 변환본의 2단 구조
- Runtime 표현: PNG (파일 또는 data URL) + Canvas 2D `drawImage`
- 2D / 3D 혼합: 없음. **2D 전용**
- 카메라 전제: 고정 orthographic 2D. 화면마다 투영이 다르다 (§9)
- Color mode: RGB(A) 8bit
- Alpha 사용: 사용. **binary alpha 권장** — 픽셀 자산에서 부분 알파는
  `image-rendering: pixelated` 와 함께 가장자리를 지저분하게 만든다

**보충:** 현재 게임은 **외부 이미지 자산이 사실상 0**이고 지도·전투·UI 를 코드가
절차적으로 그린다. 이 발주는 그 일부를 그림 자산으로 교체하는 작업이며,
**절차적 렌더와 그림 자산이 한 화면에서 섞이는 상태**가 당분간 정상이다 (§17).

## 3. 해상도와 크기

### 3-1. 확정 — 화면 비율과 3단 구조

목업 4장에서 일관되게 회수됐다 (FINDINGS §2-1 · §2-2). **비율이므로 픽셀 격자와 무관하다.**

- Aspect ratio: **9:16 세로** (941/1672 = 0.5628, 9:16 = 0.5625 — 0.5px 차)
- 화면 3단 (비율로 고정):

| 띠 | 비율 | 941×1672 에서 |
|---|---|---|
| 상단 HUD | 6.3% | 106px |
| 콘텐츠 | 85.0% | 1421px |
| 하단 탭바 | 8.7% | 145px |

### 3-2. 미정 — 논리 해상도와 픽셀 배율

**목업에서 회수 불가.** 아래는 후보이며 확정이 아니다.

#### 이 결정을 가르는 계산

목업의 요소 크기는 **화면 폭 대비 비율**로는 회수된다. 그것을 논리 해상도별로
환산하면 결정의 성격이 드러난다.

| 요소 | 목업 941px 폭 대비 |
|---|---|
| 인물 마커 | 8.3% |
| 전투 격자 셀 | 11.4% |
| 무장 상세 초상 | 64.8% |
| 성채 (허창) | 25.5% |

논리 폭 `W` 를 정하면 **인물 마커의 실제 도트 수**가 따라 나온다.

| 논리 폭 W | 마커 (8.3%) | 전투 셀 (11.4%) | 얼굴이 읽히는가 |
|---|---|---|---|
| 270 | **22px** | 31px | 불가 |
| 360 | **30px** | 41px | 불가 |
| 470 | **39px** | 54px | 어렵다 |
| 640 | **53px** | 73px | 아슬아슬 |
| **720** | **60px** | 82px | **가능** — 초상 규약이 전제한 60×62 와 일치 |
| 941 | 78px | 107px | 가능 (목업 실측) |

> **이 표가 §5 의 「픽셀 배율」 질문에 대한 실질적인 답이다.**
>
> 초상 규약 `docs/portrait-style-guide.md` §7 은 마커 60×62 를 전제로
> 「축소를 견디는 그림」 세 규칙을 세웠고, 24×28 에서는 「다 지켜도 얼룩이 되었다」고 적었다.
>
> 즉 **초상이 월드와 같은 픽셀 격자 위에 있으려면 논리 폭이 720 이상이어야 한다.**
> 그런데 논리 폭 720 을 1080 기기에 띄우면 배율이 1.5× — **정수 배율이 깨진다.**
> 정수 배율을 지키려면 배율 1× 가 되고, 그러면 **도트의 굵기라는 것이 사라진다.**
>
> 반대로 도트를 굵게(360 논리 · 3배) 가면 마커가 30px 가 되어
> **초상 파이프라인 전체가 성립하지 않는다.**
>
> **「굵은 도트」와 「회화 초상」은 한 격자 위에서 동시에 성립하지 않는다.**
> 이것이 Q1(두 화풍의 공존)의 기술적 실체다. 취향 문제가 아니라 산술 문제다.

#### 후보 3안

**A안 — 2층 분리 (월드는 굵은 도트 / 초상·글자는 기기 해상도)**

```
월드 레이어   360×640 논리, 정수 3배 → 1080×1920      canvas #1  pixelated
UI·초상 레이어 기기 해상도 그대로                        canvas #2  smooth
```

- 도트가 굵어 픽셀 아트로 읽힌다. 초상은 회화 그대로 살아난다
- 두 레이어의 경계 = **프레임** (ART_DIRECTION §13 의 「프레임이 국경」과 정확히 일치)
- 비용: 캔버스 2장, 좌표계 2개. 절차적 렌더가 어느 층에 있는지 정리 필요
- 목업의 인상에서 **가장 멀다** (목업은 도트가 이만큼 굵지 않다)

**B안 — 단일 미세 격자 (목업에 가장 가깝다)**

```
전 화면       720×1280 논리, 배율 1~1.5×
```

- 목업의 인상을 그대로 낸다. 초상 60px 확보
- **정수 배율이 대부분의 기기에서 깨진다.** `image-rendering: pixelated` 의 의미가 옅어진다
- 사실상 「픽셀 아트」가 아니라 「픽셀 질감의 회화」가 된다 — 목업이 실제로 그런 물건이다
- 제작 난도가 가장 높다. 720 폭 지도 바탕은 그리기도 생성하기도 어렵다

**C안 — 단일 굵은 격자 (초상을 도트로 내린다)**

```
전 화면       360×640 논리, 정수 3배 → 1080×1920
초상          ~30×32 도트로 재제작
```

- 가장 단순하고 가장 싸다. 정수 배율이 완전히 지켜진다
- **초상 파이프라인 22장 + 규약 전체를 버린다.** 발주서 §3 이 초상을 담당 밖으로
  둔 것과 정면 충돌한다
- 권장하지 않는다. 선택지로만 남긴다

> **Studio 의견: A안.** 근거는 §17 · REQUEST Q1.
> 다만 **확정은 디렉터가 한다.** 그리고 어느 안이든 **앵커 3~4장으로 실물 확인 후** 확정한다.

#### 정수 배율과 기기 폭

정수 배율을 지키면 기기 폭이 딱 나누어떨어지지 않는다. **레터박스가 필수다.**

```
논리 360 → 1080 기기 3배 ✓ · 1179 기기 3배(1080) + 99px 여백 · 1440 기기 4배 ✓
```

- 여백은 UI 바탕색(`#101010` 대역)으로 채운다
- **소수 배율로 늘려 여백을 없애지 않는다** — 반쪽 픽셀이 생긴다
- 안전 영역: 상단 노치·하단 홈 인디케이터. **HUD 와 탭바가 그 자리를 겸한다** —
  3단 구조의 위아래 띠가 안전 영역을 흡수하도록 설계되어 있다

### 3-3. Sprite · Tile · Portrait

**Sprite / Tile:** **전부 미정.** §3-2 확정 후에 결정한다.
논리 해상도가 정해지기 전에 타일 크기를 정하면 반드시 다시 만든다.

**Portrait** — 게임 저장소 소유. 여기서는 참조만 한다.

- 원화: 생성기 출력 (대형, 반신)
- 게임 반영본: **95×110** 도트 (`js/art.js`, `<canvas id="face" width="95" height="110">`)
- 표시: 현재 190×220 (2배)
- 목업에서의 다섯 자리: 상세 ~610×600 · 카드 ~156×160 · 전투 정보 ~85×110 ·
  전투 예상 ~80×100 · 지도 마커 **78×80**
- **마커 78×80 확정 (Q7 닫힘).** 게임 쪽이 승인 초상 22장을 60×62 와 78×80 두 크기로
  실제 렌더해 확인했다 — **회화 흉상은 60 에서도 뭉개지지 않는다**
  (홍안·장수염·안대·면류관·유건이 두 크기 모두에서 남는다).
  초상 규약 §7 은 고치지 않는다. 60 을 전제로 세운 규칙이므로 78 이면 여유가 생길 뿐이다.
  → **따라서 마커는 Q1 을 세게 밀지 않는다.** §3-2 의 「720 이상이어야 한다」는
  근거가 약해졌다. **Q1 을 미는 것은 이제 마커가 아니라 밀도다**
  (`../HANDOFF_TO_GAME_02.md` §1)

## 4. 형태와 엣지

**Outline:**

- 사용 여부: **사용** (목업의 월드 스프라이트가 어두운 윤곽을 두른다 — 육안 확인)
- 두께: **미정.** 목업에서 회수 불가(연속 계조). §3-2 확정 후 「1도트」로 정의될 값
- 외곽선 / 내부선 구분: 미정
- 색상 규칙: **자산 색의 어두운 변형** 방향 (검정 단색 아님) — 탐색 중
- 예외: UI 는 윤곽 대신 금테를 쓴다 (ART_DIRECTION §10)

**Edge:**

- Edge 성격: hard
- Antialiasing: **월드 자산 금지.** 초상은 A안 채택 시 허용
- Pixel snapping: **필수**
- Pixel grid 준수: **필수** — 단, 그 격자가 무엇인지가 §3-2
- Sub-pixel 표현 허용: **금지**

**디테일 밀도:**

- 최소 표현 단위: 1도트 (값 미정)
- 작은 디테일 제한: **미정.** 다만 방향은 확정 — 「갑옷 미늘 하나하나는 회색 죽이 된다」
  (초상 규약 §7 의 원칙을 화면 자산에 적용)

## 5. 색

**Palette:**

- Fixed palette 사용 여부: **미정.** 제한 팔레트를 쓸지 자유 색을 쓸지 결정 전
- Palette 파일 / 출처: 없음. **아직 만들지 않는다** —
  §3-2 가 정해지기 전에 팔레트를 확정하면 밀도와 맞지 않는다
- 목업 실측값 (**확정 팔레트가 아니라 관찰 기록이다**):

| 용도 | 실측 |
|---|---|
| UI 바탕 | `#101010` ~ `#202020` (패널 면적의 53~59%) |
| 탭바 | `#102020` · `#101020` (차가운 쪽 검정) |
| 금 강조 | `#d8a848` · `#c09030` · `#f0d878` · `#483000`(그늘) |
| 조 曹 | `#3048a8` |
| 손 孫 | `#a03030` |
| 유 劉 | `#304818` · `#306030` |
| 마 馬 | `#603090` |
| 원 袁 | `#a86018` |

- 세력색: **시나리오 «안»에서는 20색이 유일하다** (`js/game.js:68`, 세력 최대 20).
  다만 **7쌍이 지각적으로 붙어 있다** (CIE ΔE < 30, 최악 `#c08040`/`#e0a040` ΔE 18) —
  오렌지·갈색 3 · 파랑 3 · 초록 3계열. 78px 테두리처럼 작은 면적에서는 더 붙는다.
  **재설계 필요. 목표는 모든 쌍 ΔE ≥ 35** → `IDENTIFICATION_SYSTEM.md` §3
- 상태색: 이동 초록 · 공격 빨강 · 경고 노랑. **세력 유(녹)·손(적)과 충돌한다.**
  해결책 미정 (ART_DIRECTION §19)

**Saturation / Value:** 현재 정량 규칙 없음.
정성 방향만 있다 — 채도는 낮게, 금색과 세력색만 채도를 갖는다.

**Transparency:**

- Alpha 허용: 허용
- Partial alpha 허용: **월드 픽셀 자산에서 비권장.** UI 그림자·오버레이는 허용
- Binary alpha 필요 여부: 픽셀 자산 **권장**
- 투명 영역 RGB 처리: **미정** — 확인 필요 (fringe 방지를 위해 인접색 유지 권장)
- Premultiplied alpha: 사용 안 함 (Canvas 2D 기본)

**Color space:** sRGB · 8bit · HDR 없음

## 6. 명암과 조명

**Shading:**

- 기본 방식: **미정.** flat 인지 dithered 인지가 §3-2 와 함께 결정된다
- Value step 수: 미정
- Gradient 허용: **월드 자산 금지** 방향 (ART_DIRECTION §10 「매끄러운 그라데이션 금지」)
- Dithering: 미정 — 굵은 도트(A안)에서는 유효하고 미세 격자(B안)에서는 무의미하다

**Source와 Engine의 책임:**

- Source 에 baked 되는 요소: **전부.** 그림자 · 하이라이트 · 시간대
- Engine 이 담당하는 요소: **없음**
- Dynamic lighting 대응: **불필요.** Canvas 2D, 셰이더 없음
- Normal map / Emission: 사용 안 함

> 이 프로젝트에는 런타임 조명이 없다. **「에셋 그림자 + 엔진 그림자」의 이중 적용
> 사고가 구조적으로 일어나지 않는다.** 대신 광원 방향을 자산이 스스로 지켜야 한다.

**Shadow:**

- Cast shadow 를 source 에 포함: **포함한다** (엔진이 못 만든다)
- 광원 방향 고정 여부: **고정해야 한다. 값은 미정.**
  목업 3장이 서로 다르다 — m1 좌상 · m4 상단 · m3 좌측 (FINDINGS §3).
  좌상 고정이 무난하나 **근거가 관습뿐이므로 앵커에서 확정한다**

## 9. 환경 / 소품 / 타일

### 9-1. 확정 — 격자의 «성격» (크기가 아니라 성격이다)

FINDINGS §2-3 · §2-5 에서 판정됐다.

**전투 격자 — 정사각 top-down. 등각이 아니다.**

```
세로선 간격  107, 109, 105, 109   → 107.5 ± 2   (매우 안정)
가로선 간격  94, 102, 104, 107, 95, 111 → 102 평균
셀 비율      107 : 102 ≈ 1.05 : 1
```

- **깊이감은 투영이 아니라 그려진 지형과 스프라이트 크기에서 온다**

**지도 성채 — 축측(비스듬한 부감) 디오라마.** 성벽에 두께와 측면이 그려져 있다.

> **한 게임에 투영이 둘이다.** 잘못은 아니지만 의도 확인이 필요하고,
> 성채를 전투 타일 위에 재사용할 계획이 있다면 지금 갈라야 한다 → REQUEST Q6

## 14. 엔진 / 런타임 제약

**이 장은 확정이다.** 게임 코드에서 직접 확인했다.

- Engine / Rendering path: **없음.** HTML + Canvas 2D + 순수 JS.
  빌드 없음 · 의존성 없음 · 번들러 없음
- Filtering: **point** — `image-rendering: pixelated; image-rendering: crisp-edges;`
  (`css/style.css:60`, 모든 canvas 에 적용)
- Compression: PNG (무손실). 사진 계열 대형 자산은 WebP 검토 가능
- Mipmaps / Max texture size: 해당 없음
- Pixels per unit: 해당 없음 (직접 `drawImage`)
- Color space: sRGB
- Atlas 제한: 없음. **다만 빌드가 없으므로 아틀라스 슬라이싱을 런타임 코드가 해야 한다**
- Camera 로 인한 art constraint: 고정 2D
- **정수 배율 제약: 현재 CSS 가 「모든 수치는 2px 격자」로 서 있다** (`css/style.css:3`)

### 자산 전달 형태 (발주서 §9 에 대한 답)

**현재 문제:** 초상이 data URL 로 `js/art.js` 에 박혀 있다 — 22장에 244KB.
181장이면 약 2MB 이고, **파싱 비용까지 붙어 첫 화면을 막는다.**

> **먼저 포맷이다 (2026-08-17 게임 쪽 실측으로 추가).**
> 제 첫 제안은 「전달 형태」만 다뤘고 **포맷 축이 빠져 있었다.** 그것이 더 큰 갈림길이다.
>
> | 자리 | 크기 | PNG | **WebP q82** | 181명분 PNG | **181명분 WebP** |
> |---|---|---|---|---|---|
> | 반신 | 610×600 | 562 KB | **34.5 KB** | 99.3 MB | **6.1 MB** |
> | 카드 흉상 | 156×160 | 39.4 KB | **3.2 KB** | 7.0 MB | **0.6 MB** |
> | 마커 | 78×80 | 10.5 KB | **1.1 KB** | 1.9 MB | **0.2 MB** |
>
> **회화는 연속 계조라 PNG 가 16배 부푼다. PNG 로는 어떤 전달 형태를 써도 안 된다.**
> → **회화 계열(초상·이벤트 배경)은 WebP.**
> → **픽셀 계열(타일·아이콘·스프라이트)은 PNG 를 유지한다** — 색 수가 적어 PNG 가 유리하고,
>   손실 압축은 도트의 가장자리를 망친다.
> 포맷이 화풍을 따라 갈린다.

**제안하는 규칙 — 자산군마다 다르게 간다.**

| 자산군 | 형태 | 이유 |
|---|---|---|
| **초상 181** | **개별 WebP · 3단(반신/카드/마커) + 지연 로드** | 한 화면에 동시에 뜨는 것은 6~8장뿐. 첫 화면에 필요한 것은 마커뿐 — **0.2MB**. **data URL 에서 반드시 내려야 한다.** 게임 쪽에서 처리한다 |
| 지도 바탕 | 개별 파일 | 크고, 화면당 1장뿐 |
| 성채 · 깃발 · 지형 장식 | **아틀라스 1장** + JSON 좌표 | 수가 많고 항상 함께 쓴다 |
| 아이콘 · UI 킷 | **아틀라스 1장** + JSON 좌표 | 첫 화면에 전부 필요하다 |
| 전투 타일셋 | 아틀라스 1장 | 전투 진입 시 함께 |
| 부대 스프라이트 | 아틀라스 1장 | 병종 × 세력색 × 자세 |
| 아주 작은 것 (구슬·점 등) | data URL 허용 | 요청 1건이 파일 크기보다 비싸다 |

- **아틀라스는 정수 좌표 · 자산 간 최소 2px 여백**(pixelated 라도 좌표 오차 방지)
- **JSON 좌표표를 함께 낸다.** 빌드가 없으므로 사람이 읽고 고칠 수 있어야 한다
- 절차적 렌더와 그림 자산의 혼재 규칙 → §17

## 17. 자산 간 일관성 규칙

- **회화 초상과 픽셀 월드는 프레임으로 가른다.**
  초상이 지형에 직접 닿는 자리를 만들지 않는다. 마커·카드·전투 정보 전부 프레임 안.
  프레임은 세력색 테두리를 갖고, 그것이 두 화풍의 국경 표시를 겸한다
  (→ 확정은 REQUEST Q1)
- **절차적 렌더와 그림 자산이 한 화면에 섞일 때** — 층으로 가른다.
  같은 층에서 절차적 도형과 그림을 섞지 않는다.

```
    아래   절차적 배경 (또는 그림 바탕)
      │    그림 자산 (성채 · 스프라이트 · 장식)
      │    마커 (얼굴 · 점)          ← UI 패널보다 «아래»
      │    절차적 오버레이 (격자 · 이동 범위 · 선택 표시)
    위     UI 자산 + 글자
```

  이유: 절차적 도형은 좌표를 자유롭게 잡지만 그림은 격자에 묶인다.
  섞으면 **어느 것이 반쪽 픽셀을 만들었는지 추적할 수 없다**
- **세력색은 모든 자산군에서 같은 값을 쓴다.** 배너·마커 테두리·부대 깃발·패널 강조
- **마커는 UI 패널 위로 올라타지 않는다.** 좌표판 D1 에서 실제로 발생했다 —
  지도 왼쪽 도시 패널과 오른쪽 시세 패널 위에 마커가 얹혔다
- **UI 아이콘과 월드 자산의 렌더링을 구분한다** — UI 는 평평하고 윤곽 대신 금테,
  월드는 그려지고 어두운 윤곽 (ART_DIRECTION §15)
